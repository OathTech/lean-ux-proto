## 1. Target

wg0 initiates a handshake with steered values (ephemeral key, timestamp,
index). A response computed offline (`harness/noise.py`) completes the
handshake. wg0 sends the staged keepalive through the encrypt and tx workers.
The check confirms:
- **behavior:** the initiation, the keepalive's 32 bytes at the fixture's
  sender, the dump's `last_handshake`;
- **control flow** over all of it, with the order of deferred units checked
  from section records;
- **operands.**

**Outside the domain** (fail-noisy):
- staged payload packets meeting a session;
- received data messages naming a keypair;
- timers firing;
- cookies under load;
- more than one item in a crypt queue;
- peer removal with pending crypt work;
- `wg_prev_queue`'s MPSC internals.

## 2. Rules for every stream

- **Project rules apply** (`AGENTS.md`):
  - behavioral mirror only, no theorem proving;
  - each C choice point on a modeled path is a mirror decision, in C order;
  - out-of-scope paths are `unsupported`;
  - fixture and timing knowledge stays in `Leanux/Env.lean`;
  - checks must pay for themselves.
- **Work only in your own worktree and branch** (section 4). Commit there
  often. Never touch `main`, other worktrees, the shared `.artifacts/kernel-*`
  directories, or anything outside the repository. Never push.
- **No machine-global changes.** The QEMU lock serializes VM runs; just wait
  for it. Build kernels only into your worktree's `.artifacts`.
- **Interfaces.** Stay inside the interfaces below. If one must change, stop
  and say so in your report; do not change shared files outside your
  ownership.
- **Your report:** what you built, the evidence (commands and results), open
  issues, and the commits.

## 3. Shared interfaces (commit on `task/d1-integration`, the base of every stream)

- **Types** (`Leanux/WG/Types.lean`):
  - `KeypairId`; `Keypair` (`sending`/`receiving` as `SymmetricKey`,
    `sendingCounter`, `iAmTheInitiator`, `remoteIndex`, `refcount`,
    `internalId`, `peer`);
  - `IndexEntry.keypair`;
  - `Peer.keypairCurrent`, `keypairPrevious`, `keypairNext`,
    `walltimeLastHandshake`, `serialWorkCpu`, `txQueue`;
  - `Device.keypairs`, `nextKeypairId`, `encryptLastCpu`, `encryptQueue`,
    `txWorkQueue`;
  - `DataPacket`, `PacketState`.

  The old `Peer.nextKeypair : Bool` stays until stream B migrates the
  responder code to the store.
- **Keypair references** (`Leanux/WG/Keypair.lean`): `keypairGet` and
  `keypairPut` mirror `wg_noise_keypair_get`/`put` over the store.
  `getKeypair`/`setKeypair` are in `State.lean`.
- **Deferred units** (`Leanux/Kernel/Defs.lean`, `Leanux/Env.lean`):
  - `Worker` (send, receive, encrypt and tx workers; `net_rx_action`);
  - choice sites `sectionStart w` / `sectionStop w` (kind `section`, file =
    the function's symbol, line 0 for start and 1 for stop, 8 bytes);
  - `Env.runWorker w body`, which consumes a section's start and stop records
    around the unit while `Env.SECTION_RECORDS` is true (false until stream A
    delivers).

  Today's three deferred runs (send worker, receive worker, `wg_receive` in
  the NET_RX softirq) already go through `runWorker`.
- **Section records** (stream A defines, everyone consumes). Kind 300 (start)
  and 301 (stop) in the existing choice-record format:
  - the call site is the dispatch point;
  - the start payload is the dispatched function's address (8 bytes, mapped
    by the evaluator to its symbol);
  - the stop payload is the number of records dropped in the section;
  - sequence numbers order them with every other record.

  A NET_RX section nested in a worker's section is a loopback delivery: the
  mirror consumes it at the delivery cut point
  (`skipCut [.sectionStart .netRx, .sectionStop .netRx]` in
  `sendBufferToPeer`), and its records sit between the start and stop.
- **Decision table** (`Leanux/Kernel/Decision.lean`): streams B and C add
  constructors in their own blocks (comment `-- D1 stream B` / `-- D1 stream
  C`) to keep merges additive. Labels follow the existing
  `function.condition` style.
- **Expected outcomes** used by stream D's traces (existing labels):
  - `wg_receive_handshake_packet.response=1`
  - `wg_noise_handshake_begin_session.initiator=1`
  - `add_new_keypair.initiator=1`
  - `wg_packet_send_staged_packets.no_keypair=0`

## 4. Streams

**A — kernel and dispatch** (branch `task/d1-s1`, worktree `.worktrees/d1-s1`).

Owns: `kernel/patches/*`, `scripts/build-kernel`, `kernel/identity-*`,
`harness/guest.c` (sections, teardown), `harness/linux.py`, the section parts
of `evaluator/check.py`, `harness/steer.py` if needed, `Env.SECTION_RECORDS`.
- **Sections.** Dispatch-level KCOV remote sections, armed per trace:
  - an ioctl on the parent's remote fd loads the **dispatch set** (function
    addresses resolved on the host from `vmlinux`);
  - `process_one_work` opens a section with the trace's handle iff
    `worker->current_func` is in the set;
  - the NET_RX vector in `handle_softirqs` does the same when armed;
  - no timer sections in D1;
  - each section writes start and stop records (section 3);
  - nothing nests in task context; a softirq section inside a task section
    is allowed.
- **Retired:** the per-site sections. That is
  `kernel/patches/wireguard-kcov-remote.patch` (the `wg_receive` and receive
  worker sections) and the send-worker section and device handle in
  `choice-stream.patch`, so `choice-stream.patch` absorbs everything into
  one patch.
- **Dropped sections fail.** A section dropped because its handle is
  unregistered or its area busy increments a counter; the guest reads it
  after each trace, and nonzero fails the trace.
- **Synchronous teardown.** The guest deletes wg0 with `RTM_DELLINK` at trace
  end, before disarming, so no earlier device's workers or timers run under
  a later trace.
- **Evaluator.**
  - Map section records (kinds 300 and 301) to the `section` sites by
    symbol.
  - Handle the record from `wg_timers_handshake_complete`'s wall-clock read
    (`timers.c:197`), which is reached by a tail jump: find its real
    consumer frame in this build and report it, so stream B declares the
    site.
- **Acceptance.** On the existing suites, with `SECTION_RECORDS = true`, the
  WireGuard suite and the FS suites agree, and the section records show the
  worker order. The encrypt and tx workers are in the dispatch set; check
  coverage there with a probe trace, even before the mirror models them.
  Report the build's identity and any witness spans that changed.

### 6.3 What integration found

The streams met their acceptance criteria separately. Integration found the
following [AGENT].

**Scheduling is a captured choice, in both directions.** On this
`CONFIG_PREEMPT_NONE`, single-CPU kernel the section records showed:
- the receive worker yielding to the encrypt worker at `cond_resched`
  (receive.c:216);
- the encrypt worker yielding back, or to the tx worker, at its
  `need_resched()` (send.c:306);
- a tx worker switching to a task that has no section (trace 00017: its
  `cond_resched` line was covered, but no section record showed the switch).

The order is timing-dependent: traces of the same shape were scheduled
differently. So:
- **Kernel:** `__cond_resched` writes a resched record (kind 302) when it is
  about to schedule inside a task's dispatch section.
- **Environment** (`Env.condResched`): it reports `need_resched` from that
  record and runs the crypt workers whose section starts follow. A worker
  that switched away and finishes in the mirror before Linux recorded its
  stop leaves the stop pending. The stop is consumed where Linux recorded it
  (`skipAmbient`), and an operation must end with none pending.
- **The assumption, stated in `Env.runWorker`:** the resumed rests commute.
  On the modeled paths each rest is a final empty queue poll. A hidden read
  out of order is a mismatch.
- **In i7:** 51 resched records (receive 45, encrypt 5, tx 1).

**Other fixes:**
- The steered respond-then-initiate generator could pick a "second" key that
  clamps to the first. Linux then saw `private_key_unchanged` and did not
  initiate.
- `encrypt_packet`'s first return shares the epilogue, so its true span is
  empty.

### 6.4 Independent review (Fable)

The review found no critical defect. Correspondence of the modeled C paths
was confirmed point by point, and the scheduler was found sound against
every interleaving the reviewer constructed.

Fixed (commit `0437dbc`):
1. **Silent section loss at readout (major).** The kernel's `opened` count
   was transported but never checked. `check.py` `section_problems` now
   requires every opened section's start record in the trace. All 522 rows
   of i7 match.
   - The rule conflict: this check has no mutant that it alone rejects. It
     closes a fail-open hole, a lost section that the mirror also does not
     expect. The global rule (fail-open is a defect) and AGENTS.md "checks
     must pay for themselves" are in tension here. It is kept pending the
     user's decision.
2. `condResched`'s loop exhausting with runnable work is an `invariant`.
3. Two domain limits are `unsupported` rather than `invariant`: an unhashed
   handshake entry in `begin_session`, and a payload packet at encryption.
4. Stale notes and the dead `SECTION_RECORDS` switch are removed. The
   strategy doc marks timer sections as deferred.
5. D1-M15's evidence is recorded per run; a pass without resched records is
   "inconclusive".

Checked and found not to be a defect: datagrams to a loopback port with no
socket (port 1234). Linux handles the ICMP reply inside the same NET_RX
section, and the 22 such traces agree.

Open, as follow-ups:
- Nested NET_RX sections are consumed by a lax cut (zero or more pairs), not
  exactly once.
- A theoretical race in `kcov_dispatch_stop`: the move-fits check reads
  without the lock, so a hardirq-raised NET_RX between the check and the
  move could truncate. Unlikely in this VM.
- `harness/test_d1_keys.py` partly duplicates what the keepalive bytes
  decide.
