# 01 — WireGuard discards accepted packets silently when the encrypt ring or the peer's transmit queue is full: no `tx_dropped`, no counter at all, and the ring refuses up to 15 slots the consumer has already taken

Target: Linux 6.12.110, `drivers/net/wireguard/send.c`,
`drivers/net/wireguard/queueing.h`, `include/linux/ptr_ring.h`. Configuration
where it matters: a single CPU (`CONFIG_SMP` off in the oracle,
`kernel/config-x86_64-net-choice`), so the encrypt worker never drains the
ring while a burst is being produced; on SMP the same loss needs the
producer to outrun the worker. State: **Draft**, not filed. Drafted
2026-10-13.

No patch branch (README §5).

## Affected code (pristine 6.12.110)

- `send.c:311-331`, `wg_packet_create_data`: a packet (or list) that
  `wg_xmit` accepted and staged is queued with
  `wg_queue_enqueue_per_device_and_peer` (:320-321). On `-EPIPE` it is
  marked `PACKET_STATE_DEAD` through `wg_queue_enqueue_per_peer_tx`
  (:322-323) and the function returns (:326-327). On any other error
  (`-ENOSPC`) the keypair and peer references are dropped and the list is
  freed with `kfree_skb_list` (:328-330). No statistic is touched on either
  path.
- `queueing.h:157-178`, `wg_queue_enqueue_per_device_and_peer`: first the
  per-peer `prev_queue` (`wg_prev_queue_enqueue`, `queueing.c:72-78`,
  bounded by `MAX_QUEUED_PACKETS`, 1024, `messages.h:53`, whose comment reads
  `/* TODO: replace this with DQL */`), refusing with `-ENOSPC` (:167-168);
  then the device's encrypt ring, `ptr_ring_produce_bh` (:174), whose
  failure is mapped to `-EPIPE` (:175).
- `send.c:262-285`, `wg_packet_tx_worker`: a `DEAD` packet at the head of
  the peer's queue is freed with `kfree_skb_list(first)` (:277-278), its
  keypair and peer put (:280-281), nothing counted. The same arm handles a
  packet the encrypt worker marked `DEAD` because `encrypt_packet` failed
  (`send.c:297-302`).
- `include/linux/ptr_ring.h:104-117`, `__ptr_ring_produce`: the full test
  is physical, `r->queue[r->producer]` non-NULL (:106), and a failed
  produce returns before `r->producer` advances (:107 against :113), so the
  next produce meets the same slot.
- `include/linux/ptr_ring.h:264-289`, `__ptr_ring_discard_one`: a consumed
  slot is zeroed only when `batch` entries have been consumed since the
  last clearing or the ring's end is reached (:272-282); `batch` is
  `SMP_CACHE_BYTES * 2 / sizeof(void *)` (:477), 16 on x86-64. Until then
  the producer sees a consumed slot as occupied.

By contrast, the other losses on the send path are counted:
`wg_packet_purge_staged_packets` adds the purged count to `tx_dropped`
(`send.c:333-340`), and `wg_xmit`'s error labels count `tx_errors` and
`tx_dropped` (`device.c:213`, `:231`).

## Classification

**OBSERVABILITY GAP**, with the drop itself a **DESIGN NUANCE**. The drop
is a documented choice: the queues are fixed-size with no flow control back
to the stack (`messages.h:53` says so in its TODO), and `ptr_ring`'s
deferred clearing is explained in its own comment (`ptr_ring.h:267-271`),
so a burst of more than the ring's free slots losing its tail is the
intended behaviour of a bounded ring, and the effective capacity being
1024 minus up to 15 consumed-but-uncleared slots follows from it. What is
not defensible on the same terms is that the loss leaves no trace in the
device statistics: `wg_xmit` has returned success to the stack for these
packets, every other discard in the driver's send path increments a
counter, and an operator looking at `ip -s link` or `/sys/class/net/<dev>/statistics`
sees zero drops and a transfer count short by the lost packets. The
`kfree_skb_list` call does fire the `skb:kfree_skb` tracepoint with
`SKB_DROP_REASON_NOT_SPECIFIED` (`include/linux/skbuff.h:1314-1317`), so
the drop monitor can see it, without a reason; the device counters cannot.

## Reproducer

In this repository: the `w7-tier` suite, trace
`corpus/w7-tier/w7_ring_wrap.json` (generated by `tier()` in
`scripts/wg-w47-corpus.py`), run with

```
LEANUX_KERNEL_DIR=<the approved oracle> capped -- scripts/in-bundle python3 -m evaluator.check --suite w7-tier
```

The trace brings up a session (the handshake and its staged keepalive take
ring slot 0), sends one data message (slot 1), then sends 1024 data
messages of 64 bytes in one `wg_batch` operation through `io_uring`, so
nothing of the kernel's workers runs between two produces (the records'
sequence numbers show every worker record after the batch call returned;
`docs/2026-10-13-w7-full-ring-tier.md`). Items 1 to 1022 take slots 2 to
1023; item 1023 wraps onto slot 0, still occupied by the consumed but
uncleared keepalive, and takes `-EPIPE`; item 1024 meets the same slot and
fails too. Device counters observed after the batch (the trace's
`wg_observe`):

```
tx_packets 1025  tx_bytes 65652  tx_dropped 0  tx_errors 0
```

65652 is the initiation (148) plus the keepalive (32) plus 1023 data
messages of 64 bytes: of the 1025 data messages the stack handed to the
device, 1023 left it and 2 were discarded with every counter at zero. The
four sibling traces vary the carried residue: `w7_ring_1023` loses 1,
`w7_ring_fresh_1024` loses 1, `w7_ring_1025` loses 2 to `-EPIPE` and then 1
to `-ENOSPC` at the peer queue's 1024, and `w7_ring_batch_clear` (a prior
batch of 15 that lets the consumer clear its first 16 slots) loses 0. The
rule is: drops = items − (1024 − the consumed-but-uncleared slots carried
into the burst).

Without this repository: on a single-CPU machine or VM, bring up a
WireGuard pair, send a small packet, then send 1024 datagrams through the
interface in one burst (`sendmmsg`, or an `io_uring` batch) before the
encrypt worker has run; count the packets at the peer; compare
`ip -s link show wg0` (TX dropped 0) and `wg show wg0 transfer` (short by
the lost packets); `perf trace -e skb:kfree_skb` shows the frees from
`wg_packet_tx_worker` with reason `NOT_SPECIFIED`.

## Expected versus actual

Expected: a packet the device accepted from the stack is either sent or
counted as dropped. Actual: at a full encrypt ring or a full per-peer
queue the packet is freed and no statistic changes; and the ring is "full"
up to 15 entries before its 1024 slots are in use.

## Impact

Operators of busy or bursty senders on few-core hosts, who see loss with no
counter to diagnose it. Not attacker-steerable beyond sending bursts from
a host that is already a legitimate sender; no security consequence
identified. The missing accounting applies equally to the
encryption-failure `DEAD` arm in `wg_packet_tx_worker`.

## How this repository found it

The W7 full-ring tier of the WireGuard mirror
(`docs/2026-10-13-w7-full-ring-tier.md`): the mirror's ring model
predicted one drop at the wrap and the kernel's counters showed two; the

the second. The mirror reproduces the count on all five tier traces. The
