# 02 — WireGuard discards received data packets silently when a peer's receive queue or the decrypt ring is full: no `rx_dropped`, and the free is `consume_skb`, invisible even to the drop monitor; the queue fills before authentication

Target: Linux 6.12.110, `drivers/net/wireguard/receive.c`,
`drivers/net/wireguard/queueing.h`, `drivers/net/wireguard/queueing.c`.
Configuration where it matters: a single CPU (`CONFIG_SMP` off in the
oracle), so the decrypt worker does not drain the queue while a burst is
being received. State: **Draft**, not filed. Drafted 2026-10-13.

No patch branch (README §5).

## Affected code (pristine 6.12.110)

- `receive.c:509-540`, `wg_packet_consume_data`: a data message is looked
  up by the key index in its header (:516-519), its keypair reference taken
  (:520-521), and the packet queued with
  `wg_queue_enqueue_per_device_and_peer` on the peer's `rx_queue` and the
  device's decrypt ring (:526-527). On `-EPIPE` (the ring full) it is marked
  `PACKET_STATE_DEAD` (:528-529) and the function returns (:530-533). On
  `-ENOSPC` (the peer's `rx_queue` at `MAX_QUEUED_PACKETS`, 1024,
  `queueing.c:72-78`, `messages.h:53`) control falls to `err:` (:534-539):
  the keypair and peer references are dropped and the packet freed with
  `dev_kfree_skb(skb)`. No statistic is touched.
- `receive.c:438-489`, `wg_packet_rx_poll`: a `DEAD` packet is skipped to
  `next:` (:458-459) and freed with `dev_kfree_skb` (:480-481), nothing
  counted.
- `include/linux/skbuff.h:1451`: `dev_kfree_skb(a)` is `consume_skb(a)`, so
  these frees fire the `skb:consume_skb` tracepoint, not `skb:kfree_skb`:
  the drop monitor does not see them as drops.
- `queueing.h:157-178` and `include/linux/ptr_ring.h:104-117, 264-289`: the
  same queue, ring and deferred-clearing rules as draft 01.

By contrast, the driver counts the inner-packet errors it finds after
decryption: `wg_packet_consume_data_done` increments `rx_errors` with
`rx_frame_errors` or `rx_length_errors` for a disallowed source, a
non-IP payload or a wrong size (`receive.c:416-433`). The outer-path
discards (a malformed outer packet at `wg_packet_receive`'s `err:`,
:584-585; an invalid nonce, :461-467; a dead packet; a full queue) are all
uncounted. Of these, only the full-queue case discards traffic that was
valid.

## Classification

**OBSERVABILITY GAP**, with a **QUESTION**. The drop follows from the same
bounded queues as draft 01 and is the intended behaviour under overload.
What leaves no trace is worse than on the send side: the device counters
do not move, and because the free is `consume_skb`, neither does the
`kfree_skb` tracepoint, so an operator has no signal at all that valid
packets were lost. The question is about where the limit sits:
`wg_packet_consume_data` admits a packet to the peer's queue on the key
index alone, before any cryptographic check (the AEAD runs in the decrypt
worker, the replay counter in `wg_packet_rx_poll`). A captured valid data
datagram, replayed, therefore occupies queue slots like a genuine one until
the worker rejects it. We assume this is deliberate, since authentication
is the decryption, and the question is only whether the maintainers
consider the resulting loss of legitimate packets during such a burst
worth a counter or a note.

## Reproducer

In this repository: the trace generated by `rx_1025_pending()` in
`scripts/wg-w47-corpus.py` (`w7_ring_rx_1025`): a session, then 1025
keepalive-sized data messages (32 bytes, an empty inner) injected to the
peer in one batch operation, all queued before the decrypt worker runs
(single CPU; the workers run after the batch call returns). The 1025th
finds `rx_queue` at 1024 and takes `-ENOSPC`. Observed on the oracle,
Linux-only: the run completes in 15.6 s, 1024 messages are delivered and the
1025th is discarded, `rx_dropped` and `rx_errors` unchanged. The trace is
not in a differential suite yet: the 1024 inline NAPI polls that follow
exceed the evaluator's bound on ambiguous poll placements (`evaluator/protocol.py`,
64 per trace), so the differential verdict is withheld; the mirror runs the
trace in domain with the `-ENOSPC` arm modelled as the C's puts and free
(`docs/2026-10-13-audit-receive.md`, item F1, fixed on main).

Without this repository: on a single-CPU machine or VM, inject more than
1024 valid data datagrams to a WireGuard peer in one burst (a replay of one
captured datagram suffices to fill the queue; it is rejected later, after
decryption), then send one legitimate packet before the queue drains;
observe it lost while `ip -s link show wg0` shows RX dropped 0 and
`perf trace -e skb:kfree_skb` shows nothing for it.

## Expected versus actual

Expected: a valid data packet the device received is either delivered or
counted as dropped. Actual: at a full per-peer queue or decrypt ring it is
freed through `consume_skb` with no statistic and no drop tracepoint.

## Impact

Receivers under bursts on few-core hosts, who see loss with no counter and
no drop-monitor event to diagnose it. For the question: an off-path sender
holding one captured data datagram can fill a peer's queue with 1024
replays per drain period and cause legitimate packets arriving meanwhile
to be discarded silently; there is no amplification, no state kept beyond
the queue, and the cost is one packet per slot per drain, so this is a
transient loss, not a lockout. No other security consequence identified.

## How this repository found it

The receive correspondence audit of the WireGuard mirror
(`docs/2026-10-13-audit-receive.md`, F1): the mirror had the queue-full
arm as an "unreachable" invariant while its own enqueue returned
`-ENOSPC`; reading the C showed the silent free, and the 1025-message
trace confirmed the kernel's behaviour. The send-side twin is draft 01.
