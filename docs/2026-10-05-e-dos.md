# E: WireGuard DoS protection — cookies and the ratelimiter — design, 2026-10-05

Status: **proposed** [AGENT], **revised 2026-10-05 after an independent audit
and a VM measurement** (sections 4, 16). The first draft claimed `under_load`
is unreachable on one CPU; the audit (C1) showed that misses UDP GSO, and a
probe confirmed `under_load` **is** reachable (results:
`docs/2026-10-05-e-probe-results.md`). E is therefore rescoped to include the
under-load arms. For the user's decisions in section 14.

Line numbers are in the unpatched `.deps/linux` (6.12.110) unless a file is
named as patched. The kernel is `kernel/config-x86_64-net`: one CPU,
`PREEMPT_NONE`, `HZ=250`, no `HIGH_RES_TIMERS`, `TINY_RCU`, `CONFIG_IO_URING=y`
(`config:201`). The oracle is `.artifacts/kernel-net-choice` (the D1/D2 build).

## 1. Target

The DoS-protection paths of `drivers/net/wireguard/{cookie.c,ratelimiter.c}`
and the `under_load` arms of `receive.c`, each checked against Linux:

1. **`under_load`** (`receive.c:112-132`): `handshake_queue_len >=
   MAX_QUEUED_INCOMING_HANDSHAKES / 8` (= 4096/8 = 512, `messages.h:51`), the
   `last_under_load` kernel-global and its 1-second ktime decay.
2. **MAC2/cookie validation under load** (`wg_cookie_validate_packet`,
   `cookie.c:119-154`): `make_cookie`, `compute_mac2`, `wg_ratelimiter_allow`.
3. **Cookie reply creation** (`wg_packet_send_handshake_cookie`,
   `send.c:110-122` → `wg_cookie_message_create`, `cookie.c:180-196` →
   `wg_socket_send_buffer_as_reply_to_skb`, `socket.c:203-233`).
4. **Cookie reply consumption** (`wg_cookie_message_consume`,
   `cookie.c:198-236`) and the MAC2 it unlocks on the next handshake
   (`wg_cookie_add_mac_to_packet`, `cookie.c:156-178`).
5. **The ratelimiter** (`wg_ratelimiter_allow`, `ratelimiter.c:84-156`): the
   per-source-IP token bucket, the table, the GC work item.

The check sees: the cookie reply at the fixture sender's inbox, the MAC2 on
wg0's next initiation, the ratelimiter's allow/deny through the cookie-valid
path, the control flow and operands of each path.

## 2. The kernel mechanism, verified against source

### 2.1 `under_load` (`receive.c:92-132`)

`wg_receive_handshake_packet`, run by the handshake receive worker, computes
(for a non-cookie handshake):

```c
under_load = atomic_read(&wg->handshake_queue_len) >=
                MAX_QUEUED_INCOMING_HANDSHAKES / 8;        /* :112 */
if (under_load)
        last_under_load = ktime_get_coarse_boottime_ns();   /* :115 */
else if (last_under_load)
        under_load = !wg_birthdate_has_expired(last_under_load, 1);  /* :117 */
        if (!under_load) last_under_load = 0;               /* :118-119 */
mac_state = wg_cookie_validate_packet(&wg->cookie_checker, skb, under_load); /* :121 */
```

`last_under_load` is a **function-local `static u64`** (`receive.c:100`),
shared across all devices and persisting across traces within one boot.
`handshake_queue_len` is incremented by the producer at `receive.c:567` (in
`wg_packet_receive`, softirq) and decremented by the worker at `receive.c:215`,
after each packet.

The `packet_needs_cookie` table (`receive.c:123-132`):
- `(under_load && mac==VALID_MAC_WITH_COOKIE) || (!under_load &&
  mac==VALID_MAC_BUT_NO_COOKIE)` → `false` (proceed);
- `under_load && mac==VALID_MAC_BUT_NO_COOKIE` → `true` (send a cookie);
- else drop.

### 2.2 The cookie checker and its secret (`cookie.c`)

- `wg_cookie_checker_init` (`:19-26`), called from `wg_newlink`
  (`device.c:321`): `secret_birthdate = ktime_get_coarse_boottime_ns()`
  (`:23`) and `get_random_bytes(checker->secret, NOISE_HASH_LEN=32)` (`:24`).
- `make_cookie` (`:91-117`): if
  `wg_birthdate_has_expired(secret_birthdate, COOKIE_SECRET_MAX_AGE=120)`
  (`:96`, `messages.h:28`) it rotates the secret (`:99-100`); else
  `cookie = blake2s(key=secret, COOKIE_LEN=16, src_ip ‖ src_port)` (`:106-114`).
- `wg_cookie_validate_packet` (`:119-154`): `compute_mac1` (`:130`, keyed by
  `checker->message_mac1_key`), `crypto_memneq` (`:132`); if `check_cookie`,
  `make_cookie` (`:140`), `compute_mac2` (`:142`), `crypto_memneq` (`:143`),
  then `wg_ratelimiter_allow` (`:147`).

**Whether the secret is captured depends on when `wg0` is created** [M3]. With
the current fixture `wg0` is created at `wg_newlink` **before** the per-op
window, so the secret is not captured and `make_cookie` is not reproducible.
**Workstream L** (`.worktrees/l-life/docs/2026-10-05-l-lifecycle.md`) adds an
in-window `wg_create` op whose `wg_cookie_checker_init` draws are captured as
`.cookieSecret` (cookie.c:24, 32 B) and `.cookieSecretBirthdate` (cookie.c:23),
stored in `Device.cookieSecret`/`cookieSecretBirthdate` — L section 3 states
"E reads it". So **E's cookie-reply creation and the MAC2-validation arm are
built on L's in-window device**, where the secret is known and `make_cookie` is
exact. The 120 s rotation never fires in a 4 s trace (`cookie.c:96-101`).

### 2.3 Cookie reply creation (`cookie.c:180-196`, `send.c:110-122`)

`wg_cookie_message_create` builds a 64-byte `message_handshake_cookie`
(`messages.h:98-103`: header 4 ‖ receiver_index 4 ‖ nonce 24 ‖
encrypted_cookie 32):
- `get_random_bytes_wait(dst->nonce, COOKIE_NONCE_LEN=24)` (`:190`) — a
  `get_random_bytes` draw inside the receive worker (a recording context), so
  **captured by the existing generic hook** (new mirror site `.cookieNonce`,
  consumer `cookie.c:190`);
- `make_cookie` (`:192`) — needs the secret (L, section 2.2);
- `xchacha20poly1305_encrypt(encrypted_cookie, cookie, 16, AAD=macs->mac1, 16,
  nonce, key=checker->cookie_encryption_key)` (`:193-195`).
  `cookie_encryption_key = blake2s("cookie--" ‖ wg0_static_public)`
  (`precompute_key`, `:48-50`) — the mirror computes it.

`wg_socket_send_buffer_as_reply_to_skb` (`socket.c:203-233`) sends to the
initiating skb's source endpoint (the attacker = fixture sender), `ds=0`,
`GFP_ATOMIC` alloc (an `envOk` site).

### 2.4 Cookie reply consumption (`cookie.c:198-236`)

`wg_cookie_message_consume`:
- `wg_index_hashtable_lookup(HANDSHAKE | KEYPAIR, src->receiver_index, &peer)`
  (`:205-208`); miss → return (the arm the mirror models today);
- `!peer->latest_cookie.have_sent_mac1` → `goto out` (`:212`);
- `xchacha20poly1305_decrypt(cookie, encrypted_cookie, 32, AAD=last_mac1_sent,
  16, nonce, cookie_decryption_key)` (`:216-219`).
  `cookie_decryption_key = blake2s("cookie--" ‖ peer_static_public)`
  (`wg_cookie_checker_precompute_peer_keys`, `:61-67`, `peer.c:46`) — the
  mirror computes it from the configured peer key;
- on success (`:222-228`): store `cookie`, `birthdate =
  ktime_get_coarse_boottime_ns()`, `is_valid = true`, `have_sent_mac1 = false`.

**The cookie here is supplied by the remote (the fixture), not made from wg0's
secret.** A fixture that crafts the reply offline gives the mirror the cookie
through the trace — **no secret capture needed for this arm** (so arm 4-consume
needs neither L nor D3).

### 2.5 MAC2 on the next handshake (`cookie.c:156-178`)

`wg_cookie_add_mac_to_packet`, from every outgoing handshake (`send.c:35,95`):
always `compute_mac1` (`:163`), records `last_mac1_sent`, sets `have_sent_mac1`;
then

```c
if (latest_cookie.is_valid &&                                  /* :170 */
    !wg_birthdate_has_expired(latest_cookie.birthdate,
            COOKIE_SECRET_MAX_AGE - COOKIE_SECRET_LATENCY /* 115 */))  /* :171-172 */
        compute_mac2(macs->mac2, message, len, latest_cookie.cookie);  /* :173 */
else
        memset(macs->mac2, 0, COOKIE_LEN);                             /* :176 */
```

**The `&&` short-circuits** [m2]: the birthdate clock read fires **only when
`is_valid`**. So the mirror must gate the `.birthdateExpired` consumption on
`cookieIsValid` with `andM`, or it consumes a record Linux never produced. The
read's consumer frame is the shared inline `timers.h:28` = the existing site
`.birthdateExpired` [m3, to confirm, section 16]. Within 4 s of storing a
cookie, `!expired(birthdate, 115)` is true → a real MAC2 =
`compute_mac2(message, cookie)`; this is the observable that pays for arm 4.

### 2.6 The ratelimiter (`ratelimiter.c`)

- `wg_ratelimiter_init` (`:158-203`), from `wg_newlink` (`device.c:363`):
  `table_size` from RAM (`:173-177`). **On the 256 MiB VM `table_size = 2048`
  and `max_entries = 16384`** [m4 — the first draft's 16/128 was wrong:
  `roundup_pow_of_two((65536<<12)/(1<<14)/8) = roundup(2048) = 2048`,
  `max_entries = 2048*8`]. `queue_delayed_work(…, gc_work, HZ)` (`:191`),
  `get_random_bytes(&key, sizeof(key))` (`:192`, the `hsiphash_key_t`). L
  captures this as `.ratelimiterKey` (16 B) on its in-window device.
- `wg_ratelimiter_allow` (`:84-156`): hashes `(net_word, ip)` to a bucket
  (`:90-105`), walks it comparing `entry->net == net && entry->ip == ip`
  **exactly** (`:112`). On a hit: `tokens = min(TOKEN_MAX, tokens + now -
  last_time_ns)` (`:122-124`, `now = ktime_get_coarse_boottime_ns`, `:121`),
  `ret = tokens >= PACKET_COST`, update. On a miss: `total_entries++ >
  max_entries` → deny (`:135`); else allocate (`GFP_KERNEL`, `:138`),
  `last_time_ns = now`, `tokens = TOKEN_MAX - PACKET_COST`, return true.
  Constants (`:34-39`): `PACKETS_PER_SECOND=20`, `PACKETS_BURSTABLE=5`,
  `PACKET_COST = NSEC_PER_SEC/20`, `TOKEN_MAX = PACKET_COST*5`.
- GC (`:54-82`) is a `DEFERRABLE_WORK` requeued every `HZ`; frees entries idle
  > 1 s. A delayed work item = D3's timer domain.

**The siphash key stays a cut.** Allow/deny is a pure function of the
per-`(net, ip)` token bucket with an exact `(net, ip)` compare, so the bucket
selection is unobservable; the mirror keys its table on `ip` directly. L
captures the key, but the mirror need not use it. The table limit
(`total_entries > max_entries = 16384`, needs 16384 distinct source IPs) and
the GC stay out of scope (section 11).

## 4. Reachability on one CPU — measured [AGENT]

The first draft argued `under_load` is unreachable because the receive worker
(`WQ_CPU_INTENSIVE`, process context) drains at every producer yield. **That is
wrong: it misses UDP GSO** (audit C1), and a VM probe refutes it outright
(`docs/2026-10-05-e-probe-results.md`, `harness/probes/e_underload_probe.c`):

| Mechanism | Datagrams | Cookie replies | under_load |
|---|---|---|---|
| GSO via sendmmsg (8×128 segments) | 8 | 809 | **reached** |
| GSO via send() loop (8×128) | 8 | 794 | **reached** |
| plain sendmmsg (1024) | 1024 | 550 | **reached** |
| io_uring (1024) | 1024 | 462 | **reached** |

Loopback advertises `NETIF_F_GSO_SOFTWARE` (`loopback.c:177-179`), which
includes `NETIF_F_GSO_UDP_L4` (`netdev_features.h:213-214`), so a single
`sendmsg` with `UDP_SEGMENT` carries up to 128 segments (`UDP_MAX_SEGMENTS =
1<<7`, `include/linux/udp.h:111`; enforced `net/ipv4/udp.c:992`) as one
super-skb; wg's encap socket sets only `.encap_rcv = wg_receive`, no
`.gro_receive` (`socket.c:352-356`), so `udp_queue_rcv_skb` →
`udp_rcv_segment` fans them to `wg_receive` one by one **inside one NET_RX
softirq**, where the process-context worker cannot run. Eight such datagrams
(1024 segments) cross 512. Even plain `sendmmsg` crosses: the single-CPU worker
does not fully drain at each `cond_resched`, and under load its per-packet cost
rises (make_cookie + a cookie reply), so the queue stays above 512.

**So `under_load` is a natural single-CPU input, not a steered decision.** The
first draft's §13-q1 dichotomy ("accept unreachable, or steer a program
decision") is void.

**But "reachable" is not "cheap to model exactly"** [m5]. Two distinct facts:

- **The under-load *state* and its *control/data paths* are modeled** (§6.B/6.C):
  the `under_load` branch, `make_cookie`, the cookie reply, the ratelimiter.
- **The raw flood's *exact dynamics* are scheduling-driven and are not
  modeled** (§11): how many packets are processed while `queue_len >= 512`
  (hence the exact number of cookie replies and of `receive.c:115` clock reads)
  depends on the producer/worker interleaving, which varies run to run (the
  probe saw 462–809 replies for the same input). Reproducing that count would
  need the environment to reconstruct `queue_len` per packet from the section
  and resched records — a large build that pays little.

**The decay (`last_under_load`) is both the hazard and the lever.**

- **Hazard (audit M2):** `last_under_load` is a global `static` (`receive.c:100`)
  that teardown does not reset and that decays after 1 s. Today the mirror
  hard-codes the decay branch false (`Receive.lean:106,109`), which silently
  **assumes no trace in the whole boot ever reaches `under_load`**. That
  invariant must be stated. Under-load traces violate it, so they **run in
  their own VM batch**, isolated from normal traces; within that batch they are
  spaced so the 1 s decay has expired (and `last_under_load` reset to 0) before
  the next trace's first handshake, or one under-load trace per boot.
- **Lever:** once a flood crosses 512, `last_under_load = T`, and for the next
  **1 second every handshake is forced `under_load = true` by the decay
  (`receive.c:117`), regardless of the queue depth.** So a trace can
  **(1) flood invalid-MAC1 handshakes to set `last_under_load` (cheap drops, no
  replies, no observable count), then (2) within 1 s inject a small, fixed
  number of valid-MAC1 handshakes (an ordinary `wg_inject`), each of which is
  processed under load (via the decay) and deterministically produces exactly
  one cookie reply.** This gives an **exact, cheap, checkable** cookie-required
  / reply-creation correspondence without modeling the flood's dynamics: the
  flood's only checked effect is that the `under_load=true` branch executed
  (A2 coverage) and `last_under_load` was set; its per-packet clock reads are a
  **declared bounded cut consumer within the receive-worker section** (not
  count-checked), justified because their values reach only `last_under_load`,
  whose single checked effect (the decay window) the post-flood injection
  exercises. The timing — the flood draining within 1 s so the decay is still
  live for the injection — is a measured property (§16, risk).

## 6. The arms

### 6.A Cookie reply consumption + MAC2 (reachable, cheap, L/D3-independent)

Unchanged from the first draft; it is the safe, self-contained core.

**Trace `e_cookie_then_reinitiate`.** A steered handshake (as D1): wg0
initiates (steered ephemeral/index/timestamp); `addMacToPacket` sets
`have_sent_mac1`, `last_mac1_sent`. The fixture injects a **cookie reply**
(type 3, 64 B) naming wg0's index, cookie encrypted offline under
`blake2s("cookie--" ‖ peer_public)`, AAD = wg0's `last_mac1_sent` (computed
offline from the steered initiation), chosen nonce. wg0 consumes it, stores the
cookie, `is_valid`, `have_sent_mac1 = false`. The trace then **changes wg0's
private key** (`wg_set`), whose per-peer `wg_noise_expire_current_peer_keypairs`
(`netlink.c:574` → `noise.c:179-199`) calls `wg_noise_reset_last_sent_handshake`
(`noise.h:99-106`), clearing the rate limit while leaving `latest_cookie` intact
(verified: the key-set path touches handshakes, keypairs and cookie *keys*,
`netlink.c:544-577`, not the stored cookie; it clears the handshake and its
index entry, so the re-initiation uses a fresh handshake/index). wg0 initiates
again; `addMacToPacket` takes the `is_valid && !expired` arm and emits a real
MAC2.

**Observable.** The second initiation at the fixture inbox carries
`macs->mac2 = compute_mac2(message, cookie)`; the mirror computes the same.

**Mirror.** `cookieMessageConsume` (`Receive.lean:80-84`) beyond the miss arm:
the `have_sent_mac1` test; `xchacha20poly1305_decrypt(...)` (`.cookieDecryptFailed`);
on success store `cookie`, `cookieBirthdate ← hiddenClock .cookieBirthdate`,
`cookieIsValid := true`, `haveSentMac1 := false`. `addMacToPacket`
(`Handshake.lean:225-232`): `andM (branch .addMacCookieValid cookieIsValid)
(branch .addMacCookieFresh (!(← birthdateHasExpired cookieBirthdate 115)))`
[m2: `andM` so the clock read is consumed only when valid]; the true arm sets
`mac2 := compute_mac2(body, cookie)`.

**Crypto (new).** `xchacha20poly1305_{encrypt,decrypt}`: HChaCha20(key,
nonce[0:16]) → subkey, then the existing `aeadEncrypt/Decrypt` under the subkey
with nonce `0000 ‖ nonce[16:24]`. **HChaCha20 is the bare ChaCha permutation
(20 rounds) with no feed-forward add** [m1]: factor the 20-round core out of
`chacha20Block` (`NoiseCrypto.lean:31-39`, which adds the initial state back)
and output words 0–3, 12–15. Anchor to Linux and to `noise.py` with `#guard`.

**Controls (audit M1 — E-M4 had no rejecting trace):**
- `e_cookie_double_reply`: a **second** valid cookie reply after a successful
  consume. Linux takes `goto out` at `cookie.c:212` (`have_sent_mac1` is now
  false), reading no further; a mirror that left `have_sent_mac1` true would
  decrypt again (a hidden mismatch / extra record). **This is E-M4's rejecting
  trace.**
- `e_cookie_bad_mac1_aad`: a reply whose AAD ≠ wg0's `last_mac1_sent`: decrypt
  fails, no cookie stored, the next MAC2 is zero.
- `e_cookie_wrong_index` / `e_cookie_no_mac1_sent`: the miss arm and the
  `have_sent_mac1=false` `goto out` arm.

### 6.B `under_load` + cookie-required + reply creation (on L's device)

**Trace `e_underload_cookie` (its own isolated batch, §4 lever).**
1. `wg_create` (L) → in-window device; the cookie secret is captured.
2. Configure wg0 (private key, listen port), up.
3. **`wg_flood`** (new op, §8): K (≈ 1024) invalid-MAC1 handshake initiations
   via GSO, crossing 512 → `last_under_load` set. All dropped (INVALID_MAC);
   no replies. Checked effect: the `under_load=true` branch is covered (A2),
   `last_under_load` set; the flood's clock reads are a bounded cut in the
   receive-worker section.
4. Within 1 s, **`wg_inject`** a small fixed number (e.g. 2) of valid-MAC1
   initiations. Each is `under_load` via the decay → `VALID_MAC_BUT_NO_COOKIE`
   → `packet_needs_cookie` → `wg_packet_send_handshake_cookie` → a cookie reply
   (`make_cookie` under the captured secret, `.cookieNonce`, xchacha encrypt).
5. Observe: exactly that many 64-byte cookie replies at the inbox, bytes
   checked (A1).

**Mirror.** `receiveHandshakePacket` (`Receive.lean:97`) gains the real
under_load computation: `branchCmp .hsUnderLoad (queueLen ≥ 512)`; the
`last_under_load` state and decay (`World.lastUnderLoad : Option Int`, fixture
knowledge); `cookieValidatePacket` under load (make_cookie, compute_mac2,
ratelimiter); the `packet_needs_cookie` table; `cookieMessageCreate`
(make_cookie + `.cookieNonce` + xchacha) and the reply send. `make_cookie` =
`blake2s(key = Device.cookieSecret, 16, src_ip ‖ src_port)` (keyed blake2s
exists). The flood drops are a `handshakeReceiveWorker` loop over K invalid
packets whose per-packet clock reads are skipped as a declared cut.

### 6.C The ratelimiter (on L's device, via a valid cookie)

Reached when a handshake under load carries a **valid MAC2** (`cookie.c:143`
passes → `:147` `wg_ratelimiter_allow`). The generator, knowing the captured
secret, computes `cookie = make_cookie(secret, src_ip, src_port)` and
`mac2 = compute_mac2(packet, cookie)`, crafting a valid-cookie initiation. Under
load (decay lever) → `VALID_MAC_WITH_COOKIE_BUT_RATELIMITED` → `ratelimiter_allow`.

**Mirror.** `Kernel.ratelimiter.table : List (ip × tokens × lastTimeNs)` (L owns
`Kernel.ratelimiter`); `wgRatelimiterAllow`: the exact `ip` lookup, the token
arithmetic as `branchCmp` operands (`now` reads are new clock sites), the miss
→ new entry. The first packet for an `(net,ip)` always allows (new entry,
`tokens = TOKEN_MAX - PACKET_COST`); a burst of `> PACKETS_BURSTABLE` within a
tick exercises the deny. **Observable:** under
`VALID_MAC_WITH_COOKIE_BUT_RATELIMITED` the packet is dropped (no handshake
response); under `VALID_MAC_WITH_COOKIE` it proceeds to
`consume_initiation` → a handshake response. So allow/deny is observable as a
response-or-not. The siphash key is a cut.

## 7. Mirror state

- `Peer` (arm 4-consume): `cookie : List UInt8`, `cookieBirthdate : Int`,
  `cookieIsValid : Bool`, `cookieDecryptionKey : Key` (set at peer add =
  `blake2s("cookie--" ‖ remoteStatic)`). `cookieMac1Key`, `lastMac1Sent`,
  `haveSentMac1` already exist (`Types.lean:241-243`).
- `Device` (arms B/C, **owned by L**): `cookieSecret`, `cookieSecretBirthdate`
  (L captures these); E reads them.
- `Kernel.ratelimiter` (**owned by L**): E adds `table : List (ip × tokens ×
  lastTimeNs)` to it.
- `World.lastUnderLoad : Option Int` — the kernel-global decay state, fixture
  knowledge; its cross-trace life is the isolation invariant (§4).

## 8. Environment and the flood op

- **`wg_flood` (new op, natural harness input).** The guest sends K copies of a
  handshake template to wg0's port via `UDP_SEGMENT` GSO (one or a few
  `sendmsg`s), a real DoS flood — not steering. Wire: opcode + family + the
  148-byte template + K. The environment enqueues K into `handshakeQueue`, then
  the receive worker drains them; the under_load branch and `last_under_load`
  are modeled; the flood's per-packet clock reads are the declared cut. **The
  minimal K that crosses 512 is a measured fixture fact** (§16); the generator
  uses it with margin.
- **The decay lever and isolation** (§4): `Env` carries `lastUnderLoad`; the
  post-flood `wg_inject` reads the decay. Under-load traces are a **separate
  batch** (`harness/linux.py` runs them isolated); the mirror asserts the
  invariant that a normal batch never reaches `under_load` (keeping today's
  constant-false decay valid there).
- **Cookie reply injection** (arm 4-consume) reuses `wg_inject` (op 13)
  unchanged.
- No new timing assumptions beyond the decay window; fixture/scheduling stay in
  `Env.lean`.

## 12. Risks [AGENT]

- **Mirror cost of the flood.** K ≈ 1024 invalid-MAC1 drops per `e_underload`
  trace = 1024 keyed-blake2s MAC1 checks in Lean (cheap each, bounded; no
  make_cookie on the drops). The valid-MAC1 injection is a handful. Keep K at
  the measured minimum (§16). A flag if a trace's mirror run is slow.
- **Decay timing** (§4 lever): the flood must drain within 1 s so the decay is
  still live for the injection. The probe's reply counts suggest the flood
  takes real time; stream K measures the drain time and tunes K / the inter-op
  wait, else the lever is replaced by a valid-MAC1 flood with a coverage-only
  check.
- **Isolation of `last_under_load`** across a batch (§4): a bug here would let
  one trace's flood perturb another. The separate-batch design and the invariant
  assertion are the guard.
- **Dependency on L.** Arms B/C need L's in-window device and captured secret.
  If L slips, ship arm 4-consume (§6.A) alone, which needs nothing from L.

### 16.1 Stream E-A (arm 4-consume, §6.A): what was confirmed on Linux [AGENT, 2026-10-06]
