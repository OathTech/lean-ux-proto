# E: WireGuard DoS protection — cookies and the ratelimiter — design, 2026-10-05

Status: **proposed** [AGENT], for the user's decisions in section 13. The
direction is the user's [USER 2026-10-04]: "complete on one CPU" for
WireGuard. E is the DoS-protection slice: the `under_load` state, MAC2/cookie
validation, cookie reply creation and consumption, and the ratelimiter.

Line numbers are in the unpatched `.deps/linux` (6.12.110) unless a file is
named as patched. The kernel is `kernel/config-x86_64-net`: one CPU,
`PREEMPT_NONE`, `HZ=250`, no `HIGH_RES_TIMERS`, `TINY_RCU`. The current oracle
is `.artifacts/kernel-net-choice` (identity `a63260c1…`, the D1/D2 build).

**The headline finding (section 3): the `under_load` state is not reachable
on this single-CPU fixture.** The handshake receive worker drains the queue at
every yield the producer makes, and the producer (`sendmmsg`) yields per
datagram (`net/socket.c:2738`). So three of the five scoped arms — the
under-load trigger, cookie-reply *creation*, and the ratelimiter — have no
single-CPU execution, and the only reachable, payable arm is cookie-reply
*consumption* plus the MAC2 it unlocks (section 5.A). The design records the
unreachable arms as fail-noisy `unsupported` with a measurement that pays for
that claim, and specifies what they would need should a probe (section 12.K)
contradict the analysis.

## 1. Target

The DoS-protection paths of `drivers/net/wireguard/{cookie.c,ratelimiter.c}`
and the `under_load` arms of `receive.c`, each checked against Linux where
reachable on one CPU, and each fail-noisy `unsupported` where not:

1. **`under_load`** (`receive.c:112-132`): `handshake_queue_len >=
   MAX_QUEUED_INCOMING_HANDSHAKES / 8` (= 4096/8 = 512, `messages.h:51`), the
   `last_under_load` kernel-global and its 1-second ktime decay.
2. **MAC2/cookie validation under load** (`wg_cookie_validate_packet`,
   `cookie.c:119-154`): `make_cookie`, `compute_mac2`, `wg_ratelimiter_allow`.
3. **Cookie reply creation** (`wg_packet_send_handshake_cookie`,
   `send.c:110-122` → `wg_cookie_message_create`, `cookie.c:180-196` →
   `wg_socket_send_buffer_as_reply_to_skb`, `socket.c:203-233`).
4. **Cookie reply consumption** (`wg_cookie_message_consume`,
   `cookie.c:198-236`) and the MAC2 it unlocks on the next handshake
   (`wg_cookie_add_mac_to_packet`'s `have_received_cookie`/birthdate path,
   `cookie.c:156-178`).
5. **The ratelimiter** (`wg_ratelimiter_allow`, `ratelimiter.c:84-156`): the
   per-source-IP token bucket, the table, the GC work item.

The check sees: the cookie reply at the fixture sender's inbox, the MAC2 on
wg0's next initiation, the control flow and operands of each path, and the
`unsupported` outcome where an arm is unreachable.

## 2. The kernel mechanism, verified against source

### 2.1 `under_load` (`receive.c:92-132`)

`wg_receive_handshake_packet`, run by the handshake receive worker, computes
(for a non-cookie handshake):

```c
under_load = atomic_read(&wg->handshake_queue_len) >=
                MAX_QUEUED_INCOMING_HANDSHAKES / 8;        /* :112 */
if (under_load)
        last_under_load = ktime_get_coarse_boottime_ns();   /* :115 */
else if (last_under_load)
        under_load = !wg_birthdate_has_expired(last_under_load, 1);  /* :117 */
        if (!under_load) last_under_load = 0;               /* :118-119 */
mac_state = wg_cookie_validate_packet(&wg->cookie_checker, skb, under_load); /* :121 */
```

`last_under_load` is a **function-local `static u64`** (`receive.c:100`),
shared across all devices and persisting across traces. `handshake_queue_len`
is incremented by the producer at `receive.c:567` (in `wg_packet_receive`,
softirq) and decremented by the worker at `receive.c:215`, after each packet.

The `packet_needs_cookie` table (`receive.c:123-132`):
- `(under_load && mac==VALID_MAC_WITH_COOKIE) || (!under_load &&
  mac==VALID_MAC_BUT_NO_COOKIE)` → `false` (proceed);
- `under_load && mac==VALID_MAC_BUT_NO_COOKIE` → `true` (send a cookie);
- else drop.

So the cookie-required and cookie-reply arms are gated on `under_load`.

### 2.2 The cookie checker and its secret (`cookie.c`)

- `wg_cookie_checker_init` (`:19-26`), called from `wg_newlink`
  (`device.c:321`): `secret_birthdate = ktime_get_coarse_boottime_ns()`
  (`:23`) and `get_random_bytes(checker->secret, NOISE_HASH_LEN=32)` (`:24`).
- `make_cookie` (`:91-117`): if
  `wg_birthdate_has_expired(secret_birthdate, COOKIE_SECRET_MAX_AGE=120)`
  (`:96`, `messages.h:28`) it rotates the secret
  (`ktime_get_coarse_boottime_ns`, `get_random_bytes`, `:99-100`); then
  `cookie = blake2s(key=secret, COOKIE_LEN=16, src_ip ‖ src_port)` (`:106-114`).
- `wg_cookie_validate_packet` (`:119-154`): `compute_mac1` (`:130`, keyed by
  `checker->message_mac1_key`), `crypto_memneq` (`:132`); if `check_cookie`,
  `make_cookie` (`:140`), `compute_mac2` (`:142`), `crypto_memneq` (`:143`),
  then `wg_ratelimiter_allow` (`:147`).

**The secret is drawn once per device, at `wg_newlink`, before the per-op
coverage window** (`guest.c` opens KCOV after `network_fixture`, section 4).
Within a 4 s trace it is never rotated (120 s ≫ 4 s). So the secret is **not
captured** and the mirror cannot compute any `make_cookie` output.

### 2.3 Cookie reply creation (`cookie.c:180-196`, `send.c:110-122`)

`wg_cookie_message_create` builds a 64-byte `message_handshake_cookie`
(`messages.h:98-103`: header 4 ‖ receiver_index 4 ‖ nonce 24 ‖
encrypted_cookie 32):
- `get_random_bytes_wait(dst->nonce, COOKIE_NONCE_LEN=24)` (`:190`) — a
  `get_random_bytes` draw inside the receive worker (a recording context), so
  **captured by the existing generic hook** (new mirror site, consumer
  `cookie.c:190`);
- `make_cookie(cookie, skb, checker)` (`:192`) — needs the secret;
- `xchacha20poly1305_encrypt(encrypted_cookie, cookie, 16, AAD=macs->mac1, 16,
  nonce, key=checker->cookie_encryption_key)` (`:193-195`).
  `cookie_encryption_key = blake2s("cookie--" ‖ wg0_static_public)`
  (`precompute_key`, `:48-50`) — the mirror can compute it.

`wg_socket_send_buffer_as_reply_to_skb` (`socket.c:203-233`) sends to the
initiating skb's source endpoint (the attacker = fixture sender), `ds=0`,
`GFP_ATOMIC` alloc (an `envOk` site).

### 2.4 Cookie reply consumption (`cookie.c:198-236`)

`wg_cookie_message_consume`:
- `wg_index_hashtable_lookup(HANDSHAKE | KEYPAIR, src->receiver_index, &peer)`
  (`:205-208`); miss → return (the arm the mirror models today);
- `!peer->latest_cookie.have_sent_mac1` → `goto out` (`:212`);
- `xchacha20poly1305_decrypt(cookie, src->encrypted_cookie, 32,
  AAD=last_mac1_sent, 16, src->nonce, cookie_decryption_key)` (`:216-219`).
  `cookie_decryption_key = blake2s("cookie--" ‖ peer_static_public)`
  (`wg_cookie_checker_precompute_peer_keys`, `:61-67`, `peer.c:46`) — the
  mirror computes it from the configured peer key;
- on success (`:222-228`): store `cookie`, `birthdate =
  ktime_get_coarse_boottime_ns()`, `is_valid = true`, `have_sent_mac1 =
  false`.

**The cookie here is supplied by the remote (the fixture), not made from wg0's
secret.** So a fixture that crafts the reply offline (as D1 crafts a
handshake response) gives the mirror the cookie through the trace — **no
secret capture needed for this arm.**

### 2.5 MAC2 on the next handshake (`cookie.c:156-178`)

`wg_cookie_add_mac_to_packet`, called from every outgoing handshake
(`send.c:35,95`): always `compute_mac1` (`:163`, keyed by
`latest_cookie.message_mac1_key = blake2s("mac1----" ‖ peer_static_public)`),
records `last_mac1_sent`, sets `have_sent_mac1 = true`; then

```c
if (latest_cookie.is_valid &&
    !wg_birthdate_has_expired(latest_cookie.birthdate,
            COOKIE_SECRET_MAX_AGE - COOKIE_SECRET_LATENCY /* 120-5 = 115 */))
        compute_mac2(macs->mac2, message, len, latest_cookie.cookie);  /* :173 */
else
        memset(macs->mac2, 0, COOKIE_LEN);                             /* :176 */
```

The birthdate read is a coarse-boot-time read through the shared inline
`wg_birthdate_has_expired` (`timers.h:24-28`), **consumer frame `timers.h:28`
= the existing mirror site `.birthdateExpired`** (`Defs.lean:305`): already
captured, a new consumption point for the mirror. Within 4 s of storing the
cookie, `!expired(birthdate, 115)` is true, so wg0's next handshake carries a
real MAC2 = `compute_mac2(message, cookie)`. **This is the observable that
pays for the consume arm.**

### 2.6 The ratelimiter (`ratelimiter.c`)

- `wg_ratelimiter_init` (`:158-203`), from `wg_newlink` (`device.c:363`):
  `table_size` from RAM (`:173-177`; 16 on the 256 MiB VM: `roundup_pow_of_two`
  of `(totalram_pages<<PAGE_SHIFT)/2^14/sizeof(hlist_head)`), `max_entries =
  table_size * 8` (`:177`), `queue_delayed_work(…, gc_work, HZ)` (`:191`),
  `get_random_bytes(&key, sizeof(key))` (`:192`, the `hsiphash_key_t`). A
  global `init_refcnt` (`:16,161`) makes init/uninit idempotent; with one wg0
  at a time it draws the key once per device, **at `wg_newlink`, before the
  window** — not captured.
- `wg_ratelimiter_allow` (`:84-156`): hashes `(net_word, ip)` with the siphash
  key to a bucket (`:90-105`), walks the bucket (`:111`) comparing
  `entry->net == net && entry->ip == ip` **exactly** (`:112`). On a hit:
  `tokens = min(TOKEN_MAX, tokens + now - last_time_ns)` (`:122-124`, `now =
  ktime_get_coarse_boottime_ns`, `:121`), `ret = tokens >= PACKET_COST`
  (`:126`), update. On a miss: `total_entries++ > max_entries` → deny
  (`:135`); else allocate (`GFP_KERNEL`, `:138`), `last_time_ns = now`
  (`:146`), `tokens = TOKEN_MAX - PACKET_COST`, return true (`:147-151`).
  Constants (`:34-39`): `PACKETS_PER_SECOND=20`, `PACKETS_BURSTABLE=5`,
  `PACKET_COST = NSEC_PER_SEC/20`, `TOKEN_MAX = PACKET_COST*5`.
- GC (`wg_ratelimiter_gc_entries`, `:54-82`) is a `DEFERRABLE_WORK` requeued
  every `HZ` (`:81`); it frees entries idle > 1 s. A delayed work item =
  timers (D3's domain).

**The siphash key is a cut.** The allow/deny decision is a pure function of the
per-`(net, ip)` token bucket (`:112,122-127`); the key only selects the hlist
bucket, and the exact `(net, ip)` compare makes bucket collisions
unobservable. So the mirror keys its table on `ip` directly (`net` is the one
netns) and never needs the key — it is drawn before the window and reaches no
observable state (a cut consumer with a justification, choice-stream section
5). Only the GC and the table limit (`total_entries > max_entries`, needs
≥ 128 distinct source IPs) remain, both out of scope (section 11).

## 3. Reachability on one CPU — the central finding [AGENT]

`under_load` needs `handshake_queue_len >= 512` while the worker reads it. The
worker (`wg_packet_handshake_receive_worker`, `receive.c:206-218`) runs on
`handshake_receive_wq` (`WQ_CPU_INTENSIVE | WQ_FREEZABLE`, `device.c:333`), a
**process-context kworker**. The producer path (`wg_packet_receive`,
`receive.c:542-586`) runs in the NET_RX softirq of the injecting `sendto`,
inside the trace process's syscall, and `queue_work_on`s the worker
(`:570`).

On one CPU with `PREEMPT_NONE`, the kworker runs only when the trace process
yields the CPU. **Every primitive that enqueues a handshake yields immediately
after:**
- a single `sendto` is one datagram; its syscall return runs
  `exit_to_user_mode` which reschedules if the tick set `need_resched`,
  letting the freshly-woken `WQ_CPU_INTENSIVE` kworker drain;
- `sendmmsg`, the only syscall that sends many datagrams at once, calls
  **`cond_resched()` after every datagram** (`__sys_sendmmsg`,
  `net/socket.c:2738`), so the kworker drains between each enqueue.

So the queue ping-pongs at a depth of one or two, never 512. Additional
evidence: the trace format caps a trace at `MAX_OPS = 64` operations
(`guest.c:69`), each op one datagram, so even a maximal trace enqueues ≤ 64
handshakes — an order of magnitude short of 512 — and there is today no
sendmmsg/burst op at all.

**Conclusion [AGENT]: `under_load`, and therefore arms (1), (2 reply
creation), and (4 ratelimiter) which are all gated on it (section 2.1), have
no single-CPU execution with the available fixture primitives.** A second,
independent reason to exclude them: `last_under_load` is a cross-device,
cross-trace `static` (`receive.c:100`), which breaks the mirror's per-trace
isolation; modeling it faithfully would require tracking kernel state the
teardown does not reset.

**Decision [AGENT]: keep the `under_load=true` subtree fail-noisy
`unsupported` (as the mirror does today, `Receive.lean:104`), and pay for that
claim with a measurement** (section 12.K): a throwaway guest with a
`sendmmsg` burst op, instrumented to read `handshake_queue_len`, showing it
never reaches 512. This is the cheapest thing that discharges the question and
is consistent with "checks must pay for themselves": we do not build 512-packet
cookie/ratelimiter machinery for a state no trace can enter. Section 5.B/5.C
specify what those arms would need **if** the probe refutes the analysis — a
decision deferred to that evidence.

**[USER] question 1:** accept `under_load` (and cookie-reply creation and the
ratelimiter) as out-of-scope-unreachable on one CPU, documented by the burst
probe, rather than built? The alternative is a fixture/kernel mechanism to
force the queue depth (a steered `handshake_queue_len` comparison, or a held
worker), which does not correspond to any natural single-CPU execution and
would be the first steered *program decision* in the project — something the
choice-stream model forbids (decisions are checked against KCOV, never
supplied; section 3 there).

## 5. The arms

### 5.A Cookie reply consumption + MAC2 (reachable — the deliverable)

**Trace (D3-independent variant, `e_cookie_then_reinitiate`).** A steered
handshake (as D1): wg0 initiates with a steered ephemeral, index and
timestamp; `addMacToPacket` sets `have_sent_mac1`, `last_mac1_sent`. The
fixture, instead of a handshake response, injects a **cookie reply** (type 3,
64 B) naming wg0's steered sender index, with a chosen cookie encrypted offline
under `blake2s("cookie--" ‖ peer_public)`, AAD = wg0's `last_mac1_sent`
(computed offline from the steered initiation, as D1 computes the response),
and a chosen nonce. wg0 consumes it (`cookie_message_consume`), stores the
cookie, sets `is_valid`, `have_sent_mac1 = false`. The trace then **changes
wg0's private key** (`wg_set`), whose per-peer
`wg_noise_expire_current_peer_keypairs` (`netlink.c:574` → `noise.c:179-199`)
calls `wg_noise_reset_last_sent_handshake` (`noise.h:99-106`), clearing the
`REKEY_TIMEOUT` rate limit — the same reset `d1_respond_then_initiate` already
uses — while leaving `latest_cookie` intact (the key-set path touches
handshakes, keypairs and cookie *keys* at `netlink.c:544-577`, not the stored
cookie). It also clears the handshake and its index entry, so the re-initiation
creates a fresh handshake under a new index; the stored cookie is unaffected. wg0 then initiates again; `addMacToPacket` now takes the
`is_valid && !expired` arm (`cookie.c:170-174`) and emits a real MAC2.

**Observable.** The second initiation at the fixture sender's inbox carries a
nonzero `macs->mac2 = compute_mac2(message, cookie)`; the mirror computes the
same bytes from the cookie it consumed. The dump/counters are unchanged.

**Mirror.** `cookieMessageConsume` (`Receive.lean:80-84`) is extended beyond
the miss arm:
- the `have_sent_mac1` test (`cookie.c:212`);
- `xchacha20poly1305_decrypt(encrypted_cookie, AAD = lastMac1Sent, nonce,
  key = blake2s("cookie--" ‖ peer.remoteStatic))` → a new `branch`
  (`.cookieDecryptFailed`); on failure the dbg arm (no state change);
- on success: store `cookie`, `cookieBirthdate ← hiddenClock .cookieBirthdate`
  (`cookie.c:225`), `cookieIsValid := true`, `haveSentMac1 := false`.

`addMacToPacket` (`Handshake.lean:225-232`) replaces its two constant-false
branches with the real path: `addMacCookieValid = peer.cookieIsValid`;
`addMacCookieFresh = !(← birthdateHasExpired peer.cookieBirthdate 115)` (a
`branchCmp` on the existing `.birthdateExpired` site); the true arm sets
`mac2 := compute_mac2(body, cookie)`; the false arm keeps the 16 zero bytes.

**Crypto (new).** `xchacha20poly1305_decrypt`: HChaCha20 over `key` and
`nonce[0:16]` to a subkey (reuses `chacha20Block`'s core), then the existing
`aeadDecrypt` under the subkey with nonce `00000000 ‖ nonce[16:24]`. Anchor it
to the kernel (an offline vector) and to `noise.py`'s builder with `#guard`.

### 5.B Cookie-required + reply creation (gated on 3; design only)

Reached only if `under_load` is reachable (section 3 says it is not). If a
probe refutes that:
- the mirror models `receive.c:112-132` in C order: the `handshake_queue_len`
  read as a `branchCmp`, `last_under_load` as fixture-knowledge state
  (`World`, since it is a kernel-global — its cross-trace life must then be
  modeled or the corpus confined to one under-load trace per batch), the decay
  clock reads as new mirror sites, and the `packet_needs_cookie` table;
- `make_cookie` needs the **secret**: a new kernel capture at
  `wg_cookie_checker_init` (`cookie.c:24`) recording the 32-byte secret in the
  first in-window operation, or steering it to a fixed value (the draw is
  outside any recording context, so steering needs the window opened over
  `wg_newlink` first — a fixture change). The mirror then computes
  `cookie = blake2s(key = secret, 16, src_ip ‖ src_port)` (keyed blake2s
  exists) and the reply via `xchacha20poly1305_encrypt` under
  `blake2s("cookie--" ‖ wg0_public)`, with the captured `.cookieNonce`.

This is a large, speculative build for a state with no execution; **not
recommended** without the probe (12.K) first showing 512 is reachable.

### 5.C The ratelimiter (gated on 3; design only)

Reached only under load (`cookie.c:147`). If pursued: a mirror token bucket
keyed on `ip` (`Device.ratelimiter : List (ip × tokens × lastTimeNs)`), the
`now` reads as new clock sites, `tokens`/`PACKET_COST` arithmetic as `branchCmp`
operands. The siphash key stays a cut (section 2.6). The table limit and GC are
out of scope (section 11). Again **not recommended** without the probe.

## 6. Mirror state

Arm 5.A adds to `Peer` (`Types.lean`):

```lean
  cookie            : List UInt8 := List.replicate 16 0  -- latest_cookie.cookie
  cookieBirthdate   : Int := 0                           -- latest_cookie.birthdate
  cookieIsValid     : Bool := false                      -- latest_cookie.is_valid
  cookieDecryptionKey : Key := List.replicate 32 0       -- precomputed at peer add
```

`cookieMac1Key`, `lastMac1Sent`, `haveSentMac1` already exist
(`Types.lean:241-243`). `cookieDecryptionKey` is set at peer creation
(`wg_cookie_checker_precompute_peer_keys`, `peer.c:46`) =
`blake2s("cookie--" ‖ remoteStatic)`, alongside the existing `cookieMac1Key =
blake2s("mac1----" ‖ remoteStatic)`. Keeping the same shape as
`struct cookie` (`cookie.h:246-255`). The secret and the ratelimiter table are
**not** added (unreachable; the siphash key is a cut) — the mirror holds only
the C data its reachable paths read.

## 7. Environment rules

- **Cookie reply injection** reuses `Env.inject` (op 13) unchanged: a type-3
  message to wg0's port runs `wgReceive` → the receive worker →
  `cookieMessageConsume`. No new environment code for arm 5.A.
- **The second initiation** after the key change flows through the existing
  send worker and `deliverSent`; its MAC2 bytes reach the fixture inbox via
  the existing loopback delivery.
- **No new timing assumptions.** The cookie birthdate and MAC2 freshness use
  the recorded coarse-boot-time values; `Env.timing` is untouched. Fixture and
  scheduling assumptions stay in `Env.lean`, per AGENTS.md.
- The `under_load` branch stays `unsupported` in `Env`/`Receive`, a fail-noisy
  outcome, not an omission.

## 8. Generator and corpus

- **`harness/noise.py`:** a `cookie_message(receiver_index, cookie, nonce,
  mac1, peer_public)` builder — `xchacha20poly1305_encrypt(cookie, AAD=mac1,
  nonce, blake2s("cookie--" ‖ peer_public))` — anchored to the mirror's
  `#guard` vectors and to Linux.
- **Generator** (`generate.py`, the `steered_handshake` class at `:474`): a
  `e_cookie` variant — initiate (steered), inject a crafted cookie reply, a
  `wg_set` private-key change, initiate again; `expect` the second
  initiation's MAC2 nonzero. The index and ephemeral are already steerable.
- **Corpus** (`corpus/wireguard/e_*.json`, frozen, one per class):
  - `e_cookie_then_reinitiate` — the 5.A deliverable;
  - `e_cookie_bad_mac1_aad` — a reply whose AAD ≠ wg0's `last_mac1_sent`:
    `xchacha` decrypt fails, no cookie stored, the next initiation has a zero
    MAC2 (a control, rejecting a mirror that stores on failure);
  - `e_cookie_wrong_index` — a reply naming an unknown index: the existing
    miss arm (regression);
  - `e_cookie_no_mac1_sent` — a cookie reply before wg0 ever sent a handshake
    (`have_sent_mac1 = false`): the `goto out` arm (`cookie.c:212`).

## 9. Evidence: what pays for itself

**Mutants (mirror, rejected only on E traces):**
- E-M1: `cookieMessageConsume` stores the cookie on a failed decrypt —
  rejected by `e_cookie_bad_mac1_aad` (the next MAC2 differs: bytes).
- E-M2: `addMacToPacket` ignores `cookieIsValid` (always zero MAC2) — rejected
  by `e_cookie_then_reinitiate` (bytes).
- E-M3: MAC2 keyed by the mac1 key instead of the cookie — rejected by bytes.
- E-M4: `have_sent_mac1` not cleared after consume (`cookie.c:227`) — a second
  cookie reply would be consumed where Linux's `goto out` drops it; rejected
  by a follow-up inject (control flow / a hidden mismatch, since Linux takes
  the `have_sent_mac1` branch and reads no further).
- E-M5: freshness compared against `COOKIE_SECRET_MAX_AGE` (120) not
  `MAX_AGE - LATENCY` (115) — equivalent within a 4 s trace (both fresh); **not
  claimed** (honest: unreachable without D3 time advance, where a 115-118 s
  advance would separate them — a D3-dependent future control).

**The unreachability claim (section 3) is paid for by the burst probe
(12.K):** a measurement showing `handshake_queue_len` never reaches 512, which
is the evidence that the `unsupported` `under_load` subtree is a real
single-CPU gap and not an untested omission. This is a negative control, in the
spirit of the choice-stream step-0 enumeration.

**Not claimed:** no mutant for the ratelimiter or reply creation — those arms
are unreachable, so a mutant in them is untestable against Linux; they stay
`unsupported` (fail-noisy), which `wg-mutants.py` already treats as rejected if
a mutant flips a reachable decision into them.

## 10. Why E is small, honestly

The task scoped five arms; the single-CPU constraint collapses them to one.
That is the correct outcome under "checks must pay for themselves": the cookie
*consume* path is a genuine, reachable gap (today `unsupported`,
`Receive.lean:84`), and E closes it with one new crypto primitive, four `Peer`
fields and a handful of branches. The other four arms are either unreachable on
one CPU (`under_load` and everything it gates) or a cut (the siphash key).
Building them would add mirror code and checks for states no trace can enter —
the accretion AGENTS.md warns against. The design states them fully so the
record is complete and so a future multi-CPU stage can lift them.

| `wg_ratelimiter_allow` and the token bucket | gated on `under_load` (`cookie.c:147`) |

| cookie-secret rotation (`cookie.c:98-101`) | 120 s ≫ 4 s |

## 12. Execution plan

Worktrees and branches as in D1/D2/D3; one signoff at the end (no kernel change
for the reachable arm). Arm 5.A has **no kernel-oracle change** — it reuses the
captured `.birthdateExpired` site, the generic coarse-boot-time hook, and the
steering mechanism already in the oracle.

**Stream K — the measurement (first, gating).** A throwaway `net-probe`-style
guest op that `sendmmsg`s N copies of a well-formed garbage handshake, with a
read of `handshake_queue_len` (via a tiny debug hook or `/proc`), run on
`.artifacts/kernel-net-choice`. Deliverable: the maximum queue depth observed,
settling [USER] question 1. Budget: one short VM run; uses a private probe
trace and the shared slot briefly. If it reaches 512, re-open sections 5.B/5.C
with the user before building.

**Interface commit** (on `task/e-dos`): `Peer.cookie`, `cookieBirthdate`,
`cookieIsValid`, `cookieDecryptionKey`; `HiddenSite.cookieBirthdate` (clock,
`cookie.c:225`, 8 B) and (if 5.B is ever reached) `.cookieNonce`; the
`xchacha20poly1305_decrypt` primitive and its `#guard` vectors; the
`cookie_message` builder in `noise.py`; the `e_cookie` generator variant and
wire plumbing (none new — op 13 suffices).

**Stream M — mirror and crypto:** section 5.A; `cookieMessageConsume` and
`addMacToPacket` extensions; D1/D2/D3 suites green.

**Stream H — harness, generator, corpus, mutants:** sections 8, 9.

**Integration:** the full check, the E mutants and controls, the steering
controls, on the current oracle; the report and the signoff.

**Dependencies on other workstreams:**
- **D3 (timers):** optional. Arm 5.A is D3-independent via the private-key
  reset. D3's retransmit timer offers a second, more natural path to the
  MAC2-carrying handshake (`wg_expired_retransmit_handshake` →
  `send_queued_handshake_initiation(is_retry)` → `addMacToPacket`), and D3's
  time advance is the only way to reach the MAC2 freshness expiry (E-M5) and
  the secret/cookie age comparisons (`cookie.c:96,171`) — stated in D3 section
  6 as "out of scope with the cookie stage". E's mirror timer representation
  must match D3's (`Peer.timer* : Option Nat`); build E on the D3 base if D3
  lands first, else keep the cookie fields additive and merge-compatible.
- **L (lifecycle, `Device.lean`):** E reads `cookieDecryptionKey`/`cookieMac1Key`
  set at peer add and the private-key-change reset path (`netlink.c:544-577`);
  if L reworks peer creation or `wg_set`, coordinate the precompute call sites.
  No conflict expected.
- **A (allocation outcomes):** the cookie reply's `alloc_skb` (`socket.c:217`,
  `GFP_ATOMIC`) is an `envOk` site like the others; if A lands the fault-hook
  capture, the reply-creation arm (if ever reached) would consume it. No
  dependency for 5.A.
- **P (pipes):** none; E is WireGuard-local. E adds no generic instrument, so
  it is neutral for P's zero-new-hooks scale test.

## 13. Decisions for the user

1. **[USER] question 1 (section 3):** accept `under_load`, cookie-reply
   creation and the ratelimiter as out-of-scope-unreachable on one CPU,
   evidenced by the stream-K burst probe — rather than forcing the queue depth
   by a mechanism with no natural single-CPU execution?
2. **The E scope (section 5.A):** cookie reply consumption + MAC2 as the
   reachable deliverable, with the private-key-reset trace, no kernel change.
3. **The crypto addition:** `xchacha20poly1305_decrypt` in the mirror, anchored
   to Linux and to `noise.py`.
4. **Sequencing with D3:** build E on the D3 base if D3 merges first (shared
   `Peer.timer*` shape), else additive and merged later. Confirm the
   preference.

## 14. Uncertain kernel claims to re-verify in stream K/M

- **The `under_load` unreachability (section 3)** rests on the scheduler
  letting the `WQ_CPU_INTENSIVE` kworker drain at every producer yield. The
  `cond_resched` at `net/socket.c:2738` and the one-datagram `sendto` are
  verified; the *scheduling outcome* (the kworker actually running at those
  points on this TCG VM) is a dynamic claim the probe must confirm. This is the
  one load-bearing claim that a measurement, not source reading, settles.
- The private-key-change path that resets the rate limit while preserving
  `latest_cookie` (`netlink.c:544-577`): verified it does not touch
  `latest_cookie.cookie`/`is_valid`, but the exact reset of
  `last_sent_handshake` goes through `wg_noise_expire_current_peer_keypairs`
  /`wg_noise_set_static_identity_private_key`; the D1 `d1_respond_then_initiate`
  trace already relies on this reset, so it is corroborated, but re-confirm the
  cookie survives the key change on Linux with the `e_cookie_then_reinitiate`
  trace before trusting the MAC2 observable.
- The `.birthdateExpired` consumer frame (`timers.h:28`) also serving
  `cookie.c:171`'s freshness read: the shared-inline-consumer rule
  (choice-stream 4.2) predicts it, but confirm the resolved records of
  `e_cookie_then_reinitiate` on the oracle attribute that read to `timers.h:28`
  (not `cookie.c:171`) before relying on the existing site.
