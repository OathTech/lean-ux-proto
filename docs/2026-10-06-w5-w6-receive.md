## 1. Target and the governing rule

The stack between `napi_gro_receive` and the sender's socket is a cut: it
is not WireGuard, and the mirror holds only WireGuard's data and control
flow. D2 made the cut **fail-closed by an exact predicate** (the environment
delivers exactly the datagrams Linux delivers, and says `unsupported` for
everything else). W5 and W6 widen that predicate without changing its
nature: every inner packet the generator produces gets a **named outcome**
in the environment — delivered (with its bytes and TOS), dropped (with the
Linux arm that drops it), answered (with the reply's exact bytes), or
`unsupported` (with the reason) — and every outcome is observed, or the
shape is not added.

What the mirror gains is only what WireGuard's own code does with these
packets: the ECN rewrite arms of `INET_ECN_decapsulate` (inlined into
`wg_packet_rx_poll`), the `ds` it computes on transmit, the scope id of an
endpoint, the device counter, and `wg_xmit` entered from softirq context
with a packet the stack built.

**The boundary (v3) [USER 2026-10-07].** "Stop at the boundary of
WireGuard (unless this breaks important things)": a stack behaviour is
modeled iff (a) it is WireGuard code — including the stack helpers inlined
into WireGuard functions, whose arms are WireGuard's control flow — or (b)
its outcome is needed to predict a WireGuard observable (the sender's inbox
for a kept trace, the dump, the device counters, the ciphertext of a reply
that re-enters `wg_xmit`). Everything else is an explicit `unsupported`
whose reason names the Linux row of section 2 — never a silent pass, never
a comparison-side mask. The exact predicate of D2 keeps its nature: the
environment delivers exactly what it models and refuses the rest. "Breaks
important things" was checked per class (section 14): no kept trace
produces an inner packet that an excluded row decides, so nothing kept
becomes unpredictable.

### 2.1 The outer DS field and ECN decapsulation (W5)

- `wg_packet_receive` stores the outer DS field before queueing a data
  message: `PACKET_CB(skb)->ds = ip_tunnel_get_dsfield(ip_hdr(skb), skb)`
  (receive.c:575; ip_tunnels.h:555-566: the IPv4 `tos`, or the IPv6
  traffic class). Today the fixture's outer TOS is 0 (`Env.senderSource`,
  `tos := 0`), so every ECN arm has a constant outcome.
- `wg_packet_consume_data_done` calls `INET_ECN_decapsulate(skb, ds,
  inner)` for IPv4 (receive.c:389, inner = `ip_hdr(skb)->tos`) and IPv6
  (:393, `ipv6_get_dsfield`) and **ignores the return value**: a "drop"
  verdict (rc 2) still delivers. The arms (inet_ecn.h:251-284, the RFC 6040
  table at :234-243):
  - inner not-ECT: outer not-ECT → nothing; outer ECT(0)/ECT(1)/CE →
    rc 1/2, **no rewrite**;
  - inner ECT or CE, outer CE → `INET_ECN_set_ce` (:172-189): IPv4
    `IP_ECN_set_ce` (:77-103): `ecn = (tos + 1) & 3`; ECT(1) → `check +=
    htons(0xFFFD)`, ECT(0) → `check += htons(0xFFFE)` (ones'-complement
    16-bit adds), then `tos |= CE`; CE stays; IPv6 `IP6_ECN_set_ce`
    (:134-148): the first 32-bit word `|= htonl(CE << 20)`;
  - inner ECT or CE, outer ECT(1) → `INET_ECN_set_ect1` (:208-225): IPv4
    `IP_ECN_set_ect1` (:105-113): only ECT(0) changes, `check += htons(1)`,
    `tos ^= 3`; IPv6 `IP6_ECN_set_ect1` (:150-164): only ECT(0), the word
    `^= htonl(3 << 20)`;
  - all other combinations: nothing.
  The IPv4 checksum adjustments keep a correct header checksum correct and
  a wrong one wrong, so the input predicate (2.2) is evaluated on the
  rewritten bytes.
- **The sender's TOS is one knob for both directions.** `IP_TOS` on the
  dual-stack sender sets `inet->tos` with the ECN bits kept for a datagram
  socket (`__ip_sock_set_tos`, ip_sockglue.c:586-599; the `SOL_IP` level on
  an IPv6 socket goes to `udp_prot.setsockopt`, ipv6_sockglue.c:987) and
  `IPV6_TCLASS` sets `np->tclass` (ipv6_sockglue.c:734-751, ECN kept for
  datagrams). `__ip_make_skb` writes `iph->tos = inet->tos` (ip_output.c:
  1460). So a per-op TOS on the sender gives (a) the outer DS of an
  injected message and (b) the inner TOS of a transmitted packet, whose
  `ds = ip_tunnel_ecn_encap(0, ip_hdr(skb), skb)` (send.c:378;
  `INET_ECN_encapsulate`, inet_ecn.h:46-52: the inner ECN bits, CE → ECT(0))
  becomes the outer TOS/traffic class of wg0's datagram
  (`udp_tunnel_xmit_skb(..., ds, ...)` socket.c:85; `udp_tunnel6_xmit_skb`
  :152). D2 dropped the `ds` mutant because the TOS was 0 and the outer DS
  unobserved; W5 restores it.
- **Observation.** `IP_RECVTOS` yields an `IP_TOS` cmsg of
  `ip_hdr(skb)->tos` (ip_sockglue.c:69-74, :194-197); `IPV6_RECVTCLASS`
  yields `ipv6_get_dsfield(ipv6_hdr(skb))` (datagram.c:644-646). The
  dual-stack sender's `udpv6_recvmsg` delivers either, by the packet's
  family (ipv6/udp.c:484-490). The guest's `recvfrom` becomes `recvmsg`
  on all sockets; every observed datagram gains its TOS.

### 2.4 Reactions (W6)

Every reply below leaves through wg0 (the fixture's default route per
family), so it enters `wg_xmit` **from softirq context, inside the NAPI
poll's NET_RX section** (`napi_complete_done` → `gro_normal_list` → the
IP receive path → the reply's `ip_local_out` → `dev_queue_xmit`). From
there it is D2's path: `wg_packet_send_staged_packets`, the encrypt worker
(a `process_one_work` section after the softirq, or inside the decrypt
worker's `cond_resched` in order (a)), the tx worker, loopback to the
peer's endpoint — the sender, after roaming — whose inbox holds a
`message_data`. The reply's `wg_timers_data_sent` arm is a kind-303 record
inside the NET_RX section, as D3 expects for any recorded context.

**v3:** of the reactions below only the **IPv4 TCP RST** (2.4.1) is kept:
it is the smallest reply (40 bytes, no rate limit, no hidden input, no
sysctl) that enters `wg_xmit` from softirq with `CHECKSUM_NONE`, and that
entry and that checksum-help outcome are the only WireGuard-side facts any
reply reaches (section 14). The IPv6 RST (2.4.1), ICMPv4 (2.4.2), ICMPv6
(2.4.3), reassembly and expiry (2.4.5), options and extension headers
(2.4.6) are **excluded: beyond the WireGuard boundary** — an inner packet
of those classes is an explicit `unsupported`, and a trace containing one
never passes.

#### 2.4.1 TCP RST

A segment to any port of wg0's address finds no socket (the fixture has
none). IPv4: `tcp_v4_rcv` requires `doff ≥ 5` and a pullable header
(tcp_ipv4.c:2209-2231; `skb_checksum_init` is satisfied by
`CHECKSUM_UNNECESSARY`), then `no_tcp_socket` (:2371-2386; the checksum
completion is skipped) → `tcp_v4_send_reset(NULL, skb, …)` (:737-920):
- no reply to a segment with RST (:760-761); the route must be local
  (:766-767);
- `dest/source` swapped, `doff 5`, `rst 1`; with ACK: `seq = ack_seq`;
  without: `ack 1`, `ack_seq = seq + syn + fin + payload length`
  (:770-782); no MD5/AO/MPTCP options in this config;
- `arg.tos = ip_hdr(skb)->tos` (:889); `ip_send_unicast_reply`
  (ip_output.c:1603-1677): the inner IP options are echoed (:1618-1630;
  W6 keeps TCP segments without options), `inet_sk(sk)->tos = tos &
  ~INET_ECN_MASK` (:1649), the TCP checksum is folded in software and
  **`ip_summed = CHECKSUM_NONE`** (:1664-1668);
- the per-CPU control socket has `IP_PMTUDISC_DO` ("Please enforce IP_DF

#### 2.4.4 Rate limits: three mechanisms

**v3:** no kept reply is rate-limited (`tcp_v4_send_reset` has no limit),
so no kept trace depends on this subsection. The sysctls it motivated are
nevertheless **approved and set** [USER 2026-10-07] (D2), asserted in the
provenance row: they pin the fixture for any reinstated reply class. One
side effect to watch in the first run on the new fixture: `wg_xmit`'s own
error path (`icmp_ndo_send`, the existing `.icmpCredit` cut,
`Device.lean:78`) is no longer limited per destination, so repeated errors
to one destination all send; the existing model is record-driven and
takes either outcome, fail-noisy. The `drawBelow` rule below stays
documented for that cut and for a reinstatement; it is not built by R.

1. **Per-destination token bucket** (`inet_peer_xrlim_allow`,
   inetpeer.c:284-304): `tokens += jiffies − rate_last`, cap
   `6 · timeout`, allow iff `≥ timeout`; a new peer starts with
   `rate_last = jiffies − 60·HZ` (:240-245), i.e. full. IPv4 `timeout =
   sysctl_icmp_ratelimit = HZ` (icmp.c:1545); IPv6 `tmo = icmpv6_time = HZ`
   (af_inet6.c:958) **shifted by the route's prefix length**: the default
   route has `plen 0`, so `tmo >>= 4` = 15 ticks (ipv6/icmp.c:224-225).
   The peer (keyed by the inner source, the reply's destination) is netns
   state: it persists across the traces of a batch, and across the **two
   runs** (PC and comparison mode) of every trace. Its `jiffies` reads are
   not captured; only "certainly allowed" is decidable from the records.
2. **Global credit** (`icmp_global_allow`, icmp.c:233-263): allowed while
   `credit > 0`; a refill (to at most 50, 4 per tick) is attempted only
   when the credit is exhausted and at least `HZ/50` = 5 ticks have passed
   since the last refill stamp (:245-254). `icmp_global_consume` (:266-273)
   draws `get_random_u32_below(3)` — the existing `.icmpCredit` site
   (:268) — once per allowed reply (:334-337, ipv6/icmp.c:233-236).
   `icmpv4_mask_allow` (:276-290) exempts types outside the ratemask
   `0x1818` (:1546); all four reply types here are inside it.
3. **The `ip_error` bucket** (route.c:1021-1034), the same `rate_tokens`
   field, cost `HZ`, burst `5·HZ`: unreachable here (2.4.7).

**Rule [AGENT].** The fixture sets `net.ipv4.icmp_ratelimit = 0` and
`net.ipv6.icmp.ratelimit = 0` once per batch. With `timeout 0`, (1) is
`token = 0; token >= 0` → always allowed (inetpeer.c:296-301), and the
jiffies it reads no longer matter. (2) is always true in the domain: a
false needs 25 or more consumes within 5 ticks of a refill, while the
fixture waits ≥ 100 ticks after every `wg_inject` and no modeled operation
emits more than two errors; the environment asserts that bound
(`unsupported` beyond it) and consumes the `.icmpCredit` records of **one
`get_random_u32_below(3)`** per reply it sends — a tightening of today's
`skipCut`. That is not exactly one record (v2: M4): the constant ceiling
takes the inline u8 path (random.h:77-80), which draws `get_random_u8`
(kind 101, the site's 1 byte) until `(3·r) mod 256 ≥ 256 mod 3 = 1`, i.e.
it redraws while the byte is 0 (probability 1/256 per draw), and the
credits are `(3·r) >> 8`. The rule is the one `jitterBelowRekeyTimeout`
already applies with ceiling 83 (`Handshake.lean:343-348`), generalized
over the ceiling: `drawBelow site ceil`; `.icmpCredit` uses ceiling 3.
Without the
sysctls the per-source bucket is still decidable with a fresh inner source
per trace and an interval rule (tokens ≥ `1500 − 250·k + 100·(k−1)` after
`k` replies one inject apart, so 7 replies certainly allowed), **but** the
comparison run of the same trace reuses the same source with a depleted
bucket, which the environment cannot see. The sysctl is the clean cut; the
rate-limited arms (`ICMP_MIB_RATELIMITHOST`, a refill) are out of scope
either way (section 9).

#### 2.4.7 `ip_error` host unreachable — deferred, and why

The ICMP arm of `ip_error` (route.c:1003-1038) is reachable only with
`forwarding` on: with it off, every non-local inner destination is dropped
silently (:988-1001; W5 models that drop, 2.2 row 13). Turning forwarding
on changes the behaviour of **every** non-local inner destination — the
default route via wg0 forwards them back out through wg0 (`ip_forward`,
TTL decrement, the hop-limit-exceeded ICMP) — and reaching `ip_error`'s
ICMP then also needs an `unreachable`/`prohibit` route in the fixture.
That is a router-mode fixture with its own shapes, not a receive shape;
it belongs to a later workstream ("wg0 as a router"). The inetpeer bucket
is not the obstacle: it is the same field as 2.4.4's and decidable by the
same means.

### 3.3 One new capture: the IPv4 identifier (kernel change, user decision)

**v3: D1 deferred [USER 2026-10-07]; nothing below is built.** The
ICMPv4 class is excluded independently of the capture (2.4.2). The
analysis stays for W4+W7's K1 and for a reinstatement.

`__ip_select_ident` (route.c:489-507) returns `ip_idents[bucket] + delta`:
the delta is recorded, the counter is `get_random_bytes` at boot. The id
is in the ICMPv4 reply's plaintext, under the AEAD, so the ciphertext in
the sender's inbox is not computable without it. Proposal: a generic
record at the source, `kcov_choice_ip(K_IDENT, _RET_IP_, &id, 2)` after
the id is chosen in `__ip_select_ident` (`K_IDENT` a placeholder: the
coordinator allocates the kind; v1 wrote 120), kind class `ident` in
`check.py`. It is a hidden input recorded where it arises, like the random
draws and clocks. Masking the field in the comparison was considered and
rejected: it would hide the id and the header checksum behind a
decrypt-and-compare step in the evaluator — a comparison-side mask,
fail-open on two fields. Until the capture exists, the ICMPv4 class is
`unsupported` with that reason; ICMPv6 and both RSTs need nothing (the
IPv6 flow label is pinned by the sysctl of 2.4.1, the RST id is 0).

**The capture has two consumers, so K declares two sites (v2: M2).**
`_RET_IP_` inside `__ip_select_ident` is the caller's frame, and there are
two callers on the modeled paths:
- `.ipIdent` — `ip_select_ident_segs` (ip.h:583-587) inlined into
  `__ip_make_skb` (ip_output.c:1465): the ICMPv4 reply (non-DF; `icmp_push_reply`),
  consumed exactly by `Stack.reply`'s ICMPv4 arm as the reply's id. The
  same frame fires for `icmp_ndo_send` on `wg_xmit`'s error path, where the
  existing cut (`Device.lean:78`, `skipCutSites [.icmpCredit, …]`) gains
  it as a cut.
- `.ipIdentTunnel` — `iptunnel_xmit` (ip_tunnel_core.c:93), which calls
  `__ip_select_ident` **unconditionally** for every outer IPv4 datagram:
  `send4` passes `df = 0` and sets `ignore_df` (socket.c:84-87). This is
  the frame of today's `.ipIdentReserve`/`.ipIdentKey` cut
  (`loopbackRxSites`, `State.lean:117`; `Handshake.lean:412`,
  `Data.lean:144`). The outer IPv4 header is not observed (the listeners
  see the UDP payload), so `send4` consumes it as a **cut**, added to
  `loopbackRxSites`; carrying it as state that nothing checks would be
  accretion. If W9's `send4` (its section 4.2: the transmit at `:85`, one
  level down; `SentDatagram` with a source) lands first, the cut moves to
  that transmit point with the other three.
- **Record count.** Every existing IPv4 trace gains one record per outer
  IPv4 datagram wg0 sends (each handshake message, cookie reply, data
  message and keepalive over an IPv4 endpoint), plus one per ICMPv4 reply.
  The streams are regenerated with the new kernel identity anyway; the
  cost is the record volume and one more site in every IPv4 send cut.
- **The same capture is W4+W7's option K1** (`docs/2026-10-06-w4-w7-transmit-bulk.md`,
  section 3, item 3.6, and decision 13.1: "record the ident at `__ip_select_ident`,

  fragmentation class. That note recommends the connected-sender route

Alternatives that need no kernel change were checked and do not exist: no
sysctl sets a non-DF id to 0; the ICMP socket's `pmtudisc` is fixed at

## 4. The environment model

### 4.1 `Leanux/Env/Stack.lean`: the predicate as outcomes

`Env.deliverInner` becomes `Env.Stack.receive (pkt : List UInt8) : M Unit`,
the arms of 2.2 and 2.3 walked in Linux's order, each ending in one of
(v3):
- `deliver family src sport bytes tos` — the plain UDP datagram to wg0's
  address at 51998 from an allowed, non-martian source with a correct
  header checksum and `ulen == payload` (today's `deliverInner` case),
  appended to the sender's inbox **with its TOS** (the inner header's,
  after the ECN rewrite); from the link-local sender's injection the same,
  observed at the second socket (2.5);
- `react` — `Stack.rst4`, a pure function from the received TCP segment
  (2.2 row 17: `doff ≥ 5`, no options, not RST, to wg0's address from an
  allowed source) to the reply's bytes per 2.4.1, followed by `Stack.reply
  4 dst pkt`;
- `unsupported "excluded: beyond the WireGuard boundary: <row>"` for
  **every other row** of 2.2 and 2.3 — the drops, the trims, the
  multicast/broadcast cases, the IPv6 TCP segment, the ICMP-answered
  packets, fragments, options, extension headers — and for every
  combination not named above. The reason names the row, so a trace that
  hits one fails with the Linux arm in the message.

There is no `drop` outcome in v3: a stack drop is not a modeled outcome
but an excluded one. The rewrite of 2.1 belongs to the **mirror** (section
5); the environment receives the rewritten bytes.

### 4.2 Replies as a nested `wg_xmit`

`Stack.reply` (v3: the IPv4 RST only) does `skipCut [.inetEhashSecret]`
(the first TCP segment of a boot may draw it, 3.2), then calls the mirror's
`WG.wgXmit 4 dst pkt` with `pkt.csum := none` (`CHECKSUM_NONE`: the
segment carries its own checksum, and `encryptPacket`'s checksum-help
decision takes its false outcome). It runs inside `rxPoll`'s
`napiCompleteDone`, i.e. inside `runWorker .netRx`, so the encrypt work it
queues is picked up where D2 already picks up the responder's confirmation
flush: by `runCryptWorkers` after the decrypt worker (`Env.inject`), or
inside the decrypt worker's `cond_resched` in order (a)
(`Env.condResched`). The loopback delivery of the ciphertext and the
sender's inbox follow. No rate rule, no credit draw, no ident, no
flow-label sysctl dependency: the excluded replies took those with them
(v2's text for them is in 2.4.2-2.4.4).

### 4.3 Fragment queues and the expiry units

**v3: dropped** with the reassembly class (2.4.5). No `FragQueue`, no
`Worker.fragExpire4/6`, no change to `Env.runTimers`,
`runTimersPlaceholder` or `Runner.executeTrace`. The design below is kept
for a reinstatement.

`World.fragQueues : List FragQueue` with `{family, key (src, dst, id,
proto), fragments (offset, end, bytes, ecn), len?, firstIn, lastIn,
expires, iif}`. On a fragment: `fragTimerArm` consumed on a new queue
(`expires` from the record, `jiffies` noted as `jiffiesLast`), then the
rules of 2.4.5; on completion the reassembled packet goes back through
`Stack.receive` (minus the fragment arm). Two new environment units,
`Worker.fragExpire4` ("ip_expire") and `.fragExpire6` ("ip6_frag_expire"),
section ids after D3's; `Env.runTimers` handles their sections before
`fireTimer`: exactly one queue with `expires < J_hi` (several →
`unsupported`, their order), then the expiry: silent without `firstIn`,
else `icmp4/6 time-exceeded` quoting the first fragment, via
`Stack.reply`. The trace-end rule of 2.4.5 lives in `Runner.executeTrace`'s
end-of-trace check next to the pending-stops check. Without records (the
domain filter) `runTimersPlaceholder` fires due queues like timers.

## 10. Risks

- **R1 (low, was medium): environment facts verified only by the first

- **R2 (medium): the scoped-source path** (2.5) crosses several stack
  rules (link-local bind, `RT6_LOOKUP_F_IFACE`, the reply's source `::1`).
  A probe trace first; if the reply is not delivered to the second socket

  shows the scope" with the reply `unsupported`.
- **R5 (low): the reply's `wg_xmit` from softirq** reads nothing the
  process-context `wg_xmit` does not (no context-dependent branch exists
  in the driver); its MTU is the route's (1420) as for the sender's
  packets. A difference would be a control-flow mismatch.
- **R7 (low, v3): the approved sysctls change the existing error-path
  cut's behaviour** (2.4.4: no per-destination limit on `icmp_ndo_send`),
  so existing traces with repeated `wg_xmit` errors may show more
  `.icmpCredit` records and NET_RX sections than before. The model is
  record-driven; a mismatch is noisy.

### 15.2 Deviations [AGENT]

- **No second sender socket, and the address is `fe80::ffff:1`.** The
  design's link-local sender (a socket bound to `[fe80::1%1]:51997`) would
  take fixture descriptor 8 and change the descriptor fixture of every trace
  (`LEANUX_FIXTURE`'s `free` range, the mirror's initial table). The
  injection `from: "ll"` is instead sent by the dual-stack sender with
  `IPV6_PKTINFO` (the source and interface 1): wg0 learns the scoped
  endpoint `[fe80::ffff:1%1]:51998` with `src6 = ::1`, and its reply from
  `::1` to `fe80::ffff:1` lands at the same socket, where `IPV6_RECVPKTINFO`
  shows the destination. The design's observation (2.5, "the second
  socket's inbox") is the `dst` field of the reply entry; the design's port
  51997 does not exist. The address is not `fe80::1` because existing traces
  (`b1_trie_routing`, `wg_trie_v6`) and the generator transmit to `fe80::1`
  through wg0, which a local address would intercept (the first run showed
  it: the datagram looped back on `lo` instead of reaching `wg_xmit`). The
  fixture's address is rejected as a `wg_xmit` destination
  (`harness/wg.py`, `Leanux/Runner.lean`), like its other addresses.
- **The observation format** is extended rather than the design's
  "prints `tos` and the scope": datagrams `[family, length, type, tos,
  bytes]`; replies `[10, source, port, scope, tos, destination, length,
  type, receiver, bytes]`; `stats` with the four tstats fields. The
  `recvfrom` in `wg_observe`'s coverage window became a `recvmsg` (the same
  `udp_recvmsg` path; no listed function differs).
- **W6-M24** (the RST's `wg_xmit` after the poll instead of inside its
  NET_RX section) has no one-line mutant: `reply4` runs inside
  `napiCompleteDone` by construction, and moving it after the poll would be
  a rewrite of the environment's control flow, not a planted fault. Listed
  pending, not claimed.
- **The generator classes** (`rx_ecn`, `rx_scoped`, `stack_rst4` in
  `evaluator/generate.py`) are not built in this pass: the handwritten
  corpus covers every kept arm; the classes are a follow-up.
- **Streams H and R are one commit**: `Leanux/Env.lean` and
  `Leanux/WG/RxData.lean` carry both H's observation format and R's arms,
  and a buildable H-only tip would have needed a throwaway version of each.
