# W3 and W12: two small WireGuard coverage workstreams — design, 2026-10-06

Status: **proposed** [AGENT]. Two in-reach workstreams from the coverage
census (`docs/2026-10-06-wireguard-census.md` on `task/census`, rows W3 and
W12; row P13 is the out-of-scope sibling of W3). Both ride on D3's interface
(timer sections at `call_timer_fn`, the kind-303 arm record, the virtual time
advance), which this branch is based on (`task/d3-int`, D3 timers + virtual
time, awaiting merge). Line numbers are in the unpatched `.deps/linux`
(6.12.110) unless a file is named as patched; the kernel is
`kernel/config-x86_64-net-choice`: one CPU, `PREEMPT_NONE`, `TINY_RCU`, no
`ACPI`, periodic tick, `CONFIG_HZ=250` (a tick is 4 ms), booted
`clocksource=refined-jiffies` (D3).

Both workstreams are **behavioral, thin-layer** work: they model the C's data
and control flow and check it differentially against the instrumented kernel.
No proofs. They obey the governing rules of `AGENTS.md`: data and
control-flow correspondence; fail-closed, fail-noisy outcomes for anything
out of scope; environment facts live in `Leanux/Env.lean`, not the mirror;
and each new check **pays for itself** — a named mutant or defect it alone
rejects.

**Neither workstream needs a kernel change, a new wire opcode, a new record
kind, or a new choice-site id.** Both reuse D3's instrumentation unchanged:
the dispatch sections (kinds 300/301), the arm record (kind 303), the advance
record (kind 304), the `Worker` units (`wg_packet_handshake_send_worker` and
the five timer callbacks), and the `wg_advance` operation (opcode 14). Where
a later coordinator allocation might be wanted, placeholders are used
(⟨…⟩); none are required by the designs below.

---

## Part I — W3: `wg_peer_remove` with queued handshake work

### 1. Target

One `WG_CMD_SET_DEVICE` message (`wg_set`) that, in a single call, queues a
peer's handshake-send work and then removes that peer, so that
`peer_remove_after_dead`'s `flush_workqueue(handshake_send_wq)` runs the queued
`wg_packet_handshake_send_worker` synchronously, as a dispatch section, inside
the syscall. The mirror stops here today
(`Keypair.lean:143`, `peerRemove`: `unsupported "removing a peer with queued
handshake work"`); W3 brings the within-syscall case into the domain. The
cross-syscall case (a kworker item pending across calls) stays out
(census P13; section I.8).

This is the only path on which a *removed* peer still transmits: the flushed
worker emits one handshake initiation on the wire, which is the workstream's
headline observable.

### 2. Kernel facts, verified

**The remove path** (`drivers/net/wireguard/peer.c`):
- `wg_peer_remove` (`:156-165`): `peer_make_dead(peer)`; `synchronize_net()`;
  `peer_remove_after_dead(peer)`.
- `peer_make_dead` (`:80-92`): `list_del_init(&peer->peer_list)`,
  `wg_allowedips_remove_by_peer`, `wg_pubkey_hashtable_remove`,
  `WRITE_ONCE(peer->is_dead, true)`. The handshake state is **not** cleared
  here.
- `peer_remove_after_dead` (`:94-150`): `WARN_ON(!is_dead)` (`:96`);
  `wg_noise_keypairs_clear` (`:101`) — note the **handshake** is not cleared,
  only keypairs; `wg_timers_stop` (`:106`); `flush_workqueue(packet_crypt_wq)`
  twice (`:116`, `:118`); `napi_disable`/`netif_napi_del` (`:120`, `:124`);
  **`flush_workqueue(peer->device->handshake_send_wq)` (`:129`)**;
  `--peer->device->num_peers` (`:148`); `wg_peer_put` (`:149`).

**What queues the work, in the same message.** `wg_packet_handshake_send_worker`
runs `peer->transmit_handshake_work` on `handshake_send_wq`
(`send.c:46-53`), queued by `wg_packet_send_queued_handshake_initiation`
(`send.c:55-83`: `wg_peer_get`, then `queue_work(handshake_send_wq,
&peer->transmit_handshake_work)` at `:75`). On a device that is **up**, setting
a peer's persistent keepalive from zero to nonzero sends a keepalive at
`netlink.c:472-479` (`send_keepalive = !old && new && netif_running`); for a
keyless peer `wg_packet_send_keepalive` (`send.c:221-240`) stages an empty
skb and `wg_packet_send_staged_packets` (`:342-414`) takes the `out_nokey`
arm (`:361-362`) → `wg_packet_send_queued_handshake_initiation(peer, false)`
(`:413`). The staged-packets path after any `set_peer` (`netlink.c:482-483`,
`if (netif_running) wg_packet_send_staged_packets`) is a second route to the
same queue. Both require `netif_running`, so **W3 needs the device up** —
which the fixture supports today (`wg_up`).

`WGPEER_F_REMOVE_ME` short-circuits a peer entry before its keepalive is read
(`netlink.c:424-427`, the `goto out`), so one peer cannot both queue work and
remove itself in a *single* entry. W3 uses **two entries for the same public
key in one message**: entry A sets the keepalive (queues the worker), entry B
carries `REMOVE_ME` (flushes it). The peer list is processed in order
(`netlink.c` `set_peer` per entry), so A's `queue_work` precedes B's remove,
and nothing between them runs the worker.

**Why the flush runs the worker synchronously, and deterministically.**
`flush_workqueue` inserts a barrier and `wait_for_completion`s on the pool
(`workqueue.c:3971-`, `flush_workqueue_prep_pwqs:3892-3930`), so the queued
work runs in its kworker while the netlink task sleeps at the barrier. On one
CPU with `PREEMPT_NONE`, the worker could not have run earlier: between
`queue_work` and the flush the only blocking points are `synchronize_net`
(Tiny RCU `synchronize_rcu` only advances `gp_seq`, does not sleep —
`kernel/rcu/tiny.c:150-159`) and the two `packet_crypt_wq` flushes (no crypt
work is pending for a keyless peer). So the worker runs **exactly at the
`handshake_send_wq` flush (`:129`)**, and its `process_one_work` dispatch
section (the D3 patch, `gen-choice-stream.py:676`) is recorded in this
operation as a remote section — logically inline with the syscall.

**What the flushed worker does, with `is_dead` set.**
`wg_packet_handshake_send_worker` → `wg_packet_send_handshake_initiation`
(`send.c:21-44`), which **does not test `is_dead`**: it checks only the 5 s
rate limit (`send.c:25`; `last_sent_handshake` was reset to
`REKEY_TIMEOUT + 1` s in the past at peer create, so it passes), creates the
initiation, adds the MAC, calls `wg_timers_any_authenticated_packet_traversal`
and `_sent`, **sends** (`wg_socket_send_buffer_to_peer`, `:40`), then
`wg_timers_handshake_initiated`. The timer-arming calls go through
`mod_peer_timer` (`timers.c:30-39`), whose guard `netif_running && !is_dead`
now **fails** (`is_dead` is true), so **no timer is armed and no kind-303 arm
record is written** — but `wg_timers_handshake_initiated` evaluates
`get_random_u32_below(...)` as `mod_peer_timer`'s argument before the guard
(`timers.c:184-186`), so the retransmit-jitter record (site `.retransmitJitter`,
`timers.c:186`) **is** written. The worker ends with `wg_peer_put` (`send.c:52`)
dropping the reference it took at queue time. The peer is still in the pubkey
table for lookup? No: `peer_make_dead` removed it from pubkey/allowedips/
peer_list, but the peer object and its handshake state are intact until the
final `wg_peer_put` frees it, so `create_initiation` succeeds and the
datagram goes to the peer's (still-set) endpoint.

**Records and dispatch sections that appear in the operation.** In the
`handshake_send_wq` flush:
- the send-worker section start/stop (kinds 300/301,
  `wg_packet_handshake_send_worker`);
- inside it: `init_ephemeral` (noise.c:541), `tai64n_now` (noise.c:501),
  `index_draw` (peerlookup.c:132), `initiation_last_sent` (send.c:29),
  `initiation_last_sent_again` (send.c:39), `retransmit_jitter`
  (timers.c:186), and the loopback NET_RX section of the emitted datagram
  (`net_rx_action`, with its cut-site records);
- **no kind-303 arm record** (the `mod_peer_timer` guard fails).

**RCU: `call_rcu` → RCU softirq placement — is it recorded? No.** The final
`wg_peer_put` → `kref_release` (`peer.c:200-221`) does
`wg_index_hashtable_remove`, `wg_packet_purge_staged_packets`, then
`call_rcu(&peer->rcu, rcu_release)` (`:220`). On Tiny RCU `call_rcu` only
enqueues (`kernel/rcu/tiny.c:171-199`); `rcu_release` (`peer.c:186-198`:
`dst_cache_destroy`, `memzero_explicit`, `kmem_cache_free`) runs later in
`RCU_SOFTIRQ` via `rcu_process_callbacks`, raised at a quiescent state
(`rcu_qs`, `tiny.c:52-63`). `RCU_SOFTIRQ` is **not** sectioned (the patch
sections only the `NET_RX_SOFTIRQ` vector, `gen-choice-stream.py`), and
`rcu_process_callbacks`/`rcu_release` are **not** in the armed dispatch set,
so the callback **records nothing** and runs outside every section (census
P4). The mirror treats the free as a cut, exactly as `WG.peerPut` already
does (erases the peer from `Device.peers`; no RCU object modeled). W3 adds
no RCU modeling.

The `synchronize_net()` calls (`peer.c:163`, and inside `wg_socket_reinit`)
likewise produce no record and do not sleep on this kernel.

### 3. What is reachable deterministically; what the mirror has today

Deterministic on one CPU: the queue (A) → make-dead → flush-runs-worker (B)
sequence, with the worker's single initiation and its records. Non-deterministic
and therefore excluded (section I.8): a worker that ran *before* the flush
(needs a sleep between queue and remove — none on these paths) and a worker
pending across syscalls (census P13).

The mirror today: `WG.peerRemove`/`peerRemoveAll` (`Keypair.lean:140-184`)
bail with `unsupported` when `handshakePending`. `peerRemoveAfterDead`
(`Keypair.lean:119-137`) already runs a queued **clear** worker
(`clear_peer_work`) in a section at the flush point (D3), and drops it; the
send worker is not handled. `WG.handshakeSendWorker` (`Handshake.lean:457-461`)
and `Env.runOneSendWorker` (`Env.lean:324-332`) already model the worker and
its section; `sendHandshakeInitiation` (`Handshake.lean:441-455`) already
arms via `modPeerTimer` whose guard fails when `isDead`, and draws the jitter
before the guard (`timersHandshakeInitiated`, `:420-422`). So most machinery
exists; W3 wires the flush to the send worker and removes the bail-outs.

### 4. Mirror changes (`Leanux/WG/`)

- **`Keypair.lean`, `peerRemoveAfterDead`:** at the `handshake_send_wq` flush
  (today only the clear work), also run the peer's queued **send** worker, in
  FIFO order with the clear work on the shared `handshake_send_wq`. Concretely,
  before the final `peerPut`: while the peer's send work is queued
  (`Device.sendWorkQueue.contains pid`) or its clear work is queued, run the
  next of them in its section — `runWorker .sendWorker (handshakeSendWorker
  pid)` after removing `pid` from `sendWorkQueue` and clearing
  `handshakePending`, or the existing clear-work branch — choosing the order
  from the section records when both are present (section I.6). The send
  worker runs **after** `is_dead` is set (as the kernel does), so its
  `modPeerTimer` guard fails and no arm record is consumed, matching the
  kernel. Running the worker before the final `peerPut` also keeps
  `requireNotPending` satisfied there (`handshakePending` is false by then).
- **`Keypair.lean`, `peerRemove` and `peerRemoveAll`:** delete the
  `unsupported "removing a peer with queued handshake work"` guards
  (`:143`, `:154`). The queued work is now handled at the flush. Keep the
  existing `mayHaveSlept` placement, but note that correctness no longer rests
  on its assumption (the worker is run explicitly at the flush and its records
  consumed there), which is the fail-noisy requirement.
- **No new decisions, choice sites, records, or `Worker` units.** The send
  worker is `Worker.sendWorker` (index 0, section ids 40/41), already in the
  map.

Files: `Leanux/WG/Keypair.lean` (the two guard removals and the flush-worker
run). No change to `Leanux/WG/Send.lean`, `Handshake.lean`, `Netlink.lean`
(the two-entry message is already expressible; `setPeerCmd` processes entries
in order, queueing on A and removing on B).

### 5. Environment changes (`Leanux/Env.lean`)

None structural. The send worker's section and the loopback NET_RX it raises
are consumed by the existing `runWorker`/`loopbackSoftirq` machinery, now
invoked from `peerRemoveAfterDead` rather than from `runSendWorkers`. The
`wg_set` operation's post-return `Env.runSendWorkers` then finds the
`sendWorkQueue` already drained (the flush consumed it), so no double run.
Environment facts (the peer's endpoint being a fixture listener, so the
emitted initiation is observable and not "routed back into wg0") already hold.

### 6. Harness, trace and generator changes

- **Harness / guest:** none. W3 uses existing operations (`wg_set`, `wg_up`,
  `wg_observe`, `wg_get`) and the existing network fixture (device up). No new
  opcode (⟨none required⟩).
- **Generator (`evaluator/generate.py`):** a small `remove_queued` variant
  (either a new branch of the lifecycle/handshake family or a dedicated
  helper, ≤ 10 % of a sub-suite). Shape: configure one peer with an endpoint
  and `keepalive 0`, `wg_up`, then one `wg_set` whose `peers` list has two
  entries for the same public key — the first `{keepalive: 25}` (queues the
  worker on the up device), the second `{remove: true}`. Followed by
  `wg_observe` (the emitted initiation at the listener) and `wg_get` (the peer
  gone). This is a steered trace: the flushed initiation draws
  `init_ephemeral`/`tai64n_now`/`index_draw`, which the generator supplies as
  steered values so the datagram is byte-exact, with `expect` labels for the
  queue decision (`wg_packet_send_queued_handshake_initiation.*`) and the
  removal.
- **Trace validation (`harness/trace.py`):** none. `harness/wg.py` already
  allows two peer entries with the same key (no duplicate-public-key check in
  `validate_config`), and encodes `remove` + `keepalive` flags.

### 7. Corpus and mutants

**Corpus** `corpus/wireguard/w3_*.json` (add to a corpus script, e.g.
`scripts/wg-l-corpus.py` if W3 integrates with lifecycle, else its own):
- `w3_remove_queued_handshake`: up, one keyless peer with endpoint; one
  `wg_set` with entries `[{keepalive:25}, {remove:true}]` for that peer;
  `wg_observe`, `wg_get`. Expect: one initiation datagram at the peer's
  listener (byte-exact under the steered ephemeral/index), the peer absent
  from the dump, and the flush's send-worker section with its records (no
  kind-303). Steered.
- `w3_remove_only` (**control**): the same peer, up, one `wg_set` with a
  single `{remove:true}` entry and **no** prior keepalive — no work is queued,
  the flush runs nothing, no initiation. Shows the headline datagram is caused
  by the queued work, not by removal itself.

**Mutants** (`scripts/wg-mutants.py`), each rejected by a named trace:
- **W3-M1 — flush drops the worker without running it** (the mirror removes
  the `sendWorkQueue` entry at removal but omits `handshakeSendWorker`):
  rejected by `w3_remove_queued_handshake` — the send-worker section and the
  initiation's records are then **unconsumed** (a hidden mismatch), and the
  initiation datagram is missing from `wg_observe`.
- **W3-M2 — worker runs but arms the retransmit timer** (the mirror ignores
  `is_dead` in `modPeerTimer`'s guard on this path, i.e. arms as if alive):
  rejected by `w3_remove_queued_handshake` — the mirror would consume a
  kind-303 arm record that the kernel did not write (the guard failed), a
  hidden mismatch. This is the data-correspondence check that `is_dead`
  suppresses the arm but not the jitter draw or the send.
- **W3-M3 — worker runs at make-dead order, before `is_dead`** (the mirror
  runs the send worker in `peerMakeDead` instead of after it, i.e. as if
  alive, which would arm the timer): subsumed by W3-M2's signature; kept only
  if the order is expressible as a distinct patch, else folded into W3-M2.

W3-M1 is the paying mutant for the flush-runs-the-worker rule; W3-M2 is the
paying mutant for the `is_dead`-suppresses-the-arm-but-not-the-send rule.
Both are rejected on the Linux build via the kind-303 presence/absence and the
observed datagram — data and control-flow signals, not merely the syscall
result (the `wg_set` returns 0 either way).

### 8. Out of scope (fail-noisy), with the profound reason

| Item | Profound reason |
|---|---|
| A queued handshake worker pending **across** syscalls at removal | Not deterministically reachable on one CPU: the kworker's run relative to the next syscall is scheduling-driven (census P13). The within-syscall flush (W3) is the deterministic case. A capture of the kworker's completion would be needed, which does not pay here. |
| A removal with **both** queued send work and queued clear work whose order on `handshake_send_wq` the records do not fix | In the W3 fixture only the send worker is queued; a combined fixture is a separate, larger case. The section records would order them, but no corpus trace exercises it, so it stays `unsupported` (fail-noisy) until one does — it would not pay today. |
| A removal with queued **crypt** work (encrypt/tx) | Needs a session and in-flight data at removal; its worker timing across the two `packet_crypt_wq` flushes is scheduling-driven (census P5). `Env.requireNoCryptWork`-style exclusion applies. |
| The RCU free (`rcu_release`) as modeled state | Runs unsectioned, records nothing, frees only memory (census P4); the mirror cuts it, as `peerPut` does. |
| `peer_remove_after_dead`'s `WARN_ON(!is_dead)`, saturation/underflow arms of the refcount | Structurally dead on reachable paths (census P14); already `unsupported`/`invariant` in the mirror. |

### 9. Risks (W3)

- **Low: the flushed initiation's endpoint.** The emitted datagram must land
  at a fixture listener (the peer's endpoint), else `deliverSent` reports "a
  datagram routed back into wg0" (fail-noisy). The generator picks a listener
  endpoint, as D1 does.
- **Low: ordering of the send worker vs any clear work at the flush.** Scoped
  out above; a both-queued trace fails noisily, never silently.
- **Low: regression.** Removing the `unsupported` guards touches the shared
  removal path (`wg_destruct`'s `wg_peer_remove_all`, `wg_set`'s
  `REPLACE_PEERS`). The existing suites are the regression; W3 must re-run them
  (the removal path is exercised by many traces).

### 10. User decisions (W3)

- **[AGENT] Recommendation:** adopt W3 as specified. It needs no kernel or
  oracle change, reuses D3's instrumentation, and pays with W3-M1/W3-M2. One
  genuinely interesting behavior (a removed peer emitting one initiation) is
  made exact and checkable. No decision is required of the user beyond the
  usual merge signoff, unless the coordinator prefers to fold W3's corpus into
  the lifecycle (L) suite rather than a standalone `w3_*` set — a packaging
  choice, recommended to follow L if W3 and L integrate together.

## Part II — W12: several peers' same-kind timers firing in one pass

### 1. Target

Make the mirror run, rather than reject, a single `wg_advance` pass in which
more than one peer's timer of the **same kind** is due. Today
`Env.fireTimer` (`Env.lean:426-438`) accepts exactly one due peer per callback
and returns `unsupported "several peers' timers for {symbol} due in one pass
(their order)"`. W12 determines the kernel's order among such timers and
reproduces it in the mirror.

### 2. Kernel facts, verified — the wheel's intra-pass order

**One base, periodic tick, one pass.** Without `NO_HZ_COMMON` there is one
`timer_base` per CPU (`NR_BASES 1`, `timer.c:195-204`), so every WireGuard
timer is in `timer_bases[0]`. After the virtual advance jumps `jiffies`, the
next tick raises `TIMER_SOFTIRQ`; `__run_timers` (`timer.c:2390-2422`) loops
while `jiffies >= base->clk && jiffies >= base->next_expiry`, collecting the
due buckets at each `base->clk` (`collect_expired_timers`, `:1854-1876`) and
firing them level by level (`:2419-2420`). So all due timers run in **one
pass**, at a constant softirq `jiffies` (no tick during the softirq).

**Bucket order, then LIFO within a bucket.** `expire_timers`
(`timer.c:1813-1852`) walks each collected bucket's hlist from `head->first`,
calling `detach_timer(timer, true)` (`:1829`) and `call_timer_fn` (`:1795`,
`fn(timer)`). Timers were enqueued by `enqueue_timer` with
`hlist_add_head(&timer->entry, base->vectors + idx)` (`timer.c:659`), i.e. at
the **head**, and `collect_expired_timers` moves the list preserving order
(`hlist_move_list`). Therefore, within one bucket, timers fire in **reverse
order of insertion (LIFO)**: the most recently armed fires first. Across
buckets, lower (level, index) fires first.

**Which timers share a bucket — what "equal-expiry" means.** The bucket index
is `calc_wheel_index(expires, base->clk)` (`timer.c:584-620`), which picks a
level from `delta = expires − clk` and rounds the expiry **up** to the level's
granularity in `calc_index` (`:567-581`, `bucket_expiry = ((expires >>
3·lvl) + 1) << 3·lvl`). A timer fires no earlier than `expires + 1` and no
later than `expires + 8^lvl`. At HZ 250 the WireGuard delays fall at:
`LVL_START(1..5) = 63, 504, 4032, 32256, 258048` (`timer.c:165`):
- retransmit `1250 + [0,83)` and new-handshake `3750 + [0,83)`: level 2
  (504–4031), granularity 64 ticks;
- persistent keepalive `interval·HZ` (e.g. 25 s = 6250): level 3
  (4032–32255), granularity 512;
- send-keepalive `2500`: level 2;
- zero-key `135000`: level 4 (≥ 32256), granularity 4096.

So **two same-kind timers share a bucket when their expiries fall in one
granularity window of the same level.** Jitter-free timers (persistent
keepalive, zero-key, send-keepalive) armed in the same code path at the same
`jiffies` have **identical** expiry → one bucket. Jitter-bearing timers
(retransmit, new-handshake) armed close together share a bucket when their
jitter-spread expiries round to the same index — the common case (jitter
0–82 ticks ≤ the 64-tick granularity, armed within the same operation).

**The consequence for ordering.** Within a bucket the order is LIFO, **not**
by `expires`. A mirror that ordered same-bucket timers by expiry (earliest
first) — which is what the current domain-filter stand-in
`runTimersPlaceholder` does (`Env.lean:482-495`, "earliest first (bucket
order)") — would get the order **wrong** whenever two same-bucket timers have
different sub-bucket expiries. This is the correspondence point W12 must get
right.

### 3. Is the order determined by the records, or does it need a new capture?

**Determined by the existing records; no new capture is needed.** Each arm
writes a kind-303 record `{jiffies, expires}` at `mod_timer` (site
`timers.c:37`), and the mirror consumes one at each `WG.armTimer` call in the
order it runs the arming code — so the mirror knows, for every pending timer,
its **exact `expires`** (hence its bucket, via `calc_wheel_index`) **and its
insertion order** (hence its LIFO position within the bucket). The kind-300
section-start records confirm **which** callback fired and **how many** times
in the pass, but carry the function address, not the peer; so the per-peer
firing order is **reconstructed** by the mirror from the wheel rule, not read
from a record.

**Observability — where the order pays.** The reconstructed order is checked
only where the callbacks emit per-peer records or bytes downstream:
- **Retransmit (and new-handshake) variant — observable.** Each callback's
  retry queues the send worker, which emits an initiation drawing
  `init_ephemeral`/`tai64n_now`/`index_draw` and sending a byte-distinct
  datagram to the peer's endpoint. The send workers run in firing order and
  consume those records in that order. A mirror that fires the peers in the
  wrong order consumes peer B's initiation records for peer A's worker → the
  datagram bytes (and their endpoint pairing) mismatch → rejected, even though
  `wg_observe` sorts datagrams (the (endpoint, bytes) pairs differ as a set).
- **Persistent-keepalive variant — not independently observable.** Its
  callback sends a keepalive whose bytes come from the peer's keypair and
  counter (mirror state), not from records; swapping the order does not swap
  content, so the sorted datagram set is unchanged. This variant brings the
  multi-peer case **into the domain** but is not used as the paying mutant.

So W12 is honest to "checks pay for themselves": the **ordering rule itself**
is justified (it is the only way to admit the multi-peer pass without a
fail-open skip), and its **correctness** is paid for by a retransmit-order
mutant, not by the persistent-keepalive case.

### 4. Fixture shape

The reliable way to put several same-kind timers in one pass is to **arm them
close together, then fire them with one `wg_advance`**:

- **Primary (observable, paying) — two peers, retransmit:** one `wg_set`
  configures two peers, each with an endpoint and `keepalive 25`, no session;
  `wg_up` sends an initiation for each (the staged keepalive on a keyless peer
  queues an initiation, `device.c:54-58`), arming both retransmit timers
  within the same `wg_up` wait (a few ticks apart → same level-2 bucket); no
  response is injected; one `wg_advance(≈1450)` fires both retransmit timers
  in one pass. Each retry re-initiates (recorded ephemeral/index), emitting
  two fresh initiations in wheel (LIFO) order; `wg_observe`, `wg_get`. Steered:
  the two `wg_up` initiations and the two retries each need their draw entries
  (four initiations total), as D3's steering already supplies for later
  encounters (D3 §13.5).
- **Secondary (domain, not paying) — two or three peers, persistent
  keepalive:** peers with sessions and equal `keepalive` interval; one advance
  fires their persistent keepalives in one pass (identical expiry → one
  bucket, LIFO). Confirms the pass is admitted and the datagrams (sorted) and
  stats agree; exercises three-deep LIFO.

Two peers suffice to exhibit an order (one swap); a three-peer variant stresses
the LIFO over a longer bucket list. The `wg_advance` and margins reuse the D3
generator helpers (`fire_advance`, `quiet_limit`, `evaluator/generate.py:785-805`):
the advance covers the target timers' delay + the level's wheel granularity +
the wait, while every other pending timer (the per-peer zero-key timers from
any session, 540 s) stays below its quiet limit.

### 5. Mirror changes (`Leanux/Env.lean`, `Leanux/WG/`)

- **Record the insertion order of pending timers.** Add a monotonic arm
  counter to `World` (⟨`armSeq : Nat`⟩, incremented in `WG.armTimer`) and
  store, per pending timer, the sequence number at which it was armed — either
  a parallel field or by widening `Peer.timer*`'s value from `Option Nat` to
  `Option (Nat × Nat)` (expiry, armSeq). The latter is a shared-shape change
  (coordinate with D3/L, which read `Peer.timer*`), so the parallel-field form
  is preferred to keep the frozen D3 interface intact
  (`Peer.timer`/`timerPending`/`setTimer` unchanged). Files:
  `Leanux/WG/Types.lean` (the per-timer arm-seq), `Leanux/WG/State.lean`
  (`armTimer` stamps it), `Leanux/Kernel/Defs.lean` (`World.armSeq`).
- **`Env.fireTimer` (`Env.lean:426-438`): replace the one-peer restriction
  with the wheel order.** Compute, for the callback `w`, the set of peers whose
  timer of kind `w.timer?` is pending with `expires < jHi`; group them by
  `calc_wheel_index(expires, clk)` (a small pure helper mirroring
  `timer.c:567-620`, using the base clock the mirror tracks from `jiffiesLast`);
  fire in ascending (level, index) order and, within a bucket, in **descending
  arm-seq (LIFO)**. Each section-start record consumes the next firing in that
  computed order; a section for a callback with no due timer is still a hidden
  mismatch. A single due peer is the existing fast path. Remove the
  `unsupported "several peers' timers … (their order)"`.
- **`Env.runTimers`/`runTimersPlaceholder` (`Env.lean:451-500`):** `runTimers`
  already loops section by section; it calls the new ordered `fireTimer`. The
  placeholder (`--domain`, no records) should fire same-kind due timers in the
  **same wheel order** (bucket, then LIFO) rather than plain earliest-first, so
  the domain-filter prediction matches the checked order; this is the exact
  spot the W12-M1 mutant targets.
- **No new decisions, choice sites, records, `Worker` units, or opcodes.**

### 6. Harness, trace and generator changes

- **Harness / guest:** none. W12 uses `wg_set`, `wg_up`, `wg_inject`,
  `wg_advance`, `wg_observe`, `wg_get` and the existing fixture; no new opcode
  (⟨none required⟩).
- **Generator (`evaluator/generate.py`):** extend the D3 `steered_timers`
  family with a `multi_peer` variant (the two-/three-peer shapes of §II.4),
  reusing `fire_advance`/`quiet_limit` and the per-initiation `draw` steering.
  No wheel-order output is emitted by the mirror for checking; the order is
  checked implicitly through the initiation records and datagrams, so **no new
  `expect` form** is needed (the existing `fired:` and decision labels suffice).
- **Trace validation (`harness/trace.py`):** none.

### 7. Corpus and mutants

**Corpus** `corpus/wireguard/w12_*.json` (add to `scripts/wg-d3-corpus.py`,
the D3 corpus script, which already builds steered timer traces):
- `w12_two_retransmit`: two peers, `wg_up` (two initiations), one advance
  (both retransmits fire, two retries), `wg_observe`, `wg_get`. The paying
  trace. Expect: `fired:wg_expired_retransmit_handshake` and the retry
  decisions; two byte-exact re-initiations.
- `w12_three_retransmit`: three peers, as above; three-deep LIFO.
- `w12_two_persistent` (**domain control**): two peers with sessions and equal
  keepalive, one advance fires both persistent keepalives; the datagrams and
  stats agree. Shows the pass is admitted.

**Mutants** (`scripts/wg-mutants.py`), each rejected by a named trace:
- **W12-M1 — same-bucket timers ordered by expiry instead of LIFO** (the
  mirror sorts due same-kind timers by ascending `expires` within a bucket,
  i.e. drops the arm-seq/LIFO rule): rejected by `w12_two_retransmit` — when
  the two retransmit timers share a bucket with different sub-bucket expiries,
  the mirror fires them earliest-expiry-first while the kernel fires
  most-recently-armed-first, so the two send workers consume each other's
  initiation records → datagram-byte/endpoint mismatch. This is the mutant
  that pays for the LIFO rule; it is rejected only when the two expiries differ
  within the bucket, which the fixture arranges (two `wg_up` initiations a few
  ticks apart).
- **W12-M2 — a dropped firing in a multi-peer pass** (the mirror fires only
  the first same-kind due timer and skips the rest, the old one-peer
  behavior): rejected by `w12_two_retransmit`/`w12_three_retransmit` — a
  section-start record for the second callback is then unconsumed (a hidden
  mismatch) and one re-initiation is missing.

W12-M1 is the correspondence check for the wheel's intra-bucket order; W12-M2
is the check that every due same-kind timer in the pass is run. Both reject on
the Linux build through section-record consumption and datagram bytes.

### 8. Out of scope (fail-noisy), with the profound reason

| Item | Profound reason |
|---|---|
| Same-kind timers of several peers whose order is **not** reconstructible because their arms were **not** recorded (arm records off) | With `ARM_RECORDS` off the mirror has no `expires`/insertion data; the multi-peer pass stays `unsupported`. Arm records on is the D3 oracle, so this is not a limitation in practice, only the stated precondition. |
| Timers of several peers whose expiries straddle a **bucket boundary** such that the wheel's level re-derivation during `__run_timers`'s multi-step `base->clk` advance reorders them beyond the single-bucket LIFO rule | Multi-bucket, multi-level collection across several `base->clk` steps is an additional control path; the fixtures keep all target timers in one bucket (one pass step). A straddling case is admitted only if the records order it unambiguously, else fail-noisy. It would not pay today. |
| Interleaving of **different-kind** timers of different peers in one pass (e.g. one peer's new-handshake and another's retransmit in the same bucket window) | Different callbacks already appear as distinct section symbols, so their order is read from kind-300 records, not reconstructed — already handled by `runTimers` following the records; W12 adds nothing here. |
| The persistent-keepalive order as a *checked* property | Not independently observable (§II.3); adding an order instrument for it would not pay (no mutant it alone rejects). The ordering rule is justified by the retransmit case only. |

### 9. Risks (W12)

- **Medium: the bucket computation must match the kernel.** The mirror's
  `calc_wheel_index` helper must reproduce `calc_index`'s round-up and the
  level thresholds (`timer.c:567-620`) exactly for the WireGuard delays; a
  mistake would mis-bucket two timers and fire them in the wrong order. It is a
  small pure function over the recorded `expires` and the tracked base clock,
  and the Linux-side probe (arm records on) confirms the firing order the
  records show against the mirror's prediction before the corpus is trusted.
- **Low: the base clock the mirror tracks.** The bucket depends on
  `base->clk`, which lags `jiffies` under `__forward_timer_base`
  (`timer.c:994-1016`). W12 needs only the *relative* order within one pass;
  since all target timers are armed at (nearly) the same `jiffies` and fired in
  one pass, the LIFO-by-arm-seq rule is robust to the exact `clk`, and the
  bucket grouping only needs to agree on which timers share a bucket (a
  coarse, granularity-sized test). If a future fixture needs the absolute
  bucket, the recorded arm `jiffies` supplies it.
- **Low: getting two expiries that differ within the bucket.** W12-M1 only
  rejects when the two same-bucket expiries differ; the fixture must arm the
  two timers a few ticks apart (the `wg_up` two-initiation gap) rather than
  identically. If they were identical, the order would be unobservable and
  W12-M1 would not reject — the generator checks the gap.
- **Low: regression.** The ordered `fireTimer` replaces a single-peer fast
  path used by every D3 trace; the D3 suite is the regression.

### 10. User decisions (W12)

- **[AGENT] Recommendation:** adopt W12 as specified. It needs no kernel,
  oracle, wire, or record-format change; it lifts a single-peer restriction
  into the full wheel order using data the D3 arm records already carry; and it
  pays with W12-M1 (the LIFO-vs-expiry correspondence) and W12-M2 (no dropped
  firing). The only shared-shape question is whether to carry the per-timer arm
  sequence as a parallel `World` field or by widening `Peer.timer*`; **[AGENT]
  recommend the parallel field**, to leave D3's frozen `Peer.timer*` shape
  (and L's read of it) untouched. The user's decision is needed only at the
  usual merge signoff.
