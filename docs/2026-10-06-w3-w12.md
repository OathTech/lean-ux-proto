# W3 and W12: two small WireGuard coverage workstreams — design, 2026-10-06

Status: **proposed, revision v2** [AGENT], revised after the coordinator's
critical audit (section IV lists every finding's disposition, including the
pushbacks). Two in-reach workstreams from the coverage census
(`docs/2026-10-06-wireguard-census.md` on `task/census`, rows W3 and W12;
row P13 is the out-of-scope sibling of W3). Both ride on D3's interface
(timer sections at `call_timer_fn`, the kind-303 arm record, the virtual time
advance), which this branch is based on (`task/d3-int`, awaiting merge).
Line numbers are in the unpatched `.deps/linux` (6.12.110) unless a file is
named as patched; the kernel is `kernel/config-x86_64-net-choice`: one CPU,
`PREEMPT_NONE`, `TINY_RCU`, no `ACPI`, periodic tick, `CONFIG_HZ=250` (a tick
is 4 ms), booted `clocksource=refined-jiffies` (D3). The user's goal is 100 %
of reasonable single-CPU WireGuard; everything in reach below is brought into
scope, and the exclusions that remain are mechanized and fail-noisy.

Both workstreams are **behavioral, thin-layer** work: the C's data and
control flow, checked differentially. No proofs. They follow `AGENTS.md`:
data and control-flow correspondence; fail-closed, fail-noisy outcomes;
environment facts in `Leanux/Env.lean`; and every check **pays for itself**
with a named mutant a specific trace rejects.

**Neither workstream needs a kernel change, a new wire opcode, a new record
kind, or a new choice-site id.** Both reuse D3's instrumentation unchanged:
the dispatch sections (kinds 300/301), the arm record (kind 303), the advance
record (kind 304), the `Worker` units, and `wg_advance` (opcode 14). W12 adds
one **host-side** steering entry (section II.6). Placeholders ⟨…⟩ mark where a
coordinator allocation would go; none is required.

## Part I — W3: `wg_peer_remove` with queued handshake work

### 1. Target

One `WG_CMD_SET_DEVICE` message (`wg_set`) that, in a single call, queues
handshake-send work and then removes a peer, so that the flushes in
`peer_remove_after_dead` run the queued `wg_packet_handshake_send_worker`
synchronously — as dispatch sections inside the syscall. The mirror stops
here today (`Keypair.lean:167` and `:178`, `unsupported "removing a peer with
queued handshake work"`; the same guards on `task/l-m` at `:149` and `:162`).
W3 brings the within-syscall case into the domain, for the removed peer's own
work **and for other peers' work the same flush drains** (section I.2, "what a
flush runs"). The cross-syscall case (a kworker item pending from an earlier
call) stays out (census P13; section I.8).

This is the only path on which a *removed* peer still transmits: the flushed
worker emits one handshake initiation, which is the workstream's headline
observable, together with `tx_dropped = 1` from the staged keepalive purged
at the peer's release.

### 2. Kernel facts, verified

**The remove path** (`drivers/net/wireguard/peer.c`):
- `wg_peer_remove` (`:156-165`): `peer_make_dead`; `synchronize_net()`;
  `peer_remove_after_dead`.
- `peer_make_dead` (`:80-92`): `list_del_init(&peer->peer_list)`,
  `wg_allowedips_remove_by_peer`, `wg_pubkey_hashtable_remove`,
  `WRITE_ONCE(peer->is_dead, true)`. The handshake state is **not** cleared.
- `peer_remove_after_dead` (`:94-150`): `WARN_ON(!is_dead)` (`:96`);
  `wg_noise_keypairs_clear` (`:101`; keypairs only, not the handshake);
  **`wg_timers_stop` (`:106`)** = five `timer_delete_sync` and
  **`flush_work(&peer->clear_peer_work)`** (`timers.c:235-243`, the flush at
  `:242`); `flush_workqueue(packet_crypt_wq)` twice (`:116`, `:118`);
  `napi_disable`/`netif_napi_del` (`:120`, `:124`);
  **`flush_workqueue(peer->device->handshake_send_wq)` (`:129`)**;
  `--num_peers` (`:148`); `wg_peer_put` (`:149`).
- `wg_peer_remove_all` (`:167-184`): `wg_allowedips_free`, every peer made
  dead, `synchronize_net`, then `peer_remove_after_dead` per peer — so the
  **first** peer's flushes drain whatever is queued for every peer.

**What queues the work, in the same message.** `transmit_handshake_work`
(`wg_packet_handshake_send_worker`, `send.c:46-53`) is queued on
`handshake_send_wq` by `wg_packet_send_queued_handshake_initiation`
(`send.c:55-83`: `wg_peer_get`, `queue_work` at `:75`). On an **up** device,
setting a peer's persistent keepalive from zero to nonzero sends a keepalive
at `netlink.c:472-479`; for a keyless peer `wg_packet_send_keepalive`
(`send.c:221-240`) stages an empty skb (`:233`) and
`wg_packet_send_staged_packets` (`:342-414`) takes `out_nokey` (`:361-362`):
the skb goes **back on the staged queue** (`:406-408`) and
`wg_packet_send_queued_handshake_initiation(peer, false)` queues the worker
(`:413`). `netlink.c:482-483` (`if (netif_running)
wg_packet_send_staged_packets`) is a second route to the same queue.

`WGPEER_F_REMOVE_ME` short-circuits a peer entry before its keepalive is read
(`netlink.c:424-427`), so one entry cannot both queue and remove. W3 uses
**two entries for the same public key in one message** — entry A sets the
keepalive (queues the worker), entry B carries `REMOVE_ME` (flushes it);
`set_peer` runs per entry in list order. `harness/wg.py` `validate_config`
(`:77-109`) has no duplicate-key rule, so the message is already expressible.

**What a flush runs (audit M2, verified).** A workqueue pool's worker runs
its worklist FIFO. `flush_work(w)` (`workqueue.c:4232-4300`) inserts a
barrier **right after `w`** in the worklist (`insert_wq_barrier`, `:3808-`,
`head = target->entry.next`) and waits; everything queued **before** `w` on
that pool runs first. `flush_workqueue(wq)` (`:3971-`,
`flush_workqueue_prep_pwqs:3892-3930`) waits for every item queued on `wq` so
far. `handshake_send_wq` is `WQ_UNBOUND` on the shared default unbound pool,
and both `transmit_handshake_work` and `clear_peer_work` are queued on it.
So, in `peer_remove_after_dead`:
- at **`:106`** (`wg_timers_stop` → `flush_work(clear_peer_work)`): if the
  peer's clear work is pending, every `handshake_send_wq` item queued before
  it (any peer's send work or clear work) runs, then the clear work; if it is
  **not** pending, `start_flush_work` finds no pool (`:4186-4188`) and
  **nothing runs**;
- at **`:129`** (`flush_workqueue(handshake_send_wq)`): **every** queued item
  runs, FIFO, for every peer.
`flush_work`/`flush_workqueue` with nothing pending do not sleep; neither does
`synchronize_net` on Tiny RCU (`kernel/rcu/tiny.c:150-159`). With
`PREEMPT_NONE` on one CPU the queued worker therefore runs **exactly at the
first flush that covers it**, in its kworker while the netlink task waits at
the barrier; its `process_one_work` dispatch section (the D3 patch,
`gen-choice-stream.py:676`) is recorded in this operation.

**What the flushed worker does, with `is_dead` set.** `wg_packet_send_handshake_initiation`
(`send.c:21-44`) **does not test `is_dead`**: the 5 s rate limit passes
(`last_sent_handshake` was reset to `REKEY_TIMEOUT + 1` s in the past at
create, `peer.c:55`), the initiation is created and MAC'd, the two timer calls
go through `mod_peer_timer` (`timers.c:30-39`) whose guard `netif_running &&
!is_dead` now **fails** — so **no timer is armed and no kind-303 record is
written** — but `wg_timers_handshake_initiated` evaluates
`get_random_u32_below(...)` as `mod_peer_timer`'s argument before the guard
(`timers.c:184-186`), so the **retransmit-jitter draw is recorded**; the
datagram is **sent** (`wg_socket_send_buffer_to_peer`, `:40`, to the still-set
endpoint); `wg_peer_put` (`:52`) drops the queue-time reference. For
another, still-alive peer whose work the same flush drains, the guard passes
and its arms **are** recorded — the two cases differ exactly in the kind-303
records.

**Records and sections in the operation**, for the removed peer's worker: its
section start/stop (`wg_packet_handshake_send_worker`); inside,
`init_ephemeral` (noise.c:541), `tai64n_now` (noise.c:501), `index_draw`
(peerlookup.c:132), `initiation_last_sent` (send.c:29),
`initiation_last_sent_again` (send.c:39), `retransmit_jitter`
(timers.c:186), and the nested loopback NET_RX section of the datagram; **no
kind-303 record**.

**`tx_dropped` (audit m5).** The staged keepalive skb from entry A is still on
the staged queue at the final release: `kref_release` (`peer.c:200-221`) calls
`wg_packet_purge_staged_packets` (`:217`; `send.c:333-340`, `tx_dropped +=
qlen`) → **`tx_dropped = 1`**. The mirror's `peerPut` already adds
`p.staged.length` to `txDropped`. The control without a queued keepalive
leaves it at 0.

**RCU (`call_rcu` → RCU softirq): not recorded.** `kref_release` ends in
`call_rcu(&peer->rcu, rcu_release)` (`:220`); on Tiny RCU `call_rcu` only
enqueues (`tiny.c:171-199`), and `rcu_release` (`peer.c:186-198`: free only)
runs in `RCU_SOFTIRQ` at a later quiescent state (`rcu_qs`, `tiny.c:52-63`).
`RCU_SOFTIRQ` is not sectioned (the patch sections only the `NET_RX` vector)
and neither function is in the armed set, so it **records nothing** (census
P4). The mirror cuts the free, as `WG.peerPut` already does.

### 3. What is reachable deterministically; what the mirror has today

Deterministic on one CPU, within one `wg_set`: send work queued by earlier
entries (for the removed peer and/or other peers) runs at the first covering
flush of the remove — `:106` only when the removed peer's clear work is
pending, else `:129`. **Not** reachable deterministically, hence excluded
(section I.8): a `clear_peer_work` pending at a syscall (it is queued only by
the zero-key timer callback in a softirq and runs in that advance's wait —
stream M's `d3_zero_key`, `d3_zero_key_after_new_handshake`; it could be
pending at a syscall only if the timer expired inside that syscall, a timing
event, or under the `advance-wait-0` guest variant, a control), and
`wg_peer_remove_all` with queued work (`REPLACE_PEERS` is processed before
the peers list, `netlink.c:540`, and `wg_destruct` is a later syscall).

The mirror today: `peerRemove`/`peerRemoveAll` bail with `unsupported`
(`Keypair.lean:167`, `:178`); `peerRemoveAfterDead` (`:143-161`) runs a
queued **clear** work at `wg_timers_stop`'s flush (`:149-157`, the D3 rule,
inlining `hidden (.sectionStart .clearPeerWorker)`); the send worker is not
handled. `WG.handshakeSendWorker` (`Handshake.lean:459-461`),
`sendHandshakeInitiation` (`:441-455`, arming through `modPeerTimer` whose
guard fails when `isDead`, jitter drawn before the guard at `:421`) and
`Env.runOneSendWorker` (`Env.lean:324-332`) already model the worker. W3 wires
the flushes to the queue and removes the bail-outs. On `task/l-m` the
`mayHaveSlept` calls are already gone (`Keypair.lean:150-152` there), with
the Tiny-RCU reason (audit M5); W3 lands **after L** and inherits that.

### 4. Mirror changes

**One FIFO for `handshake_send_wq` [AGENT, recommended; coordinator's OK
needed, it touches D3 fields].** The C has one workqueue carrying two kinds of
item; the mirror has two lists (`Device.sendWorkQueue`, `Device.clearWorkQueue`,
`Types.lean:336-357`), which lose the inter-kind order the flush semantics
need. Replace them by `Device.handshakeSendWq : List WqItem` with
`inductive WqItem | send (pid) | clear (pid)`, oldest first — the C's shape.
Then every flush is a plain FIFO drain and a wrong order shows as a section
mismatch (fail-noisy), with no record peeking in mirror code. Readers to
update: `Send.lean:68` (enqueue), `Timers.lean:61-64` (the clear enqueue and
its `already_queued` test), `Keypair.lean:152-153`, and in `Env.lean`
`runOneSendWorker` (`:324`), `runSendWorkers` (`:338-344`), `afterXmit`
(`:358`), `runOneClearWorker` (`:405-410`), `runTimers` (`:459-466`, `:473`),
`runTimersPlaceholder` (`:498-500`), `observe` (`:560`). `Peer.handshakePending`
stays as the `queue_work` pending bit. **Alternative** if the D3 fields must
not move: keep the two lists and drain in record order by peeking the next
section start (`peekHiddenSite` is available to `WG` code; `Env.runTimers`
does this at `Env.lean:451-470`); this is correct but puts a record-driven
choice into mirror code, which the single FIFO avoids.

**Module placement (audit M1, verified cycle).** The import order is
`Peer ← Keypair ← Send ← Netlink ← Handshake ← Data ← Timers` (and
`Receive`, `Device`, `RxData` above), so `Keypair.lean` cannot call
`handshakeSendWorker`. Restructure, coordinated with L (which owns the new
`Socket.lean` on `task/l-m`):
- move `andM`/`orM` (`Netlink.lean:93-94`) down to `State.lean`;
- move `clearPeerEndpointSrc`, `endpointEq`, `setPeerEndpoint`
  (`Netlink.lean:88-91`, `:115-135`) into L's `Leanux/WG/Socket.lean`, placed
  **below** `Handshake` (importing `Send`);
- `Handshake.lean` imports `Socket` and `NoiseCrypto` instead of `Netlink`;
- `peerRemove`, `peerRemoveAll`, `peerRemoveAfterDead` move from `Keypair.lean`
  to a new **`Leanux/WG/PeerRemove.lean`** importing `Handshake` (and, for
  the clear work, `Keypair`'s `queuedExpiredZeroKeyMaterial`);
- `Netlink.lean` imports `PeerRemove`.
Resulting order: `Peer ← Keypair ← Send ← Socket ← Handshake ← PeerRemove ←
Netlink ← Device`, `Handshake ← Data ← Timers`: acyclic.

**`PeerRemove.lean`, `peerRemoveAfterDead`:** mirror the two flushes with a
local drain `drainHandshakeSendWq (upTo : Option PeerId)`:
- at `wg_timers_stop` (`peer.c:106`): if `.clear pid` is in the FIFO, run every
  item from the head up to and including it; else nothing;
- at `:129`: run every remaining item.
Each item runs **inline with its section records**, as the clear-work
precedent does: `_ ← hidden (.sectionStart .sendWorker); handshakeSendWorker
p; _ ← hidden (.sectionStop .sendWorker)` (the send worker has no
`cond_resched`, `Worker.resched?`, so no deferred stop), and likewise for
`.clear`. For a `.send p` item set `handshakePending := false` first (the
`queue_work` bit clears when the item is dequeued). The removed peer's own
worker runs after `is_dead` is set, so its `modPeerTimer` guards fail and no
arm record is consumed; another peer's worker arms normally. The drain
precedes `--num_peers` and the final `peerPut`, so `requireNotPending` holds
there.

**`peerRemove`, `peerRemoveAll`:** delete the `unsupported` guards; no
`mayHaveSlept` (M5). `peerRemoveAll`'s per-peer `peerRemoveAfterDead` drains
the whole FIFO at the first peer, as the kernel does; in reach only with an
empty queue (section I.3), so the drain is exercised there trivially.

**No new decisions, choice sites, records, `Worker` units, or opcodes.**

### 5. Environment changes (`Leanux/Env.lean`)

Only the readers of the merged FIFO (section I.4). The operation's post-return
`runSendWorkers` finds the FIFO already drained. The emitted datagram goes to
the peer's endpoint, a fixture listener, so `deliverSent` delivers it.

### 6. Harness, trace and generator changes

- **Harness / guest / trace validation:** none (existing operations; no new
  opcode, ⟨none required⟩).
- **Generator:** a `remove_queued` variant in the lifecycle family (L's
  `lifecycle` class, `evaluator/generate.py`), ≤ 10 % of it: one keyless peer
  with a listener endpoint and `keepalive 0`, `wg_up`, one `wg_set` with

  second peer whose `{keepalive: 25}` entry precedes the remove (its work is

**Mutants** (`scripts/wg-mutants.py`), each rejected by a named trace:

### 8. Out of scope (fail-noisy), with the reason

| Item | Reason |
|---|---|
| Work pending **across** syscalls at a remove, including a pending `clear_peer_work` | Not deterministically reachable: the clear work is queued only in a softirq and runs in the same wait (stream M); a kworker item outliving a wait is scheduling-driven (census P13). The `advance-wait-0` variant that could produce it is a control, not the oracle. |
| Queued **crypt** work at a remove (a session's keepalive queued by entry A, flushed at `peer.c:116`/`:118`) | **In reach and deterministic** (audit m2): the two flushes run the encrypt worker, then the tx work it queued. Stays `unsupported` meanwhile. |
| `wg_peer_remove_all` with queued work | Not reachable in-syscall (section I.3); the drain is still correct. |
| The RCU free as modeled state | Unsectioned, records nothing, frees only memory (census P4). |
| `WARN_ON(!is_dead)`, refcount saturation arms | Structurally dead (census P14); already `unsupported`/`invariant`. |

### 9. Risks (W3)

- **Low: the emitted datagram's endpoint** must be a listener, else
  `deliverSent` fails noisily; the generator picks listeners as D1 does.
- **Low: the FIFO merge** touches D3 fields read by `Env.runTimers`; the D3
  suite is the regression. If the coordinator declines the merge, the
  record-order drain is the fallback (section I.4).
- **Low: the module restructure** touches L's `Socket.lean` and Handshake's
  imports; it is a pure move, with `lake build` and the suites as evidence.

### 10. User decisions (W3)

- **[AGENT] Recommendation:** adopt; land **after L**, folded into L's corpus;

## Part II — W12: several peers' same-kind timers firing in one pass

### 1. Target

Run, rather than reject, a `wg_advance` pass in which more than one peer's
timer of the **same kind** is due: `Env.fireTimer` (`Env.lean:426-438`)
accepts exactly one due peer per callback today and returns `unsupported`.
W12 reproduces the kernel's intra-pass order — **across buckets and within a
bucket** — and makes the mirror's per-timer state carry what the wheel uses.
Multi-bucket passes and differing intervals are in scope (audit M4); the only
exclusions left are mechanized (section II.8).

### 2. Kernel facts, verified — the wheel's intra-pass order

**One base, one pass.** `NR_BASES 1` (`timer.c:195-204`). After the advance,
the tick raises `TIMER_SOFTIRQ`; `__run_timers` (`:2390-2422`) loops
`while (jiffies >= base->clk && jiffies >= base->next_expiry)` (`:2400-2401`):
`collect_expired_timers` sets **`base->clk = base->next_expiry`** (`:1857`)
and moves every level's bucket due at that `clk` into `heads[]` in ascending
level order (`:1862-1875`); `base->clk++`, `timer_recalc_next_expiry`
(`:2416-2417`); then **`while (levels--) expire_timers(base, heads + levels)`
(`:2419-2420`): the highest collected level first.** Each `expire_timers`
(`:1813-1852`) walks its list from `head->first`, `detach_timer` (`:1829`),
`call_timer_fn` (`:1795`). So every due timer runs in one pass at a constant
softirq `jiffies`.

**Buckets.** `calc_wheel_index(expires, clk)` (`:584-620`) picks the level
from `delta = expires − clk` (`LVL_START(n) = 63 << 3(n−1)`: 63, 504, 4032,
32256, 258048; `:165`) and `calc_index` (`:567-581`) rounds **up**:
`bucket_expiry = ((expires >> 3·lvl) + 1) << 3·lvl` (`:579-580`); the slot
index is `LVL_OFFS(lvl) + (that & LVL_MASK)` (`:581`) — **it wraps mod 64**,
so the mirror orders by the absolute `bucket_expiry`, never by the index.
`enqueue_timer` inserts at the **head** (`hlist_add_head`, `:659`);
`hlist_move_list` preserves order.

**The order (audit C1).** Timers fire in ascending **`bucket_expiry`**; at one
`clk` step (several levels collected together) the **higher level first**;
within one bucket in **reverse insertion order (LIFO)**. Key:
`(bucket_expiry asc, level desc, insertion seq desc)`.

**Re-arming (audit M3).** `__mod_timer` (`:1064-1190`) on a **pending** timer
computes the new index (`:1115-1116`) and, if it equals the old one, only
updates `timer->expires` and **keeps the list position** (`:1123-1130`); only a
bucket change detaches and re-enqueues at the head (`:1144`, `:1181-1183`).
An unchanged expiry returns at once (`:1087`). A fired timer is detached
(`:1829`), so its callback's re-arm is a fresh enqueue at the head.

**`base->clk` at arm time (audit m6).** `forward_timer_base` (`:1018-1021`,
`__forward_timer_base:994-1016`) moves `clk` to `jiffies` only when
`next_expiry > jiffies`; with a due timer still pending it moves to
`next_expiry`, behind `jiffies`. Inside a catch-up pass this happens at a
re-arm from a callback while later buckets are still due.

**WireGuard delays at HZ 250:** retransmit `1250 + [0,83)` and new-handshake
`3750 + [0,83)`: level 2, granularity 64; send-keepalive 2500: level 2;
persistent keepalive `interval·HZ` (25 s = 6250, 30 s = 7500): level 3,
granularity 512; zero-key 135000: level 4, granularity 4096. The retransmit
jitter range (0–82) **exceeds** the level-2 granularity (64), so two
retransmit timers armed at the same `jiffies` with unsteered jitters share a
bucket only about half the time (v1 had this wrong; audit C2).

### 3. Is the order determined by the records, or does it need a new capture?

**Determined; no new capture.** Each arm writes a kind-303 record
`{jiffies, expires}` at `mod_timer` (site `timers.c:37`), consumed by
`WG.armTimer` in the mirror's own arming order. So for every pending timer the
mirror holds its exact `expires`, the `jiffies` at the arm (its `clk`, under
the m6 condition), hence its level and `bucket_expiry`, and its insertion
sequence (bumped only on a (re)enqueue, per M3). The kind-300 section starts
say which callback ran and how many times — the function address, not the
peer — so the **per-peer order is reconstructed** from the wheel rule.

**Where the reconstruction is checked.** The order is observable, and a
mis-ordering mutant rejected, whenever the callbacks leave per-peer records or
bytes downstream:
- **retransmit / new-handshake:** each retry's send worker draws
  `init_ephemeral`/`tai64n_now`/`index_draw` and emits a byte-distinct
  initiation (MAC1 keyed by the peer's public key, the encrypted static). A
  wrong order makes the mirror consume peer B's draws for peer A's worker:
  the datagram **bytes** differ (the observation carries family, length, type
  and bytes only, `harness/linux.py:211-234` — no receiving endpoint, which
  v1 wrongly relied on), and the index entries land on the wrong peers;
- **persistent keepalive with differing intervals** (audit M4): each tx
  worker's `create_data_done` re-arms through traversal with
  `interval·HZ`, and `armTimer` checks `expires − jiffies ∈ {delay−1,
  delay}` — the first arm record after a swapped order fails that check. Only
  equal intervals are order-blind; v1's "not observable" claim was too broad.

### 4. Fixture shape

Two peers suffice; three stress a longer LIFO list. Fixtures:
- **`w12_retransmit_lifo` (same bucket, LIFO):** two keyless peers A, B with
  listener endpoints and `keepalive 25`; `wg_up` sends A's then B's initiation
  (the send workers run FIFO in the `wg_up` wait, usually within one tick),
  with **both retransmit jitters steered equal** (section II.6) so the two
  expiries are identical (or differ by one if a tick lands between the two
  arms) and share the level-2 bucket; one `wg_advance(1450)` fires **B then
  A** (LIFO); each retry re-initiates (steered draws), two initiations;
  `wg_observe`, `wg_get`. The persistent keepalives (6250, level 3) stay below
  their quiet limit (`quiet_limit(6250)` = 3975 > 1450).
- **`w12_persistent_buckets` (different buckets, bucket order; audit M4):**
  peers A (`keepalive 25`) and B (`keepalive 30`), both with sessions (two
  steered handshakes, D1's responder per peer), armed A then B; one
  `wg_advance(8050)` (≥ 7500 + 512 + 25). Expiries differ by ≥ 1250 > 512, so
  they are in different level-3 buckets and **A fires first** although B was
  armed later; both re-arm from their tx workers with delays 6250 and 7500,
  which `armTimer` checks. The responses' traversal re-arms exercise M3
  (same bucket → position kept, or a 512-boundary crossing → re-enqueue; the
  mirror computes either).
- **`w12_three_retransmit`:** three peers as the first fixture (stretch).

### 5. Mirror changes

- **Per-timer state (audit M3/m6)** — a parallel field, leaving D3's frozen
  `Peer.timer* : Option Nat` untouched [AGENT]: `Peer.timerWheel : PeerTimer →
  Option { level : Nat, bucketExpiry : Nat, seq : Nat }` (five fields or a
  small map; `Types.lean`), plus `World.armSeq : Nat` (`Defs.lean`). In
  `WG.armTimer` (`State.lean`): take the record's `jiffies` as `clk` **only if
  no pending timer has `bucketExpiry ≤ jiffies`**, else `unsupported "an arm
  while a due timer is pending (base->clk may lag jiffies)"` (m6, fail-noisy);
  compute `(level, bucketExpiry)` as `timer.c:567-620`; if the timer was not
  pending or the bucket changed, `seq := armSeq++` (a head enqueue); else keep
  `seq` (position kept). Correct the `armTimer` comment (`State.lean:66-67`,
  "`mod_timer` of a pending timer moves it … overwritten"): the field is
  overwritten in both arms, but the **list position** changes only with the
  bucket. `delTimer` and a firing clear the wheel entry.
- **`Env.fireTimer` (`Env.lean:426-438`):** among the peers whose timer of the
  callback's kind is pending with `expires < jHi`, fire the first by
  `(bucketExpiry asc, level desc, seq desc)`; the section-start record
  consumes it. None due stays a hidden mismatch. Remove the "several peers …
  (their order)" `unsupported`.
- **`runTimersPlaceholder` (`Env.lean:482-500`):** the domain filter fires
  same-kind due timers in the same key order (today earliest-`expires` first,
  which is the W12-M1 behavior).
- **No new decisions, choice sites, records, `Worker` units, or opcodes.**

### 6. Harness, trace and generator changes

- **Steering the jitter (audit C2), host-only.** `harness/steer.py:31`
  `STEERABLE` gains `'retransmit_jitter'` (site 14, `timers.c:186`, kind 101
  `get_random_u8`, 1 byte; `HOOKS` already maps it) and, for symmetry,
  `'new_handshake_jitter'` (site 16, `timers.c:150`). The kernel applies
  steering generically by IP (`kcov_steer_apply`, patch `:108-125`), so no
  kernel change. **Domain:** a byte `r` the inline sampler accepts,
  `(83·r) mod 256 ≥ 7` (`random.h:76-80`, mirrored at
  `Handshake.lean:343-348`); the result is `(83·r) >> 8`. `r = 0x00` is
  **rejected** by the sampler (a second draw the schedule would also have to
  cover), so jitter 0 is steered as `r = 0x01`. The generator emits one entry
  per initiation encounter in order (four in `w12_retransmit_lifo`: two at
  `wg_up`, two retries), as D3's `D3_DRAWS` does for the other sites.
- **Generator:** a `multi_peer` variant of `steered_timers`
  (`generate.py:807-`) producing the two fixtures of section II.4, reusing
  `fire_advance`/`quiet_limit`. No new `expect` form: `fired:` is a **set**
  of labels (`check.py:937`), so the count and order are checked through the
  section records and bytes, not through `expect`.
- **Harness / guest / trace validation:** none (⟨no opcode required⟩).
- **`scripts/wg-mutants.py`:** for the W12 mutants, read the run's recorded
  kind-303 records and **assert the bucket relation the fixture intends**
  (same level-2 bucket for `w12_retransmit_lifo`; different level-3 buckets
  with A's lower for `w12_persistent_buckets`); a run where it does not hold is
  reported **inconclusive**, as `D1-M15`/`D2-M12` are (`:387-394`).

### 7. Corpus and mutants

**Corpus** `corpus/wireguard/w12_*.json` (in `scripts/wg-d3-corpus.py`):
`w12_retransmit_lifo`, `w12_persistent_buckets`, `w12_three_retransmit`.

**Mutants**, each rejected by a named trace:
- **W12-M1 — same-bucket order by `expires` (stable) instead of LIFO:**
  `w12_retransmit_lifo`. With equal steered jitters the expiries are
  identical, so a stable sort fires A first while the kernel fires B first; if
  a tick fell between the two arms, B's expiry is one higher and the sort
  again fires A first. Either way the two retries' draws are consumed for the
  wrong peers → initiation bytes mismatch. The only escape — the one-tick gap
  straddling a 64-tick boundary, about 1/64 of the already rare tick-between
  case — is flagged inconclusive by the bucket assertion, never a false pass.
- **W12-M2 — only the first same-kind due timer fires:**
  `w12_retransmit_lifo` / `w12_three_retransmit` — the second section-start
  record is left **unconsumed** (hidden mismatch); one retry is missing.
- **W12-M3 — pure LIFO, buckets ignored (audit M4):**
  `w12_persistent_buckets` — the mutant fires B first; B's tx worker then
  checks the first arm record (A's, delay 6250) against 7500 → hidden
  mismatch.

### 8. Out of scope (fail-noisy), with the reason

| Item | Reason |
|---|---|
| Arm records off | Without kind-303 the mirror has no `expires`/insertion data; the multi-peer pass stays `unsupported`. Arm records on is the D3 oracle. |
| An arm while a due timer is pending (`base->clk` behind `jiffies`, m6) | The bucket would be computed with the wrong `clk`; `armTimer` stops noisily. Can arise only for a re-arm inside a callback while later buckets of the same pass are still due; none of the D3 corpus traces hit it (one timer due per pass), and the W12 fixtures re-arm from workers after the pass. |

v1's "straddling buckets" and "admitted only if the records order it" items
are gone (audit M4, m7): multi-bucket passes are ordinary and the key above
orders them; the second had no mechanism and was fail-open.

### 9. Risks (W12)

- **Medium: the bucket helper must match `timer.c`.** A pure function of
  `(expires, clk)`; the Linux-side probe (arm records on) compares the firing
  order the sections show with the mirror's prediction on both fixtures before
  the corpus is trusted.
- **Low: the m6 condition on existing traces.** A D3 trace that re-arms inside
  a callback while another bucket is due would now stop; none does today, and
  a new one would stop noisily, not silently.
- **Low: jitter steering.** The schedule must cover every jitter encounter
  with an accepted byte; a rejected byte costs an extra draw the schedule did
  not plan, which the steering check reports as a mismatch (fail-noisy).
- **Low: the two-session fixture's budget** (two handshakes, one advance)
  fits `WAIT_BUDGET_SECONDS` (2.8 s: two `wg_set`/`wg_up` waits, two injects,
  one advance).
- **Low: regression** of the ordered `fireTimer` on the D3 suite.
