# D3: WireGuard timers and time control — design, 2026-10-05

Status: **proposed** [AGENT], for the user's decisions in section 11.4. The
direction is the user's [USER 2026-10-04]: "complete on one CPU" for
WireGuard, in the sequence D2 data plane, **D3 timers**, then pipes as the
scale test. D3 needs (a) timer dispatch sections, (b) a way to make armed
timers fire within a trace without waiting real seconds, treated as a
supplied or captured scheduling choice, and (c) time control with monotonic
consistency for the key-expiry arms. Timers and clocks are generic kernel
mechanisms, so the instrument must serve pipes and epoll unchanged.

D3 **needs a kernel change** (sections 3, 4 and 11), which the user
approves at signoff as an oracle change. Line numbers are in the unpatched
`.deps/linux` (6.12.110) unless a file is named as patched; the kernel is
`kernel/config-x86_64-net`: `CONFIG_HZ=250` (a tick is 4 ms),
`CONFIG_HZ_PERIODIC`, no `NO_HZ`, no `HIGH_RES_TIMERS`, `PREEMPT_NONE`, one
CPU, `TINY_RCU`, no `SUSPEND`/`PM_SLEEP`, no hung-task or lockup detectors
(`config-x86_64-net:92-95,110-114,130,258-290,331-335,372,2034-2037`).

## 1. Target

Every path of `drivers/net/wireguard/timers.c` reachable on one CPU, checked
against Linux:
- the five timers armed, modified, deleted and **fired**, with what each
  callback does: the retransmit with its attempt count up to
  `MAX_TIMER_HANDSHAKES`, the keepalive with `need_another_keepalive`, the
  new handshake, the zeroing of key material through its work item, and the
  persistent keepalive;
- the **key-expiry arms** that D2 deferred: `REJECT_AFTER_TIME` on send
  (`send.c:365`) and receive (`receive.c:253`), send-side `keep_key_fresh`
  at `REKEY_AFTER_TIME` (`send.c:134`), receive-side `keep_key_fresh` at
  165 s (`receive.c:232-233`);
- the clocks these paths compare: coarse boot time (recorded today, kind
  208) and `jiffies` (unrecorded today, "a declared gap").

The check sees the datagrams the callbacks cause (initiations, keepalives),
`tx_dropped` from the retransmit's purge, the dump, control flow in all of
`timers.c`, and the operands of every clock comparison.

## 2. The kernel mechanism

### 2.1 WireGuard's five timers

`struct wg_peer` holds five `struct timer_list` (`peer.h:53-55`), the
attempt counter and the two flags (`:56-59`), and three work items
(`:49`). `wg_timers_init` (`timers.c:219-233`) sets the callbacks with
flags 0: not pinned, not deferrable, not irqsafe.

|---|---|---|---|

| `timer_send_keepalive` | `data_received` (`:154-163`), if not pending; else `need_another_keepalive = true` | `KEEPALIVE_TIMEOUT*HZ` = 2500 | `any_authenticated_packet_sent` (`:170`); the retransmit's give-up (`:51`) |

by `wg_stop` (`device.c:124`) and `peer_remove_after_dead` (`peer.c:106`).

**The callbacks** (`timers.c:41-142`), each entered with its own timer
already detached (section 2.3):
- `wg_expired_retransmit_handshake` (`:41-77`): if
  `timer_handshake_attempts > MAX_TIMER_HANDSHAKES` (18): `del_timer`
  of the keepalive timer, `wg_packet_purge_staged_packets`
  (`send.c:333-340`: `tx_dropped += qlen`), and the zero-key timer armed
  if not pending; else `++attempts`, `wg_socket_clear_peer_endpoint_src`
  (`socket.c:308-314`), and
  `wg_packet_send_queued_handshake_initiation(peer, true)`
  (`send.c:55-83`: `is_retry` keeps the count; the rate limit at `:66`
  reads coarse boot time; `queue_work` on `handshake_send_wq`).
- `wg_expired_send_keepalive` (`:79-89`): `wg_packet_send_keepalive`
  (`send.c:221-240`: stage a zero-length skb if nothing is staged, then
  `wg_packet_send_staged_packets`, `:342-414`), then if
  `need_another_keepalive`: clear it and re-arm at +10 s.
- `wg_expired_new_handshake` (`:91-103`): clear the endpoint source, then
  `..._queued_handshake_initiation(peer, false)` (attempts reset,
  `send.c:58-59`).
- `wg_expired_zero_key_material` (`:105-120`): if `!is_dead`, `wg_peer_get`
  and `queue_work(handshake_send_wq, &clear_peer_work)` (a second queue
  drops the extra reference). The work,
  `wg_queued_expired_zero_key_material` (`:122-133`), runs
  `wg_noise_handshake_clear` (`noise.c:88-96`: index entry removed,
  handshake zeroed) and `wg_noise_keypairs_clear` (`noise.c:151-176`),
  then `wg_peer_put`.
- `wg_expired_send_persistent_keepalive` (`:135-142`): a keepalive if the
  interval is still nonzero.

No callback sends on the wire itself: each queues work (the handshake
send worker, the clear work, or through `wg_packet_create_data` the
encrypt worker), or arms and deletes timers. `handshake_send_wq` is
`WQ_UNBOUND` (`device.c:338-339`); the clear work and the send worker
share it, FIFO on one CPU.

### 2.2 Arming and deleting (`kernel/time/timer.c`)

- `mod_timer` (`:1240-1243`) is `__mod_timer(timer, expires, 0)`
  (`:1064-1190`). On a pending timer with the same `expires` it returns
  at once (`:1087`); otherwise it locks the base, `forward_timer_base`
  (`:1018-1021`: `base->clk` catches up to `jiffies`, or to
  `next_expiry` if a timer is overdue, `:994-1016`), and computes the
  bucket: same bucket → only `expires` is updated (`:1123-1130`); else
  detach (`:1144`), `timer->expires = expires` (`:1173`), enqueue
  (`:1181-1183`).
- **The wheel rounds up.** `calc_wheel_index` (`:584-631`) picks a level
  by `delta = expires - base->clk` (`LVL_START(n) = 63 << 3(n-1)`:
  63, 504, 4032, 32256, 258048; `:154-171`), and `calc_index` (`:567-580`)
  sets `bucket_expiry = ((expires >> 3n) + 1) << 3n`: a timer fires **no
  earlier than `expires + 1` and no later than `expires + 8^n`** ticks.
  At HZ 250: 5 s, 10 s and 15 s are level 2 (up to 64 ticks, 256 ms,
  late); 17–129 s level 3 (512 ticks, 2 s); 120–540 s level 4 (4096
  ticks, 16.4 s). `enqueue_timer` (`:655-690`) records the bucket in the
  timer's flags and lowers `base->next_expiry`.
- `timer_pending` is "hashed in a bucket" (`timer.h:145-148`).
  `del_timer` → `timer_delete` → `__timer_delete(timer, false)`
  (`timer.h:200`, `timer.c:1451`, `:1407-1430`): detach if pending, under
  the base lock. `timer_delete_sync` (`:1721`, `:1638-1680`) also waits for
  a running callback (`:1498-1520`, `base->running_timer`), which cannot
  happen on one CPU (a softirq is not preempted by a task).
- Without `NO_HZ_COMMON` there is one base per CPU (`NR_BASES 1`,
  `:195-204`), so every WireGuard timer is in `timer_bases[0]`.

### 2.3 Expiry: tick → `TIMER_SOFTIRQ` → `call_timer_fn`

1. The periodic tick (`tick_periodic`, `tick-common.c:86-103`) takes
   `jiffies_lock` and `jiffies_seq` (`jiffies.c:43-45`), advances
   `tick_next_period` (`:93`), `do_timer(1)` (`timekeeping.c:2325-2329`:
   `jiffies_64 += ticks`), `update_wall_time()` (`:98`), then
   `update_process_times` (`:101`; `timer.c:2514-2531`) →
   `run_local_timers` (`:2462-2505`): `hrtimer_run_queues` (low-res
   hrtimers expire here, in hardirq, `hrtimer.c:1944`), then
   `raise_softirq(TIMER_SOFTIRQ)` iff `jiffies >= base->next_expiry`
   (`:2502-2504`).
2. At interrupt exit, `__irq_exit_rcu` runs pending softirqs unless the
   interrupted context was itself in interrupt or had BH disabled
   (`softirq.c:652-665`, `:444-461`); otherwise they run at the next
   `local_bh_enable` (`:384-410`, the non-RT variant) or in ksoftirqd. `handle_softirqs`
   (`:536-600`) runs the vectors in bit order: `TIMER_SOFTIRQ` (bit 1)
   before `NET_RX_SOFTIRQ` (bit 3) (`interrupt.h:557-566`), each
   `h->action()` at `:579`. Vectors never nest: a hardirq during a softirq
   does not run softirqs (`in_interrupt()` at `:661`).
3. `run_timer_softirq` (`timer.c:2447-2460`) → `__run_timer_base`
   (`:2424-2435`) → `__run_timers` (`:2390-2422`): **while
   `jiffies >= base->clk && jiffies >= base->next_expiry`**, collect the
   buckets at `base->clk = next_expiry` (`collect_expired_timers`,
   `:1854-1876`), `base->clk++`, recompute `next_expiry`, and
   `expire_timers` per level (`:1813-1850`). So after a jump in `jiffies`
   every due bucket is run in one pass, in bucket order, and the pass is
   proportional to the number of due buckets, not to the ticks skipped.
4. `expire_timers`: `base->running_timer = timer`, **`detach_timer(timer,
   true)`** (`:1828-1829`: the callback sees its own timer not pending),
   the base lock dropped with irqs enabled (`:1845`), and `call_timer_fn`
   (`:1769-1811`), which calls **`fn(timer)` at `:1795`** between the
   `timer_expire_entry/exit` tracepoints.

### 2.4 Two clocks

- **`jiffies`** (`jiffies.h:85-86`) is a plain load. WireGuard uses it
  only for timer expiries (`timers.c:62,87,149,159,185,206,216`). It is
  the one place where a clock reaches kernel data without a reader
  function, so the choice-stream strategy left it a declared gap.
- **Coarse boot time**, `ktime_get_coarse_boottime_ns`
  (`timekeeping.h:141-144` → `ktime_get_coarse_with_offset(TK_OFFS_BOOT)`,
  `timekeeping.c:804-821`: `tkr_mono.base + offs_boot + xtime_nsec`,
  updated at the tick), is every other WireGuard clock
  (`wg_birthdate_has_expired`, `timers.h:24-29`; `send.c:25,29,39,66,89,
  102,134,365`; `receive.c:115-117,232,253`; `noise.c:396,637,650`;
  `noise.h:103`; `cookie.c:23,96-99,171,225`). Recorded as kind 208.
- `walltime_last_handshake` is real time (`timers.c:197`, kind 205),
  record-only.

Both advance at the tick: `jiffies` by `do_timer`, the coarse clocks by
`update_wall_time` → `timekeeping_advance` (`timekeeping.c:2188-2265`),
from the clocksource. Any time control must move them together, or the
C compares a stale boot time against a timer that already fired
(section 4.2).

## 3. Capture

### 3.1 Timer dispatch sections at `call_timer_fn`

A kernel change in `kernel/time/timer.c` (unanchored; `correspondence/
kcov.json` anchors `drivers/net/wireguard/*` and the FS files, not
`kernel/time/*`): in `call_timer_fn`,

```c
	struct kcov_dispatch_section section;	/* LEANUX */
	...
	trace_timer_expire_entry(timer, baseclk);
	kcov_dispatch_start(&section, fn);
	fn(timer);
	kcov_dispatch_stop(&section);
	trace_timer_expire_exit(timer);
```

exactly as `process_one_work` and the NET_RX vector are sectioned today
(`gen-choice-stream.py:662-698`). A section opens iff `fn` is in the
**armed dispatch set**, which gains the five `wg_expired_*` callbacks and
`wg_queued_expired_zero_key_material` (`harness/linux.py:37-39`,
`DISPATCH_SYMBOLS`; 12 of `DISPATCH_MAX` 16). The start record (kind 300)
carries `fn`'s address, resolved by the host to its symbol as for workers
(`evaluator/check.py:292-299`). Every other timer that the jump fires
(vmstat, `addrconf_verify`, neighbour GC, the clocksource watchdog, RCU)
opens no section and records nothing: the armed-set policy of the
strategy's section 4.4, unchanged.

**Nesting, resolved.** The strategy excluded `TIMER_SOFTIRQ` from the
vector section because a timer section inside it would nest
(`kcov.c:880`, the softirq double-start check). D3 sections the
**callback, not the vector**:
- two timer callbacks are sequential `call_timer_fn` calls, never nested;
- `TIMER_SOFTIRQ` and `NET_RX_SOFTIRQ` run one after the other in
  `handle_softirqs` (section 2.3, item 2), so a timer section and a NET_RX
  section are siblings. A callback that raises NET_RX (none of WireGuard's
  does; they queue work) would still not nest, because the vector runs
  after the timer vector returns;
- a tick that lands inside a **task** section (a worker, or the trace
  process's own syscall) gives a softirq section nested in it, which KCOV
  supports (`kcov_remote_start`, `kcov.c:872-884,926-929`: the task's mode
  is saved and the per-CPU softirq area used) and the D1 machinery already
  consumes for NET_RX (`Env.sectionOf`, `skipAmbient`). Section 5.4 says
  where the mirror accepts such a section and where it is a fail-noisy
  mismatch;
- a tick in the idle task (the trace process asleep in its wait) gives a
  top-level softirq section, as ksoftirqd's NET_RX does in D2's order (a).
  **To verify first** (stream K): a timer section opening and being moved
  to the remote area from the idle task's softirq.

`kcov_dispatch_start`'s own guard (`gen-choice-stream.py:468`) still
drops, counted, any section that would nest in a softirq section.

### 3.2 Records for firing

A fired timer is captured by its section: start (kind 300, `fn`), the
callback's choices (the retransmit's clock read at `send.c:66`, the
keepalive's at `send.c:365`, the jitter draw of a re-arm) and stop (kind
301). Which timers fired, and in what order, is therefore **captured**, as
the strategy wants for dispatch choices: nothing is predicted from
`jiffies` arithmetic alone.

### 3.3 The arm record (kind 303) [AGENT, a decision for the user]

`jiffies` reaches data at `mod_timer`. A hook at `mod_timer`'s entry
(`timer.c:1240`), gated like a section (`timer->function` in the armed
set, and only in a recording context), writes one record per call:
`kcov_choice_ip(303, _RET_IP_, {jiffies, expires}, 16)`. Its consumer frame
is `timers.c:37` (`mod_peer_timer`, inlined into its seven callers: one
site for all, like `timers.h:28`). Every WireGuard arm happens in a
recorded context (workers, NET_RX sections, timer sections; none in a
syscall), so the record count is exact.

What it buys, each with evidence in section 8:
- the mirror's **expiry data** becomes checkable: `expires` must equal the
  recorded `jiffies` plus the delay the mirror computes (`5*HZ + jitter`,
  `10*HZ`, ...). Today a wrong delay in the mirror is invisible (pending
  flags only): mutant D3-M8;
- the known survivor **C-M3** (no traversal re-arm after receiving)
  becomes rejected: the re-arm's record is missing;
- the environment knows **elapsed `jiffies`** exactly at every arm, so the
  firing window (section 5.3) does not rest on the trace's real-time
  bound, and natural firings within the bound are in the domain.

Without it (the fallback, section 11.4), the window uses the 4 s bound as
the elapsed-time bound and the three items above are lost.

### 3.4 The advance record (kind 304)

The time-advance operation (section 4.4) writes one record in the trace
process's task stream: `{jiffies before, jiffies after}`, resolved by kind
(like 300–302), consumed by `Env.advance`. It gives the environment the
exact `jiffies` after the jump.

### 4.2 The semantic rule for C

The steering rule (steering design, section 3): a supplied value must be a
possible output of its source, and must not interact with an unsteered
hidden input. For a scheduling or time choice: the resulting execution
must be one Linux can produce. After `advance(N)`:
- `jiffies`, coarse monotonic, boot and real time have moved by N ticks
  together, as N real ticks move them; the wheel's catch-up pass runs the
  due buckets in bucket order (`timer.c:2400-2420`), as after any stall;
  pending low-res hrtimers expire at the next tick (`hrtimer.c:1944`), as
  they do when time passes;
- no WireGuard code runs between the old and the new values: the advance
  is a trace operation issued at an idle point (the trace process in a
  syscall, workers idle, no softirq pending), so no C read observes an
  intermediate value that real time would have produced;
- the recorded clock values the mirror consumes are Linux's actual values.

Differences from N real seconds, each declared, none touching modeled
state:
1. the N·HZ intermediate ticks' side effects do not happen
   (`sched_tick`, `rcu_sched_clock_irq` (Tiny RCU here),
   `calc_global_load`, `account_process_tick`, `profile_tick`);
2. `CLOCK_MONOTONIC_RAW` (`tkr_raw`) does not advance; a recorded raw read
   (kinds 201, 209, 213) would show it; WireGuard has none;
3. the coarse clocks and `jiffies` move in one step rather than per tick.

A real-wait control (section 8) shows the same decisions and record kinds
as the virtual trace. Option D is kept as a later, separately justified
control for the suspend case (`wg_pm_notification` is out of scope).

### 4.3 Recommendation [AGENT]: option C, as a trace operation

`wg_advance {ticks}`: the guest calls `ioctl(3, KCOV_LEANUX_TIME_ADVANCE,
&ticks)` on its own KCOV descriptor (fd 3; the ioctl needs no instance
state, and the LEANUX cases sit before `kcov_ioctl`'s locked path,
`kcov.c:695-760`, as the steering ioctls do), then waits
`ADVANCE_WAIT_US` (100 ms, as `QUEUE_WAIT_US`; stream K measures). Within
the wait the next tick raises `TIMER_SOFTIRQ`, the due callbacks run in
sections, the work they queue runs in sections, and loopback delivers.
The remote records of all of it land in this operation (the guest reads
`remote[0]` after the wait, `guest.c:753-758`).

The kernel helper, `leanux_time_advance(ticks)` in `timekeeping.c`
(modelled on `do_settimeofday64`, `:1343-1383`, and
`timekeeping_inject_sleeptime64`, `:1782-1803`), with interrupts disabled
throughout so the tick cannot land between its two halves:
1. `raw_spin_lock(&timekeeper_lock)`, `write_seqcount_begin(&tk_core.seq)`,
   `timekeeping_forward_now(tk)` (`:692-711`), **`tk_xtime_add(tk,
   &delta)`** (`:144`) with `delta = ticks * TICK_NSEC` and
   `wall_to_monotonic` and `offs_boot` unchanged, so real, monotonic and
   boot time all move by `delta` (`tk_update_ktime_data`, `:624`:
   monotonic = xtime + wall_to_monotonic), then
   `timekeeping_update(tk, TK_CLEAR_NTP | TK_MIRROR | TK_CLOCK_WAS_SET)`
   (`:655-682`), unlock, and `clock_was_set(CLOCK_SET_WALL |
   CLOCK_SET_BOOT)` (`hrtimer.c:951`, `tick-internal.h:184-191`) as the
   sleep injection does;
2. `raw_spin_lock(&jiffies_lock)`, `write_seqcount_begin(&jiffies_seq)`,
   `tick_next_period += delta`, `do_timer(ticks)`, unlock: `tick_periodic`
   minus `update_wall_time` (done in step 1). `jiffies_lock`, `jiffies_seq`
   and `tick_next_period` are visible through `tick-internal.h`
   (`:22`), which `timekeeping.c` includes (`:28`).
3. The ioctl handler in `kcov.c` records kind 304 `{before, after}` and
   returns 0. It does not raise `TIMER_SOFTIRQ`: the next tick does
   (`timer.c:2502-2504`), as when time passes.

Clocks first, then `jiffies`: if the order were reversed and a tick could
land between, a callback would run against a stale boot time (the option
A defect). With interrupts disabled the order is belt and braces.

Steps of at most 2^31 ticks; the generator uses what the trace needs
(1400 ticks for a retransmit, 139100 for the zero-key timer). The
accumulation in `timekeeping_forward_now` is the regular one; the jump
itself does not go through the clocksource, so `max_idle_ns` does not
bound a step.

**Guest side.** The trace bound (`guest.c:51-53,733-738`,
`REKEY_BOUND_NS`, read from `CLOCK_BOOTTIME`) must subtract the virtual
advance: the guest keeps `advanced_ns` and compares real elapsed time.
The wait itself is `usleep` after the ioctl, so no sleep of the trace
process is in flight when time jumps. `rcu_cpu_stall_suppress` is not
needed: Tiny RCU has no stall detector; the hung-task and lockup detectors
are not configured.

**Why keep the 4 s bound.** It bounds real elapsed time, which the firing
window (5.3) uses where no `jiffies` is recorded, and it keeps the number
of traces per batch high on the TCG VM. With the arm record it is no
longer needed for correctness, only for throughput; lifting it for a
control class is section 8's option.

### 4.4 Fail-noisiness of the supply

- A section for a timer the mirror has as not pending, or not yet due:
  a hidden mismatch (the record is at a site the mirror does not expect).
- A timer certainly due that did not fire: `invariant` at the end of the
  advance operation (5.3).
- An advance whose window is ambiguous for some pending timer: the
  generator's domain filter marks the trace `unsupported` before Linux
  runs (5.3), so target traces are never timing-dependent.
- `jiffies` recorded by consecutive records must advance by at least the
  advances between them and by at most that plus the real-time bound: a
  tick handler that double-counted the jump (4.5) fails here.
- The dropped- and opened-section counters and `section_problems` apply
  to timer sections unchanged.

## 5. The mirror

### 5.1 Timer state: `expires`, not flags

The C's timer datum is `timer->expires`; `timer_pending` is "in a
bucket". The mirror mirrors that shape (`Leanux/WG/Types.lean:224-231`
today holds three `Bool` pending flags):

```lean
  /-- The five `struct timer_list`: `some expires` (absolute jiffies, from
      the arm record) while pending. -/
  timerRetransmitHandshake  : Option Nat := none
  timerSendKeepalive        : Option Nat := none
  timerNewHandshake         : Option Nat := none
  timerZeroKeyMaterial      : Option Nat := none
  timerPersistentKeepalive  : Option Nat := none
  timerHandshakeAttempts    : Nat := 0            -- today a cut (Send.lean:55)
  timerNeedAnotherKeepalive : Bool := false       -- unchanged
  sentLastminuteHandshake   : Bool := false       -- unchanged
```

`modPeerTimer pid timer delayTicks` (`Handshake.lean:313-316`) keeps its
two decisions and, inside the guard, consumes the arm record:
`let (j, e) ← hiddenArm .modTimerArm`; `e == j + delayTicks` else a
hidden mismatch ("timer expiry differs from Linux"); sets the field. The
jitter helpers return their value instead of discarding it
(`jitterBelowRekeyTimeout`, `:322-327`). `delTimer` clears a field.
`timer_pending` is `isSome`. `timing.timerMayExpire` and its three
`unsupported`s (`:335-336,344-345,377`) are retired: firing is modeled.

Every existing arm site maps one to one: `timersDataSent` (`:331-337`),
`timersDataReceived` (`:340-348`), `timersHandshakeInitiated`
(`:402-404`), `timersTraversal` (`:374-378`), `session_derived`
(`:415`, `sendHandshakeResponse`; and the response arm of the receive

### 5.3 The environment: fired timers from records [AGENT]

`Env.advance ticks` (the `wg_advance` operation, after `fdget 3` as every
fixture call does, `Syscalls.lean:50-60`):
1. consume the kind-304 record `(J₀, J₁)`; `J₁ − J₀ == ticks` else a
   hidden mismatch; remember `J₁` as the last known `jiffies`;
2. **timer sections**, while the next record starts a timer section for
   `fn`: the peer is the one whose timer of kind `fn` is pending and
   could be due (below); exactly one, else `unsupported` (several peers'
   timers of one kind in one pass: their order follows the arming order,
   which the mirror could compute but does not need yet). Clear the
   field, `runWorker (.timerX) (expiredX pid)`;
3. **the work they queued**, as today: `runSendWorkers` (the send worker
   and now the clear worker, FIFO on `handshake_send_wq`, ordered by
   records), `runCryptWorkers`, `deliverSent`;
4. **the must-fire check**: every timer still pending whose window is
   certainly past is an `invariant`.

**The firing window.** For a timer armed by a record `(j, e)` with delay
`d = e − j`, the wheel places it at `bucket_expiry ∈ (e, e + G]`, with
`G = 8^level(δ)` for the level `calc_wheel_index` picks from
`δ = e − base->clk` (section 2.2). `base->clk ≤ jiffies`, with equality
except inside a timer callback, where `clk ≥ e_F + 1` for the firing
timer `F` (`collect_expired_timers`, `timer.c:1856`; `clk++`, `:2416`).
So `δ ∈ [d, d + (j − e_F)]`, and the environment uses the level of the
largest value: `G = 8^level(d + lag)`, `lag = j − e_F` inside a callback,
0 elsewhere. The softirq that fires it runs at a tick with `jiffies` in
`[J_lo, J_hi]`: after an advance `J_lo = J₁ + 1` and `J_hi = J₁ + W`
(`W` = the wait in ticks, 25); at any other idle point `J_lo = J_last`
and `J_hi = J_last + R + W` (`R` = the real-time bound, 1000 ticks).
Then:
- **could fire** (a section is accepted): `e < J_hi`;
- **must fire** (missing section → `invariant`): `e + G ≤ J_lo`;
- **between**: the records decide, both outcomes being real (wheel
  rounding and tick phase). The generator keeps target traces out of this
  zone, and the domain filter marks a trace in it `unsupported`;
- **order** of two fired timers: if `e₁ + G₁ < e₂ + 1` the first must
  precede the second (`invariant` otherwise); overlapping windows accept
  either order.

Without the arm record (fallback), `j` is unknown: `J_lo − j ≤ R`, and the
window widens by `R` on the "must" side; `lag` is bounded by the advance.

**Idle points.** Timer sections are accepted at the places the guest
sleeps: inside `wg_advance`, and in the waits after `wg_inject`,
`wg_xmit`, `wg_set`, `wg_up` and before `wg_observe` (`Env.inject`,
`afterXmit`, `runSendWorkers`, `observe`), where a natural firing of a
short timer (a persistent keepalive of 1–4 s) lands. A timer section
anywhere else, nested at an arbitrary point of a worker's body or a
syscall, is a hidden mismatch: the mirror cannot run a callback mid-body,
and says so. The waits are where the kernel is idle, so this is the
common case by construction.

## 8. Evidence: what pays for itself

Each item names what no existing check catches.

**Mutants** (mirror, rejected only on D3 traces):
- D3-M1: the retransmit does not increment `attempts` (or `>` becomes
  `≥`): `d3_retransmit_gives_up` gives up a cycle early or late
  (`tx_dropped`, sections).
- D3-M2: the keepalive callback ignores `need_another_keepalive`: the
  second advance's section is for a timer the mirror has as not pending.
- D3-M3: firing does not clear the timer: the next `data_received`'s
  pending test differs, so an arm record is consumed or not.
- D3-M4: the clear worker clears keypairs but not the handshake: the
  index removal's control flow (A2) and the next initiation's state.
- D3-M5: send-side `keep_key_fresh` at 180 s instead of 120 s: no
  initiation at 121 s (behavior, A2).
- D3-M6: receive-side `keep_key_fresh` does not set
  `sent_lastminute_handshake`: an extra clock record on the second inject
  (hidden mismatch).
- D3-M7: `send_staged_packets` ignores `REJECT_AFTER_TIME`: a data message
  instead of an initiation (bytes).
- **D3-M8** (the arm record's evidence): `timer_new_handshake` armed at
  `KEEPALIVE_TIMEOUT*HZ` instead of `(KEEPALIVE_TIMEOUT + REKEY_TIMEOUT)*HZ`
  — invisible today, rejected only by the kind-303 `expires` check.
- **C-M3**, the known survivor (no traversal re-arm after receiving):
  rejected by a missing arm record on the receive path.

**Controls:**
- `d3_persistent_natural` vs `d3_persistent_keepalive`: a real-time
  firing and a virtual one show the same decision sequence and record
  kinds, differing only in clock values (the semantic argument of 4.2,
  witnessed).
- An advance with wait 0 (a guest variant): the sections land in the
  next operation and the mirror meets an unexpected section there.
- A trace whose advance falls in a timer's "between" zone: the domain
  filter marks it `unsupported` before Linux runs.
- The `jiffies`-progress check against a kernel that double-counts (Q1):
  not built; the check is the guard.

**Not claimed:** the opened-section count has no new mutant; the clear
worker's `peer_put` is covered by the existing refcount decisions.

## 9. Out of scope (fail-noisy), and why

| Item | Why it waits |
|---|---|
| A timer section nested at an arbitrary point of a worker or syscall | the mirror cannot run a callback mid-body; a mismatch names it |
| Several peers' timers of one kind in one softirq pass | order by arming time; one peer per kind per advance for now |
| Natural firing of a timer beyond the real-time bound | the bound stays for throughput |
| `wg_pm_notification`, `wg_vm_notification` (`device.c:66-109`) | no `PM_SLEEP`; option D is their control, later |
| Cookie secret and cookie ages, `under_load` | the cookie/DoS stage |
| `REKEY_AFTER_MESSAGES` / `REJECT_AFTER_MESSAGES` on send | 2^60 messages (D2) |
| `CLOCK_MONOTONIC_RAW` consistency | unread by WireGuard; declared |
| hrtimer-driven behaviour of the subsystem | hardirq, unrecordable (strategy section 7); none in WireGuard |
| Timer migration, `TIMER_MIGRATING`, several bases | one CPU, one base |
| `timer_delete_sync` waiting on a running callback | impossible on one CPU |

## 10. Risks

- **Medium: the tick handler's mode (Q1).** Checked on the first VM run
  and guarded by the `jiffies`-progress check.
- **Medium: other kernel timers the jump fires.** They run unsectioned
  (vmstat, `addrconf_verify`, neighbour GC, the clocksource watchdog,
  writeback). None touches wg0's state: wg0's addresses are static with
  infinite lifetimes (`guest.c:396-432`, `IFA_F_NODAD`), its link-local
  generation is `NONE` (`device.c:48`). The clocksource watchdog compares
  raw clocksource deltas, which the jump does not change. Fail-noisy if
  wrong: a cut or hidden mismatch.
- **Low: the catch-up pass's cost after 540 s.** Proportional to due
  buckets (`collect_expired_timers` jumps `clk` to `next_expiry`).
- **Low: the attempt-exhaustion trace's budget.** 20 waits of 0.1 s; if
  tight, the class is a stretch target.
- **Low: the mirror's timer representation change** touches D1/D2 code;
  the existing suites are the regression.
- **Sequencing:** every existing trace arms timers, so once the mirror
  consumes arm records the whole corpus needs the D3 kernel. The kernel
  stream lands first (section 11).
