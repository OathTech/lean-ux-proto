## 1. Target

**W1.** Every arm of `drivers/net/wireguard/netlink.c` that a natural netlink
message reaches and that the mirror today pins to a constant or to
`unsupported`, becomes a computed decision with a trace that reaches each
outcome: device lookup by ifindex, `-EBADR`, `-EOPNOTSUPP` for a non-WireGuard
device, `WGPEER_A_PROTOCOL_VERSION`, a peer without a public key, an allowed
IP missing an attribute, a malformed nested entry (the one rejection that is
the parse's own, not a policy length), unknown flag bits, endpoint attributes
of the wrong length or family, nonzero `sin6_flowinfo` and `sin6_scope_id`,
IPv4-mapped IPv6 endpoints. Observables: the operation's error code, the next
dump (data), and the decision stream (A2).

**W2.** The dump becomes the kernel's: a sequence of skbs of a known size,
each filled by one `wg_get_device_dump` call that stops at the first
attribute that does not fit, with the `next_peer` / `next_allowedip` cursors,
the `allowedips_seq` check, the dead-cursor exit, the `NLM_F_DUMP_INTR` flag,
and `NLMSG_DONE` placement. The guest steps a dump one `recvmsg` at a time so
a `wg_set` can run between two dump calls. Observables: the per-message
attribute structure and flags of every message (new), the coalesced device
state as today, and the decision stream, which now includes the
`-EMSGSIZE` outcomes.

Both stay inside the AGENTS.md altitude: no bytes, no C memory; attribute
*sizes* are modeled because they decide control flow (`nla_put` fails on
`skb_tailroom`), attribute *bytes* are not.

### 2.2 Generic netlink parsing: strict everywhere; which errors

- `wg_genl_family` sets no `.validate` flags (netlink.c:610-634), so the
  top-level attributes are parsed with `NL_VALIDATE_STRICT` for both the
  doit (genetlink.c:1093-1095 with `GENL_DONT_VALIDATE_STRICT` unset) and the
  dump (`genl_start`, :976-982, `GENL_DONT_VALIDATE_DUMP[_STRICT]` unset).
- `nla_parse_nested` (include/net/netlink.h:1310-1322) first rejects an entry
  without `NLA_F_NESTED` with `-EINVAL` ("NLA_F_NESTED is missing", :1315-1318),
  then parses strictly. This is the one rejection that is the parse's own
  check, not a policy-table length: **W1 uses it as the single sanctioned
  malformation** to reach the `ret < 0` arms at netlink.c:461 and :590.
- Under `NL_VALIDATE_STRICT` the policy tables produce (lib/nlattr.c):
  `-EINVAL` for an unknown type (`type == 0 || type > maxtype`, :604-631), a
  fixed-width integer of the wrong length (:413-419), a nested-policy
  attribute without `NLA_F_NESTED` or a non-nested one with it (:423-436),
  trailing bytes (:646-651), a `NUL_STRING` without NUL or longer than
  `IFNAMSIZ - 1` (:471-496); `-ERANGE` for a `NLA_BINARY` outside its declared
  range (`nla_validate_range_unsigned`, :170-237; the extack message for a
  `NLA_BINARY` is "binary attribute size out of range", :226-230):
  keys of a length other than 32 (`EXACT_LEN`), an endpoint shorter than 16,
  an allowed-IP address shorter than 4 (`MIN_LEN`). **All of these are P8**
  and stay out (section 5).
- A `GET_DEVICE` without `NLM_F_DUMP`, or a `SET_DEVICE` with it, is
  `-EOPNOTSUPP` from `genl_get_cmd` (genetlink.c:1179-1183) before any
  WireGuard code runs; also out.

### 2.3 The dump's skb budget (net/netlink/af_netlink.c)

- `__netlink_dump_start` runs `start` (:2427-2434; `wg_get_device_start`
  via `genl_start`), sets `dump_done_errno = INT_MAX` and **calls
  `netlink_dump` once inside the `sendmsg`** (:2437-2440), then returns
  `-EINTR` (:2450), which `netlink_rcv_skb` turns into "no ack" (:2551). A
  `start` error returns before that and is acknowledged as `NLMSG_ERROR`
  (:2556). **An error ack echoes the whole request unless the socket has
  `NETLINK_F_CAP_ACK` set** (:2478-2481: `payload += nlmsg_len(nlh)`, else
  `NLM_F_CAPPED`); today no guest socket sets it (`grep setsockopt
  harness/guest.c`: only `IPPROTO_IP/IPV6` options), so a failing 11 KB
  `wg_set` is acknowledged with an 11 KB message. 4.1 sets it on both
  generic-netlink sockets; every ack is then 36 bytes.
- Each `netlink_dump` allocates a fresh skb of `alloc_size =
  max(min_dump_alloc, NLMSG_GOODSIZE)`; if the socket's `max_recvmsg_len` is
  larger, it first *attempts* that size with `__GFP_NORETRY` and no direct
  reclaim (:2279-2290) and falls back on failure. The skb is trimmed to
  exactly `alloc_size` of tailroom (:2312). Generic netlink passes no
  `min_dump_alloc` (genetlink.c:1059-1066).
- `max_recvmsg_len` is the running maximum of the lengths passed to
  `recvmsg` on that socket, capped at `SKB_WITH_OVERHEAD(32768)` (:1940-1943).
- `NLMSG_GOODSIZE = SKB_WITH_OVERHEAD(PAGE_SIZE) = 4096 -
  SKB_DATA_ALIGN(sizeof(struct skb_shared_info))` (include/linux/netlink.h:270-273,
  include/linux/skbuff.h:255-257). `sizeof(struct skb_shared_info)` is
  **0x140 = 320** in the reference build (`llvm-dwarfdump-19
  --name=skb_shared_info .artifacts/kernel-net-choice/vmlinux`:
  `DW_AT_byte_size (0x0140)`; `CONFIG_MAX_SKB_FRAGS=17`), `SMP_CACHE_BYTES`
  = 64 (`X86_L1_CACHE_SHIFT=6`), so **`NLMSG_GOODSIZE = 3776`** and
  `SKB_WITH_OVERHEAD(32768) = 32448`.
- **Today the budget is not deterministic.** The guest reads every netlink
  reply with a 65536-byte buffer (`nl_buffer`, guest.c:218, :251 on `main`),
  so `max_recvmsg_len` is 32448 from the family lookup on, and every dump
  skb is 32448 bytes if an order-3 no-reclaim allocation succeeds and 3776 if
  it does not. On a fresh VM that allocation effectively always succeeds, so
  today's chunks are 32448 bytes in practice; the nondeterminism is one of
  memory pressure, not of observed behavior. The current `DUMP_BOUND` 3000
  (`Netlink.lean`) is below both sizes, which is why nothing has shown. W2
  removes the ambiguity by design (section 4.1).
- Before the callback, a second receive-buffer check: the fresh skb's
  `truesize` is charged to `sk_rmem_alloc`, and if the socket already held
  data and the total reaches `sk_rcvbuf` the call gives up without dumping
  (:2296-2300, `errout_skb`; the next `recvmsg` retries). For the stepped
  socket at most one chunk and one 36-byte ack are ever queued (4.9), so
  this and the half-`rcvbuf` test below always pass.
- After the callback: `-EMSGSIZE` with data in the skb means "more"
  (:2333-2334) — **dead for WireGuard**: `wg_get_device_dump` cancels its
  header before returning `-EMSGSIZE` (netlink.c:286-289), so `skb->len` is
  0, and with 3776 bytes of room the device part (≤ 128 bytes) always fits,
  so it never returns `-EMSGSIZE` at all; a positive return keeps the dump
  running; the skb is queued without `NLMSG_DONE` if the callback wants more
  **or fewer than `nlmsg_total_size(4) = 20` bytes remain** (:2339-2346);
  otherwise `NLMSG_DONE` carrying `dump_done_errno` is appended to the same
  skb (:2350, `netlink_dump_done` :2225-2250), `done` runs (:2370,
  `wg_get_device_done`) and `cb_running` clears (:2372).
- `recvmsg` dequeues one skb (`skb_recv_datagram`, :1916-1917; with
  `MSG_DONTWAIT` and nothing queued it returns `-EAGAIN` there), then, if the
  dump is still running and the receive queue is below half `sk_rcvbuf`,
  runs the next `netlink_dump` (:1974-1980). **So dump call k+1 runs inside
  the `recvmsg` that returns chunk k**, and dump call 1 runs inside the
  `sendmsg`. When the dump finished in call k but `NLMSG_DONE` did not fit,
  the `netlink_dump` inside recv k skips the callback (`dump_done_errno` is
  0, :2322) and only appends `NLMSG_DONE` to a fresh skb, runs `done` and
  clears `cb_running`; the recv that pops that skb runs no dump call.
- A second dump request on a socket whose dump is running gets `-EBUSY`
  (:2406-2407) as an `NLMSG_ERROR` queued behind the pending chunk; the
  running dump is untouched, and the recv that pops the ack still runs the
  next dump call (:1974).
- **The device reference.** `lookup_interface` returns `wg0` held
  (`dev_get_by_index/name`, netlink.c:59-64); `wg_get_device_done` drops it
  (:304-311), and `netlink_release` runs `done` for a dump still running
  (af_netlink.c:768-773). v1 claimed the trace child exits before `wg0` is
  deleted; **it is the other way round**: the trace process itself calls
  `delete_wg0` before `_exit` (guest.c:985, :1001; `task/l-m` :1012, :1026),
  with fd 7 and the stepped socket still open. An undrained stepped dump
  would hold the reference through `RTM_DELLINK`, and `netdev_run_todo` →
  `netdev_wait_allrefs_any` (net/core/dev.c:10798) would loop forever in the
  kernel — the process cannot take the watchdog's signal while it is there,
  so the whole guest hangs until the slot times out. The same holds for L's
  `wg_delete` issued while a dump is pending. 4.2 makes both impossible.

### 2.4 The consistency flag and the cursors

- `cb->seq = wg->device_update_gen` at every dump call (netlink.c:222);
  `genl_dump_check_consistent` (:229 → include/net/netlink.h:1193-1199) sets
  `NLM_F_DUMP_INTR` on a data message iff `prev_seq` is set and differs,
  i.e. iff `device_update_gen` changed between two dump calls. It changes only
  at netlink.c:523, reached by every `wg_set_device` that passes the lookup,
  flag and permission checks (device.c:323 initializes it to 1). The
  `NLMSG_DONE` header is checked too (af_netlink.c:2237) but can never carry
  the flag: the last callback set `seq` and `prev_seq` equal.
- `get_peer` on a cursor peer (`ctx->next_allowedip` set) skips the fixed
  part (:123-163) and resumes the allowed-IP list from the node (:175-176).
  `ctx->allowedips_seq` is taken at the first visit (:166-167) and compared
  at every later one (:168-169); a mismatch ends the peer **without** an
  allowed-IPs nest. `wg_allowedips_insert_v4/v6`, `remove_by_peer` and
  `free` bump `seq` (allowedips.c:262, :287, :298, :311); the mirror already
  keeps it (`AllowedIps.seq`, bumped at `AllowedIps.lean:179, :188, :260`
  and in `removeByPeer`).
- `next_peer_cursor` advances only past peers whose `get_peer` *completed*
  (:270-276); the peer that did not fit is retried in the next chunk from
  its cursor state. On the first chunk the cursor is NULL, so a first peer
  that does not fit leaves `ctx->next_peer` NULL and **the next chunk
  repeats the whole device part** (:231-252) before continuing the peer.
- A cursor peer removed between calls (`is_dead`, peer.c:89) cancels the
  peers nest and ends the dump (:264-268); the dump's reference is released
  at :282 (the last one, so the kref release path runs in that operation).
- `get_peer`'s `err:` path (:194-196) cancels the whole peer nest but does
  **not** reset `ctx->allowedips_seq` if it was already taken at :167
  (the `allowedips_nest` start failing at :171-173 is the case). The retry
  in the next chunk then sees `seq_changed` if any allowed-IP change
  happened in between, and dumps the peer without IPs.
- **The stale cursor (M1).** `get_peer` reads `ctx->next_allowedip` first
  (:110), and its null test decides whether the fixed part is emitted
  (:123); both cursors are cleared only when a `get_peer` *completes*
  (:191-192) — not on `err:`, not when the cursor's peer is removed, not at
  the dead-cursor or empty-list exits. The node pointer is dereferenced only
  at :175 (`list_for_each_entry_from`), after the `seq` check (:166-169). A
  split peer is never itself `ctx->next_peer` (the cursor advances only past
  completed peers, :270-276), so removing it does not trigger the
  dead-cursor exit; instead, two reachable shapes: (a) the split peer P is
  removed and a peer R follows the cursor — R is dumped as **`{public_key}`
  only**: the fixed part is skipped (stale node non-null), `remove_by_peer`
  bumped `seq` (allowedips.c:309-311; P had allowed IPs or it would not have
  split), so `no_allowedips` ends R without a nest, R's completion resets
  both cursors, and the peers after R are dumped normally; (b) P was the
  only peer (`ctx->next_peer` NULL) — the next call repeats the device part,
  finds the list empty, cancels the peers nest and ends the dump, the stale
  cursor still set. The stale pointer is never dereferenced in either shape
  because the `seq` check precedes :175 and a removal always bumps `seq`.

### 2.5 Attribute sizes the kernel computes

`nla_put` fails iff `skb_tailroom(skb) < nla_total_size(len) =
NLA_ALIGN(4 + len)` (lib/nlattr.c:1094-1097; `nla_reserve` has the same
test at :969); a nest start is a zero-length put
(include/net/netlink.h:1925-1950); `nla_nest_cancel` restores the tail
(:1975); `nlmsg_put` needs `nlmsg_total_size(payload)` (:955-958).
`CONFIG_HAVE_EFFICIENT_UNALIGNED_ACCESS=y`, so `nla_put_u64_64bit` adds no
pad attribute (include/net/netlink.h:2028-2074).

| Put (in C order) | Bytes |

| `genlmsg_put`: nlmsghdr 16 + genlmsghdr 4 | 20 |

| `WGDEVICE_A_IFNAME` (`strlen + 1`; "wg0" → 4) | `NLA_ALIGN(4 + len + 1)` = 8 |
| `WGDEVICE_A_PRIVATE_KEY`, `PUBLIC_KEY` (if `has_identity`) | 36 each |

| peer nest; `WGPEER_A_PUBLIC_KEY` | 4; 36 |

### 3.1 Trace schema (harness/trace.py, harness/wg.py; the mirror's Runner mirrors it)

## 4. W2 — multi-message dumps

### 4.1 Make the budget deterministic: one recv length

Fixture change, no kernel change: **every `recv` on the generic-netlink
sockets uses a buffer of exactly `NL_RECV_LEN = NLMSG_GOODSIZE = 3776`
bytes** (guest.c: `nl_receive`, `resolve_wireguard_family`, and the new
stepped recv). Then `max_recvmsg_len ≤ NLMSG_GOODSIZE`, the
`alloc_min_size < max_recvmsg_len` attempt at af_netlink.c:2282 never
happens, every dump skb is `alloc_skb(3776, GFP_KERNEL)` — a single page,
with reclaim, whose failure is `-ENOBUFS` and an environment failure, not
a silent fallback — and **every chunk has exactly 3776 bytes of room**. The
family lookup's reply is a few hundred bytes.

Two guest changes are **required** with this, not optional (C2):

1. `setsockopt(fd, SOL_NETLINK, NETLINK_CAP_ACK, &one, sizeof one)` on fd 7
   and on the stepped socket, at fixture setup (outside every window).
   Without it an error ack echoes the request (2.3): a failing `wg_set`
   larger than ~3.7 KB would be acknowledged with a message longer than the
   buffer; `netlink_recvmsg` truncates it (af_netlink.c:1946-1949, the rest
   is discarded), `NLMSG_OK` rejects the truncated header, and `nl_receive`
   blocks forever on its next `recv` (guest.c:251-253: no `MSG_DONTWAIT`,
   nothing else queued). With it every ack is `nlmsghdr` + `nlmsgerr` = 36
   bytes with `NLM_F_CAPPED`. `wg_set` observes only the error code, so no
   observation changes.
2. `nl_receive`, `resolve_wireguard_family` and the stepped recv use
   `recvmsg` and fail the trace (`environment_failure`, `netlink_truncated`)
   when `msg_flags & MSG_TRUNC` is set. v1 said the guest "checks `MSG_TRUNC`
   anyway"; it does not — `MSG_TRUNC` occurs once in guest.c, as a
   `recvfrom` flag on the UDP sender (:639). A chunk never exceeds its
   3776-byte skb and an ack is 36 bytes, so this is a fail-noisy guard, not
   a path.

Rejected alternatives: keeping 65536 (nondeterministic, section 2.3);
a per-trace `recv_len` (adds a hidden monotone per-socket state for no new
path: the same chunk sizes are reachable with 3776 and ≤ 256 IPs).

Consequence for existing traces: none in behavior (all current dumps are
under 3000 bytes), but every network trace's genl socket now reads this
way, so the whole WireGuard suite is the regression check for this step.

The constant is pinned twice: by the DWARF size (2.3) and by the first
boundary-targeting traces (4.8), whose `expect` labels fail loudly if the
room were anything else.

### 4.2 The stepped dump: two ops and a dump socket

- **`DUMP_FD = 8`**: a second `NETLINK_GENERIC` socket, opened (after the
  one at 7, no `SOCK_CLOEXEC`, `NETLINK_CAP_ACK` set) only for traces that
  contain a stepped op; the guest sees this from the parsed ops. Why a
  second socket: a `wg_set` ack queued behind a pending dump chunk on one
  socket would be received after the chunk, and that `recv` would run the
  next dump call (2.3), entangling the two ops. **Why a fixture descriptor
  rather than a temporary socket: the dump lives in the socket** (M4).
  `cb_running`, the queued chunk and `struct dump_ctx` are per-socket state
  that must persist from `wg_get_start` across the interleaved ops to the
  last `wg_get_recv`; a socket opened and closed around one op cannot carry
  it. v1's rationale (that `socket()`/`close()` would put `alloc_fd` /
  `fd_install` decisions into the op) was not the reason: L already opens
  its rtnetlink socket outside the window with no decision in the op
  (`task/l-m` guest.c:628-637, `Syscalls.lean:86-108`, `rtnetlinkRequest`).
- **Fixture shapes, and L's temporary socket.** For stepped traces the
  fixture record becomes `reserved [0..8]`, `free [9, rlimit-1]`; the check
  at harness/linux.py:396 learns the two shapes; `Runner.initialKernel` gets
  fd 8 as a fixture file `"generic-netlink-dump"` and `nextFd 9` for them
  (`task/l-m` Runner.lean:362-376 is the integrated form to extend). L's
  temporary socket takes the lowest free descriptor at or above `nextFd`
  (`rtnetlinkRequest`; `alloc_fd` in the guest), so **in a stepped trace it
  lands at 9**, in both the guest and the mirror, and is closed again before
  the next op, leaving `nextFd` at 9; `initialKernel` and `Syscalls.lean`
  agree by construction once fd 8 is marked open. Validator: stepped traces
  require `rlimit_nofile ≥ 9` (L's range is 8..1024, `task/l-m`
  trace.py:88), and `≥ 10` when they also contain `wg_create` or
  `wg_delete` — below that `socket()` fails with `-EMFILE` in the guest
  (`environment_failure`) and `rtnetlinkRequest` is `unsupported`; both
  fail-noisy, the static rule only says it earlier.
- **`wg_get_start`** `{"op", "device"?}` (opcode `OP_W2_GET_START`, section
  7): `sendmsg(DUMP_FD, GET_DEVICE, NLM_F_REQUEST|NLM_F_DUMP)`. ret 0 always:
  a start error is an `NLMSG_ERROR` queued for the next recv, and so is the
  `-EBUSY` of a start while the socket's dump is running (2.3), which is
  modeled (4.3, 4.9), not refused. Inside this op's window the kernel runs
  `__netlink_dump_start`, `wg_get_device_start` and dump call 1 — or only
  the `-EBUSY` arm.
- **`wg_get_recv`** `{"op"}` (opcode `OP_W2_GET_RECV`): one
  `recvmsg(DUMP_FD, 3776, MSG_DONTWAIT)`. ret 0, or `-EAGAIN` (errno 11,
  semantic) when nothing is queued. Inside this op's window the kernel runs
  the *next* dump call (if the dump is still running), including
  `wg_get_device_done` when it finishes. When the previous recv already
  finished the dump (DONE in its own skb, 2.3), or nothing is queued, no
  netlink.c code runs in the window; 4.9 says how A2 still sees the op.
- **Interleaving rule** (from 2.3): a `wg_set` placed between `wg_get_start`
  and the first `wg_get_recv` runs between dump calls 1 and 2; one placed
  between recv k-1 and recv k runs between dump calls k and k+1. `wg_set`
  stays on fd 7. Any other op may be interleaved too.
- **Observation** of `wg_get_recv` (ret 0): `"messages"`, the list of
  netlink messages that one recv returned, in order:
  `{"kind": "data", "flags": 2 | 18, "attrs": {...}}`,
  `{"kind": "done", "flags": 2, "error": e}`, `{"kind": "error", "error": e}`.
  `attrs` holds exactly the attributes present, in the kernel's names:
  `listen_port`, `fwmark`, `ifindex`, `ifname`, `private_key`, `public_key`
  when the device part is present; `peers` (a list) iff the `WGDEVICE_A_PEERS`
  nest is present (it is cancelled on the dead-cursor and empty-list exits);
  each peer exactly its attributes (`public_key`, and on a first visit
  `preshared_key`, `last_handshake`, `keepalive`, `tx_bytes`, `rx_bytes`,
  `protocol_version`, `endpoint` if any), with `allowed_ips` present iff the
  nest is present — possibly `[]`, which is what the kernel emits when the
  first IP does not fit (netlink.c:182). Absent and empty are different
  observations. The guest's `LEANUX_WG` record carries per message its
  kind, `nlmsg_flags` and payload; the harness decodes (`decode_messages`),
  never coalesces, and rejects anything the kernel cannot produce. Op 9's
  guest record becomes the same per-message record (4.5).
- **Dump-pending discipline (C1).** The guest keeps a counter for the
  stepped socket: `+1` per `wg_get_start`, `−1` per `done` or `error`
  message received (every start is answered by exactly one of them: the
  dump's `done`, a start error, or the `-EBUSY` ack, which answers the
  second start and leaves the first dump running — so "a dump is running"
  is "counter > 0"). Two guards: (a) at the end of **every** trace the trace
  process **closes the stepped socket and fd 7 before `delete_wg0`** (after
  the result lines, outside every window; `netlink_release` runs `done` and
  drops the device reference, 2.3) — so a trace may end mid-dump by design,
  including the deliberate `-EBUSY` trace, and the exit never waits on the
  dump's reference; (b) L's `wg_delete` with the counter above zero is an
  `invalid_input` failure before the `RTM_DELLINK` is sent (it would hang,
  2.3), and the mirror's `wgDelete` with `cbRunning` on either socket is
  `unsupported`. A second `wg_get_start` while running is **not** refused:
  it is the `-EBUSY` path, and with guard (a) it leaves nothing to drain.

### 4.3 Mirror: the dump machine and the put model

- **`Leanux/Kernel/NetlinkDump.lean`** (new): the per-socket state the C
  keeps in `netlink_sock` and `netlink_callback`, as a cut-point contract
  for af_netlink.c's dump loop, with exactly the three `Decision`
  constructors of 4.9 (`nlDumpStartBusy`, `nlRecvEmpty`,
  `nlRecvDumpRunning`); every other outcome of the loop is observed by A1
  through the messages:
  `NlSock { queue : List Skb, cbRunning : Bool, dumpDoneErrno : Int,
  prevSeq : Nat, ctx : DumpCtx }`, two instances (fd 7 and fd 8).
  `Skb { room : Nat, len : Nat, messages : List Message }` with
  `room = 3776` fresh.
  `netlinkDumpStart` (if `cbRunning`, queue `.error (-EBUSY)` behind the
  pending chunk and stop — af_netlink.c:2406-2409, the running dump
  untouched; else the start callback; on its error queue `.error e`; else
  `cbRunning := true, dumpDoneErrno := INT_MAX`, then `netlinkDump`);
  `netlinkDump` (fresh skb; if `dumpDoneErrno > 0` call the dump callback —
  the `-EMSGSIZE`-with-data case (:2333-2334) is `unsupported`, unreachable
  for WireGuard (2.3), so reaching it is a modeling defect; queue without
  DONE if the callback wants more or `room < 20`; else append DONE, run
  `done`, clear `cbRunning`); `netlinkRecvmsg` (pop one skb or `-EAGAIN`;
  then `netlinkDump` if `cbRunning`). `wgDelete` (L) with `cbRunning` on
  either socket is `unsupported` (C1, 4.2).
- **`DumpCtx { wg, nextPeer : Option PeerId, allowedipsSeq : Nat,
  nextAllowedip : Option NodeId }`**, the C's `struct dump_ctx`, kept in the
  socket. The cursor peer's reference is taken at netlink.c:281 and
  released at :282 / :310 through the existing `peerGet`/`peerPut`, so the
  kref release of a cursor peer removed in between runs in the right op.
  **C order in `getPeerDump` (M1):** `getPeerFirst := ctx.nextAllowedip.isNone`,
  evaluated right after the public-key put (netlink.c:123), so a stale
  cursor skips the fixed part exactly as the C does; the node is
  *dereferenced* — looked up in `Device.nodes` — only where the C
  dereferences it, at the list walk's start (:175), after
  `getPeerSeqUnset/Changed` (:166-169); a missing node there is
  `unsupported` (an unchanged `seq` implies the node is live, so a miss is a
  modeling defect). Both cursors reset only on completion (:191-192): not on
  the `err:` path, not when a peer is removed, not at the dead-cursor or
  empty-list exits (2.4).
- **Put model**: `Skb.put (n : Nat) : M Bool` returns `room < n` (the
  failure) and otherwise reserves; `nestStart` is `put 4` and records the
  saved room; `nestCancel` restores it. `wgGetDeviceDump` and `getPeerDump` /
  `getAllowedips` keep their decisions but compute each `*Put*Failed`,
  `*NoNest`, `getPeerAipFail`, `dumpGetPeerFail`, `dumpFirst`,
  `getPeerFirst`, `getPeerSeqUnset/Changed`, `dumpCursorSet/Dead`,
  `dumpOutNotDone/HasCursor`, `dumpDone` from the state, in the C's order
  and with the C's cancels (section 2.4 and 2.5 are the specification).
  `wgGetDevice` is split into `wgGetDeviceStart`, `wgGetDeviceDump` (one
  call = one chunk, returning `skb.len` / 0 / `-EMSGSIZE` as the C), and
  `wgGetDeviceDone`. `dumpSize` and `DUMP_BOUND` go.
- **`requireNotPending`** applies per dump call, as today, for every peer
  the call dumps: a stepped dump over a running device with a handshake
  worker pending stays `unsupported`, fail-noisy.
- **`Decision.lean`**: the dump-call decisions (`dumpNoHdr` … `dumpDone`,
  `getDoneHasWg`) become `repeatable`: in `wg_get` (op 9) several dump
  calls run in one op. The `get_peer` decisions already are.
- **The `NLM_F_DUMP_INTR` flag**: computed in `wgGetDeviceDump` from
  `prevSeq` and `deviceUpdateGen` (the C of include/net/netlink.h:1196-1198);
  data, not a decision (header line, unanchored).

### 4.5 `wg_get` (op 9) after W2

Unchanged interface: the guest's `nl_receive` loop drains to `NLMSG_DONE`
(now in 3776-byte chunks) and records **the same per-message record as the
stepped ops** (kind, `nlmsg_flags`, payload); the harness coalesces
(`decode_dump`, on top of `decode_messages`) to the canonical `device`
state, and the mirror runs the same dump machine to completion in the op
and coalesces with the same rule (`coalesce : List Message → Json`, one
function, used only here). The coalescing rule (M3): continued peers merge
as today; a repeated device part must be identical (fail-noisy otherwise);
**a peer without an `allowed_ips` nest gets `allowed_ips: []` after
coalescing**, so the `device` observation of every existing trace is
unchanged — only the per-message observation of 4.2 distinguishes absent
from empty; and `NLM_F_DUMP_INTR` on any message, an `error` message, or a
continuation without `allowed_ips` is rejected fail-noisy: nothing can
change `device_update_gen` or `allowedips.seq` between the dump calls of
one op 9 (only `wg_set_device` and the allowed-IP operations it calls do,
and the trace process, the sole writer, runs nothing else in the window).
Keeping `device` keeps the 1,288-trace corpus and the stage reports'
expectations meaningful.

A2 in op 9: several dump calls run in one op, so the `dump*` / `getPeer*`
decisions are repeatable and both outcomes may appear; check.py:618-621
then waives the "opposite outcome covered" test for them. **A2's arm
discrimination for the dump decisions therefore lives in the stepped ops**,
where one dump call runs per op; op 9 contributes "outcome witnessed" and
order only. This is why the `expect` labels of 4.8 go on stepped traces.

### 4.6 Harness decoder (harness/wg.py)

`decode_messages(records)` is the primitive: per message, kind, flags and
exactly the attributes present (`_decode_peer` no longer defaults
`allowed_ips`; the endpoint decoder as in 3.2). `decode_dump` for op 9
coalesces on top of it and restores `allowed_ips: []` for IP-less peers
(4.5), so op 9's `device` is what it is today. Unit tests in
`harness/test_wg.py` cover a continued peer, an empty `allowed_ips` nest, a
`{public_key}`-only continuation, a repeated device part, a cancelled peers
nest, a DONE in its own message, an `-EBUSY` ack between chunks, and the
op-9 rejections (`NLM_F_DUMP_INTR`, differing device parts, an `error`
mid-dump).

### 4.7 256 allowed IPs on the device, 32 per `wg_set`

The per-`wg_set` cap of 32 allowed IPs per peer **stays** (validator,
Runner, guest unchanged); the device accumulates up to 256 per peer across
sets. Three caps make a single 256-IP set unsafe (M2):
- the per-trace label cap `len(branches) > 4096` (evaluator/protocol.py:
  99-100): `branch` pushes one step per evaluation (Leanux/Kernel/Defs.lean:
  675), so a set reports every per-IP decision once per IP — about 9 in
  netlink.c (`aipNo*`, `aipV4*`/`aipV6*`, `peerAipsIter`, `peerAipParseErr`,
  `peerAipErr`, Netlink.lean:107-192) plus the trie's per-node decisions
  (AllowedIps.lean, 49 sites, several per node on the insert path);
- the KCOV area of 64K PCs per op (guest.c:32; `count >= CAPACITY - 1`
  fails the trace at :928) and its mirror `count < 65535` (harness/linux.py:
  396): a `wg_set` of n IPv6 IPs walks O(n²) trie node steps.
32 per set is known to fit all three (the current corpus); 256 would not.

Accumulation reaches every path of 4.4: the repeated device part needs 87
IPv6 IPs on the first peer (3 sets); a peer spanning into a third chunk
needs 177 (6 sets: 86 fit in chunk 1 after the device part, 90 in chunk 2
after the repeated device part, key and nests). **Measure first.** The
label count of a trace is computable offline (`executeTrace` is pure), so
the N2 generator runs the mirror on each candidate and rejects one over
4096 labels, printing the count; if the 177-IP target cannot be built under
the cap, the cap is raised in `protocol.py` with that measurement as the
evidence (it is a harness output-size guard, not a kernel constant) — not
before. The KCOV count is not computable offline; the guest's `CAPACITY`
failure is the fail-noisy backstop, and the per-set cap of 32 is what keeps
it from firing. A 256-IP dump in op 9 adds ≈ 4 labels per IP (`getAip*`)
and a few hundred PCs per IP, inside both bounds.

### 4.8 Generators (scripts/wg-n2-corpus.py; scripts/wg-n1-corpus.py for W1)

- A **boundary-targeting** generator builds configurations whose dump
  reaches a chosen room before a chosen put, using the size table of 2.5
  in Python (the same table the mirror uses; a wrong table makes a trace
  miss its target, not pass falsely). Each such trace states what it is
  for with `expect` labels (`get_allowedips.put_family_failed=1`, …).
- **`expect` on unsteered traces**: today `expect` requires `steer`
  (harness/trace.py:84-90). W2 lifts that (one validator line; the check
  already enforces `expect` on any agreeing trace). This pays: every
  targeted trace becomes self-verifying, and a wrong `NLMSG_GOODSIZE` fails
  at the first such trace instead of silently moving every boundary.
- Random traces (`evaluator/generate.py`'s WireGuard classes) gain stepped
  dumps with interleaved sets at low frequency; W1's selectors and
  malformations at low frequency, so the existing streams keep their
  content (the generator's seeding convention).

### 4.9 What W2 models in af_netlink.c, and what it does not

- **Three decisions in two functions, nothing else. [AGENT, for the user]**
  A2 requires every operation to cover an anchored file and to report at
  least one decision (evaluator/check.py:597-598, :614-615). A `wg_get_recv`
  that finds nothing (`-EAGAIN`), one that pops a lone `NLMSG_DONE` (2.3),
  and a `wg_get_start` answered by `-EBUSY` run no netlink.c code; without
  anchoring they cannot be in the domain at all, and with them go the "DONE
  in a separate skb", `-EBUSY` and `-EAGAIN` rows of 4.4 (a `Stop` drops the
  whole trace). W2 therefore lists `__netlink_dump_start` and
  `netlink_recvmsg` in `correspondence/kcov.json` with
  `nlDumpStartBusy` (af_netlink.c:2406; true span :2407, false span :2411),
  `nlRecvEmpty` (:1917; true :1918, false :1920) and
  `nlRecvDumpRunning` (:1974-1975; true :1976, false: no exclusive line, an
  empty span as at netlink.c:67). These are the stepped ops' own choice
  points — the mirror takes each of them (`.error (-EBUSY)` or start; pop or
  `-EAGAIN`; run the next dump call or not) — and every op 8 and 9 also
  reaches both functions (acks and dumps arrive through `netlink_recvmsg`)
  and reports `nlRecvEmpty=0` and `nlRecvDumpRunning=0/1`, which is correct
  and costs nothing. **This reverses v1** ("af_netlink.c stays unanchored").
  What pays for it: the three rows of 4.4 and N2-M13. The alternative —
  keep `-EBUSY`, `-EAGAIN` and the lone-DONE recv `unsupported` — loses
  those rows, and N2-M6 is then rejected only through op 9's `getDoneHasWg`
  placement rather than by a visible `done`. Section 8, question 8.
- `netlink_dump`'s own outcomes (the fresh skb, more/done, DONE placement)
  have no decisions: all are visible in the stepped messages (A1), and the
  `-EMSGSIZE`-with-data conversion is unreachable (2.3), an explicit
  `unsupported` in the mirror (4.3).
- `sk_rcvbuf`: at most one chunk skb and one 36-byte ack are queued at any
  time (each recv pops one and pushes at most one; a second start pushes
  one ack), so against the default `rmem_default` the half-`rcvbuf` test at
  :1975 always passes and the `rmem >= rcvbuf` abort at :2296-2300 never
  fires; stated, not modeled.

## 6. Risks

1. **`NLMSG_GOODSIZE`.** Pinned by DWARF (320) and by `expect`-labelled
   boundary traces; a wrong value fails loudly at the first of them.
2. **The recv-length change touches every network trace.** The full
   WireGuard suite plus the integrated branches' corpora are the
   regression; nothing should move (all dumps < 3000 bytes).
3. **fd 8 for stepped traces** changes the FS mirror's initial state only
   for those traces; `test_evaluation` gets a case for each fixture shape
   and one with L's temporary socket landing at 9 (4.2). There is no
   per-op alternative: the dump state lives in the socket.
4. **Workers during a stepped dump.** `requireNotPending` guards tx_bytes
   and endpoints; traces mixing `wg_inject` with stepped dumps are allowed
   only when the mirror can prove nothing is pending at each dump call.
5. **Repeatable dump decisions** in op 9: both outcomes of `dumpFirst`,
   `dumpPeerListEmpty`, … may appear in one op; the check's "both" rule
   covers repeatable decisions, but the first witnessed order is now per
   call — the order check compares first witnesses only, so this is sound.
   The price is 4.5's loss of arm discrimination in op 9; the stepped ops
   carry it.
6. **Generator cost.** Reaching 256 IPs on a peer takes eight 32-IP sets
   and long mirror runs (trie inserts); keep such traces to the targeted
   ones.
7. **Merge load.** `Netlink.lean`, `Runner.lean`, `trace.py`, `protocol.py`
   are edited by both streams in different regions (section 7 fixes the
   split first).
8. **The per-trace label budget** (4.7) may not admit the 177-IP target;
   the generator measures before building, and raising the 4096 cap is a
   user-visible change made only with that evidence.
9. **Anchoring af_netlink.c** (4.9) lists two functions every netlink op
   reaches; a wrong span there fails every WireGuard trace at once — loud,
   and caught by the first run of the existing suite.
10. **Dump-pending at trace end** is covered by the exit-time close (4.2).
    The hang of 2.3 needs an open dump socket *and* a `delete_wg0` in the
    same process; the close order excludes it, and a trace process that
    dies before either has its sockets released by the kernel at exit while
    no `delete_wg0` runs at all (only the trace process deletes).
